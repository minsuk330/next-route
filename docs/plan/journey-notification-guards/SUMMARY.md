# 발송 직전 재검증 (Phase 5 ⑤, M)

## 뭘 하나

알림을 보내기 직전에 세 가지를 더 확인한다 — lease 가 살아 있나, 사용자 명령으로 상황이 바뀌지
않았나, 접근 알림이라면 아직 그 말이 뜻이 있나. 뜻이 사라진 알림은 보내지 않고 취소한다.
마이그레이션 없음. 운영 발송은 이 PR 도 켜지 않는다.

## 왜

계산한 순간과 보내는 순간 사이에 세상이 바뀐다. 지금은 여정 종료와 경로 교체만 걸러서, lease 가
끝난 뒤에도 보내고 사용자가 이미 버스를 탄 뒤에도 "곧 도착해요"가 나간다.

## 핵심 결정

- **`commandVersion` 만 엄격 비교한다.** 평가 번호(`evaluationVersion`)는 ETA 숫자만 바뀌어도
  오르므로 취소 근거로 쓰면 정상 알림이 발송 전에 대거 죽는다 — 조용한 실패가 중복보다 나쁘다
- **접근 알림은 놓쳤거나 이미 탑승했으면 취소한다.** 둘 다 "곧 온다"가 무의미해진 경우다
- **위험 알림에는 상태 재확인을 걸지 않는다.** `MISSED` 알림을 상태로 거르면 자기 자신을 지운다
- **읽기를 늘리지 않는다.** lease·명령 번호는 이미 읽는 `journey_session` 행에 있고, 환승 조회는
  접근 알림일 때만 한다
- **취소 사유마다 이름을 붙인다.** 왜 안 갔는지 운영에서 갈라 봐야 한다

## 건드는 곳

`JourneyNotificationOutboxStateService`, `JourneyNotificationMetrics`, `PHASE-5.md`

## 리스크

- 검사를 하나 더할 때마다 "안 가는 알림"이 는다. 사유별 지표가 그것을 드러내는 유일한 창이다
- 취소도 시도 횟수를 하나 쓴다(②의 기존 계약). 재확인이 자주 취소하면 DEAD 가 빨라진다

## 검증법

`./gradlew test` 전체 + 버스 도착 알림·토스 경로 회귀. 핵심 4개: ①lease 만료 뒤 발송 0
②`commandVersion` 이 오르면 취소 ③**`evaluationVersion` 만 올랐으면 정상 발송** ④접근 알림은
놓침·탑승에 취소되고, 위험 알림은 `MISSED` 여도 정상 발송.
