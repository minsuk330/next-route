## 0. 범위가 넓어졌다

PHASE-6 의 ⑥은 "제안이 생겼다는 것을 알린다"였고 티어는 **M** 이었다. 그런데 그 알림이 실제로
울릴 상황이 **지금은 없다.**

제안은 **사용자가 "다시 찾아줘"를 눌렀을 때만** 만들어진다(SC-15 D6). 방아쇠(①)는 신호를 세기만
하고 제안을 만들지 않는다 — `RerouteTriggerEvaluator` 가 `RerouteProposalService` 를 **주입조차 받지
않는 것**이 그 계약을 구조로 지킨다. 그러니 알림을 붙여 봐야, 방금 버튼을 눌러 **그 화면을 보고 있는
사용자**에게 한 번 더 울릴 뿐이다.

그래서 ⑥의 범위를 **자동 생성까지** 넓힌다. 사용자가 앱을 껐어도 환승이 위험해지면 서버가 스스로
대안을 찾아 알린다 — 그것이 이 사다리를 만든 이유다. 티어는 **L** 로 올린다(요금·워커 부하·사용자
체감이 한꺼번에 열린다).

## 1. 확정 결정

| # | 결정 | 한 줄 근거 |
|---|---|---|
| D1 | **자동 생성을 연다.** 방아쇠가 cooldown 을 통과하면 서버가 후보 생성(③④)을 부른다 | 알림이 의미를 갖는 유일한 조건이다. 사용자 요청 제안은 이미 화면에 결과가 떠 있다 |
| D2 | 자동 생성은 **평가 트랜잭션 밖 + 전용 실행 풀**에서 돈다. 평가 스레드를 물지 않는다 | 후보 생성은 최악 6.5초(④)다. 평가 안에서 부르면 그 여정의 평가가 6.5초 잡히고 동시 여정 수만큼 곱해진다 |
| D3 | **자체 스위치**(`journey.reroute.auto.enabled`, 기본 꺼짐)를 둔다. `journey.reroute.enabled` 와 별개다 | 하나로 묶으면 "사용자 요청은 열고 자동은 닫는" 상태를 만들 수 없다. 요금이 붙는 쪽만 따로 잠근다 |
| D4 | **일일 호출 상한**을 Redis 카운터로 둔다(`RerouteAutoQuotaPort`). 소진되면 자동 생성만 막고 사용자 요청은 통과 | 방아쇠 발생률을 아직 아무도 모른다. 상한이 없으면 켜는 순간 요금이 먼저 온다 — `BusApiQuotaPort` 가 같은 이유로 존재한다 |
| D5 | 상한 저장소가 죽으면 **자동 생성을 막는다**(fail-closed). 사용자 요청은 영향 없다 | 열려 있으면 캐시 장애가 곧 요금이다. 막혀도 사용자는 버튼으로 같은 것을 얻는다 |
| D6 | 자동 생성은 **`TRIGGER` cooldown 키**를 그대로 쓴다. 사용자 요청 키와 섞지 않는다 | 이미 갈라 둔 이유가 그대로 유효하다 — 섞으면 자동 생성이 잠금을 태워 사용자 버튼이 2분간 거절된다 |
| D7 | 알림 체크포인트 **`REROUTE_PROPOSED`** 를 더하고, 논리 키에 **proposalId 를 접미사로** 붙인다. **마이그레이션 없음** | 키는 `varchar(255)` 문자열이다. PHASE-6 이 걱정한 `scopeId int` 제약은 <b>범위 칸의 제약이지 키의 제약이 아니었다</b> |
| D8 | 제안 알림을 만들 때 같은 환승의 **PENDING `MISSED` 를 밀어낸다** | `MISSED` 문구가 이미 "앱에서 새 안내를 확인하세요"다. 둘 다 나가면 같은 사건에 두 번 울린다 |
| D9 | 제안 알림 만료는 **제안 TTL 그대로**. 180초 바닥을 씌우지 않는다 | 제안 TTL 이 120초다. 바닥을 쓰면 이미 만료된 제안을 광고하고 사용자는 눌렀을 때 409 를 본다 |
| D10 | payload 는 **식별자와 `proposalId` 만**. 개선폭·후보를 담지 않는다 | 알림은 상태 저장소가 아니다. 늦게 도착한 push 가 낡은 숫자를 보여 준다 |
| D11 | 제안이 만료·교체되면 그 알림의 PENDING 을 **취소**한다(`proposal-expired`·`proposal-superseded`) | 사라진 제안을 광고하면 눌렀을 때 409 다 |
| D12 | 자동 생성이 **빈손이면 아무 일도 없다.** 실패도 조용하다 | 대안이 없을 때 "대안 없음"을 알리는 것은 소음이다. 기존 위험 알림이 이미 그 상황을 말한다 |

## 2. 자동 생성이 여는 것 셋 (D1·D2·D4)

### 요금

④는 유료 검색(ODsay)을 부른다. 지금은 **사용자가 누른 횟수**만큼 나가지만, 자동이면 **방아쇠가
통과한 횟수**만큼 나간다. 그 수를 아직 모른다 — shadow 방아쇠가 재고 있는 것이 정확히 그 값이다
(`journey.reroute.trigger.fired` / `admitted`).

그래서 상한을 **먼저** 박는다(D4). 상한은 두 겹이다.

- **여정당 하루 N건** — 한 사람이 계속 신호를 내는 경우를 막는다(cooldown 2분만으로는 하루 수백 건이 가능하다)
- **전체 하루 M건** — 요금의 천장. 소진되면 자동 생성만 멈추고 버튼은 계속 동작한다

### 워커 부하

후보 생성은 최악 6.5초다(검색 2초 + 기준선 1.5초 + 후보 3초). 평가는 여정마다 10~30초 주기로
돌고 워커 풀은 유한하다. **평가 스레드에서 부르면** 그 스레드가 6.5초 묶이고, 신호가 몰리는
시간대(출퇴근)에 평가 자체가 밀린다.

그래서 전용 bounded 풀에 던진다. 포화되면 **거절하고 지표만 남긴다**(`AbortPolicy`) —
`SearchHistoryExecutorConfig` 가 같은 판단을 이미 했다. 재탐색은 "있으면 좋은" 기능이라 밀려서
평가를 늦추는 것보다 그 한 건을 버리는 편이 낫다.

### 사용자 체감

안 물어봤는데 알림이 온다. 그 빈도를 정하는 것은 방아쇠 조건(`decision-window` 600초, cooldown
2분)과 상한(D4)이다. **대안이 없으면 알림도 없다**(D12) — 실제로 울리는 것은 "더 빠른 길이
있고, 개선폭이 300초를 넘을 때"뿐이다.

## 3. 알림 키 — PHASE-6 의 전제가 틀렸다 (D7)

PHASE-6 은 이렇게 적었다.

> `scopeId` 는 `int` 라 proposalId 를 그대로 담지 못하므로 … ⓐ 알림 행에 `proposal_id` 를 더하고
> 키 생성 규칙을 확장(마이그레이션 1건 추가), ⓑ … `MISSED` 알림 하나만 재사용

둘 다 필요 없다. 멱등 키는 **`logical_checkpoint_key varchar(255)` 문자열 칸**이고, 거기에
proposalId 를 붙이면 제안마다 다른 키가 된다.

```
journeyId:revision:TRANSFER:transferIndex:REROUTE_PROPOSED:{proposalId}
```

`scopeId` 는 그대로 `transferIndex` 다 — 범위는 여전히 "그 환승"이고, 그래야 기존 밀어내기·조회가
그대로 통한다. **취소도 논리 키로 한다**(D11): 제안을 접는 코드는 그 proposalId 를 알고 있으므로
같은 규칙으로 키를 다시 만들면 그 알림만 정확히 집는다.

## 4. 기각한 대안

| 대안 | 왜 기각했나 |
|---|---|
| ⑥을 원래 범위(알림만)로 끝낸다 | 알림이 울릴 상황이 없다. 통로만 만들고 "완료"라 부르면 사다리는 여전히 사용자 손가락에 매달려 있다 |
| 자동 생성을 평가 트랜잭션 안에서 부른다 | DB 커넥션을 잡은 채 외부 API 를 6.5초 기다린다. ③④가 트랜잭션 밖을 고집한 이유와 같다 |
| 자동 생성을 평가 스레드에서(트랜잭션 밖) 동기로 부른다 | 커넥션은 안 잡지만 평가가 밀린다. 신호가 몰리는 시간대가 정확히 평가가 바쁜 시간대다 |
| 상한 없이 켜고 지표를 본다 | 요금이 먼저 온다. shadow 를 깐 이유가 그것이었다 |
| 상한 저장소 장애 시 자동 생성을 통과시킨다 | 캐시 장애가 곧 요금이 된다. 막혀도 사용자는 버튼으로 같은 것을 얻는다(D5) |
| 자동 생성과 사용자 요청이 cooldown 키를 공유한다 | 자동 생성이 잠금을 태워 사용자 버튼이 거절된다. 이미 갈라 둔 것을 되돌리는 일이다 |
| 알림 행에 `proposal_id` 컬럼을 더한다(PHASE-6 ⓐ) | 키가 문자열이라 필요 없다. 마이그레이션 없이 같은 성질을 얻는다 |
| `MISSED` 알림만 재사용한다(PHASE-6 ⓑ) | `MISSED` 없이 뜨는 제안(다른 방아쇠 사유)을 못 알린다 |
| 대안이 없을 때 "대안 없음"을 알린다 | 소음이다. 기존 위험 알림이 이미 그 상황을 말하고 있다 |

## 5. 리스크

- **요금이 실측 없이 열린다.** 상한이 유일한 방어선이라 값이 곧 예산이다. 켜기 전에 Grafana 의
  `trigger.admitted` 를 보고 상한을 정한다 — 플래그가 꺼진 채 머지되므로 구현을 막지는 않는다
- **자동 생성이 사용자 요청과 같은 코드를 쓴다.** 한쪽을 고치면 다른 쪽이 함께 바뀐다. 그 편이
  두 벌보다 낫지만, "사용자 요청에서만 나던 오류"가 이제 워커 로그로도 온다
- **알림이 늘어난다.** 위험 알림 + 제안 알림이 같은 사건에서 연달아 날 수 있다. D8 이 아직 안 나간
  `MISSED` 만 막으므로, 이미 나간 뒤라면 두 번 울린다(순서가 자연스러워 허용)
- **워커 풀 포화는 조용한 실패다.** 거절된 자동 생성은 지표에만 남고 사용자는 아무것도 모른다 —
  그 상황에서도 버튼은 살아 있다는 것이 유일한 위안이다

## 6. 후속 과제

- **상한 값 튜닝** — 켠 뒤 며칠치 `admitted` 와 실제 제안 생성률을 보고 조정한다
- **자동 생성 사유별 성공률** — 어떤 방아쇠 사유가 실제로 쓸 만한 대안을 낳는지. 낮은 사유는
  방아쇠 조건에서 빼면 요금이 준다
- **알림 피로도** — 하루에 몇 번까지 허용할지. 지금은 cooldown·상한이 간접적으로 정한다
