# 자동 제안 + 알림 (Phase 6 ⑥)

## PR 두 개

| | 브랜치 | 티어 | 내용 |
|---|---|---|---|
| PR-1 | `feat/journey-reroute-auto-propose` | L | **방아쇠가 스스로 대안을 찾게 한다**(자동 생성) |
| PR-2 | `feat/journey-reroute-notification` | M | "더 빠른 길을 찾았어요" 알림 + 취소 |

## 뭘 하나

지금은 사용자가 **"다시 찾아줘"를 눌러야만** 대안을 찾는다. 이제 서버가 환승이 위험해지는 것을
보면 **혼자 찾아서 알린다.** 사용자는 앱을 껐어도 "더 빠른 길을 찾았어요" push 를 받고, 누르면
제안 화면에서 고른다.

## 왜 범위가 넓어졌나

PHASE-6 의 ⑥은 "알림만"이었고 M 이었다. 그런데 **그 알림이 울릴 상황이 지금은 없다** — 제안은
사용자가 버튼을 눌렀을 때만 생기고, 그 사람은 이미 결과 화면을 보고 있다. 알림 통로만 만들면
사다리는 여전히 사용자 손가락에 매달려 있다. 그래서 자동 생성을 함께 연다(**L**).

## 핵심 결정

- **자동 생성은 전용 풀에서 돈다.** 후보 생성은 최악 6.5초라 평가 스레드에서 부르면 출퇴근 시간에
  평가 자체가 밀린다. 풀이 포화되면 **그 한 건을 버리고 지표만 남긴다** — 재탐색이 밀려서 여정
  평가를 늦추는 것보다 낫다
- **자체 스위치 + 일일 상한 두 겹**(여정당·전체). ④가 유료 검색(ODsay)을 부르는데 방아쇠가 하루 몇
  번 도는지 **아직 아무도 모른다** — shadow 가 재고 있는 값이 정확히 그것이다. 상한이 없으면 켜는
  순간 요금이 먼저 온다. 상한이 소진되면 자동 생성만 막히고 **버튼은 계속 동작한다**
- **상한 저장소가 죽으면 자동 생성을 막는다**(fail-closed). 막혀도 사용자는 버튼으로 같은 것을 얻는다
- **대안이 없으면 알림도 없다.** 실제로 울리는 것은 "더 빠른 길이 있고 개선폭이 300초를 넘을 때"뿐이다
- **알림 키 문제는 마이그레이션 없이 풀린다.** PHASE-6 은 "컬럼을 더하거나 MISSED 를 재사용하거나"
  둘 중 하나로 봤는데, 멱등 키가 문자열 칸이라 거기에 proposalId 를 붙이면 끝이다
- **`MISSED` 와 겹치면 제안 알림이 이긴다.** 아직 안 나간 `MISSED` 를 밀어낸다 — 문구가 이미
  "앱에서 새 안내를 확인하세요"라 둘 다 보내면 같은 말을 두 번 한다
- **만료에 180초 바닥을 안 씌운다.** 제안 TTL 이 120초라 바닥을 쓰면 이미 만료된 제안을 광고한다

## 켜는 순서 (배포 계약)

1. `journey.reroute.enabled=true` — **사용자 요청 경로만** 열린다(요금은 누른 만큼)
2. Grafana 에서 `trigger.admitted` 를 며칠 본다 → 자동 생성 시 예상 호출 수
3. 그 수로 상한을 정하고 `journey.reroute.auto.enabled=true`
4. push 발송은 PHASE-5 §1.1 절차를 함께 탄다

**두 PR 모두 플래그가 꺼진 채 머지된다.** 켜는 것은 별도 판단이다.

## 리스크

- **요금이 실측 없이 열린다.** 상한이 유일한 방어선이라 그 값이 곧 예산이다
- **워커 풀 포화는 조용한 실패다.** 거절된 자동 생성은 지표에만 남는다(버튼은 살아 있다)
- **알림이 연달아 날 수 있다.** 이미 나간 `MISSED` 뒤에 제안 알림이 오는 경우는 막지 않는다 —
  "놓쳤다 → 대안 있다"는 순서가 자연스러워 허용한다
- 방아쇠 클래스에 "제안을 만들지 않는다"가 **계약으로 적혀 있다.** 코드와 함께 그 주석을 고쳐야 한다

## 검증법

스위치가 꺼져 있으면 방아쇠는 지금처럼 세기만 한다. 상한 소진·저장소 장애는 자동 생성만 막고
사용자 요청은 통과. 자동 생성이 실패해도 평가는 성공으로 기록된다. 같은 환승에 제안이 두 번 뜨면
알림도 두 건, 제안이 사라지면 알림도 취소, 사용자 요청 제안에는 알림 0건.
