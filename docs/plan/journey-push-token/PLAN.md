## 0. 이 PR 이 하는 일

Phase 5 의 첫 조각 = **"알림을 보낼 곳"**. 기기 push token 을 받아 두는 테이블 하나와
등록·해제 API 두 개. 발송 자체는 하지 않는다.

PR ②(`journey_notification` outbox)·③(FCM sender)이 둘 다 "이 사용자에게 보낼 token 목록"을
여기서 읽으므로 ①이 선행이다. ①이 머지되면 ②③은 병렬 가능.

현재 코드베이스에 push token·FCM 관련 코드는 **전혀 없다**
(`grep -ri "push_token\|pushToken\|fcm\|deviceToken" src/main` → V28 주석뿐). 전부 신설.

## 1. 확정 설계 결정 (재논의 금지)

| 항목 | 결정 | 이유 |
|---|---|---|
| token 유일성 | 부분 unique 인덱스 `(token) WHERE deleted_at IS NULL` | 통 unique 면 한 번 해제한 token 을 그 기기가 영영 재등록 못 한다. FCM 은 재설치·재로그인 뒤 같은 token 을 그대로 내줄 수 있다 |
| PUT 등록·교체 | native `INSERT … ON CONFLICT (token) WHERE deleted_at IS NULL DO UPDATE` | 한 문장 = race-safe, 예외 없음 → rollback-only 함정 회피. `BusAlertNotificationRepository.enqueue` 와 같은 이유 |
| 기기 물려주기 | 기존 행의 `user_id` 제자리 교체 | soft-delete+재삽입은 원자적이지 않고, 한 문장 CTE 로 합쳐도 "한 명령 안에서 unique 값 교체" 실패에 걸린다. 잃는 정보 없음(발송 감사는 ②의 outbox 소유) |
| DELETE 의미 | soft delete(`deleted_at`), `enabled=false` 아님 | 다른 사건이다. `deleted_at`=사용자가 해제, `enabled=false`=provider 가 `UNREGISTERED` 라 우리가 끔(③). DELETE 가 `enabled=false` 면 인덱스가 token 을 붙잡아 기기 물려주기가 막힌다 |
| DELETE 입력 | JSON 본문 `{"token":"..."}` → 204 | 쿼리 파라미터는 nginx access log·APM URL 에 token 평문이 남는다(REQUIREMENTS §6 마스킹) |
| 패키지 | 새 `domain/push` + `application/push` + `in/api/push` | token 은 알림이 아니라 **주소**. `domain/notification` 은 alert/outbox 세계이고 서비스가 이미 19개. ②가 그 디렉터리에 파일을 넣으므로 텍스트 충돌도 피한다 |
| 새 ErrorCode | 없음 | 비즈니스 예외를 던지지 않는다. 400·401 은 기존 핸들러가 처리 |

**의존 방향**: `notification → push` 단방향. token 은 알림을 읽지 않는다.

## 3. V39 SQL

경로: `src/main/resources/db/migration/V39__create_user_push_token.sql`

스타일은 `V35__create_journey.sql` 을 그대로 따른다 — 한국어 `--` 헤더로 *왜* 를 설명,
`id bigint generated by default as identity primary key`, 감사칼럼 `timestamp(6)`,
도메인 시각 `timestamptz`, enum 은 PG enum 이 아니라 `constraint <table>_<col>_check`,
인덱스 `uq_`/`idx_` 접두, 부분 인덱스 `WHERE deleted_at IS NULL`.

```sql
-- 여정 알림을 보낼 곳. 사용자 한 명이 여러 기기(=여러 token)를 가질 수 있다.
--
-- 기기 테이블을 두지 않는다(SC-1). 기기 식별자를 저장하지 않고 사용자와 token 만 묶는다.
-- 발송 대상은 "그 사용자의 살아 있는 enabled token 전부"다.
--
-- unique 는 (user_id, token) 이 아니라 token 하나다. 기기를 물려주거나 같은 폰에서 계정을
-- 바꿔 로그인하면 같은 token 이 다른 사용자로 다시 등록된다. 그때 앞선 소유자에게서 떼어 내지
-- 않으면 한 기기에 두 사람의 여정 알림이 간다. 복합 unique 로는 DB 가 그 사고를 못 막는다.
--
-- 유일성을 부분 인덱스로 거는 이유. 이 코드베이스는 소프트 삭제가 수동이라 해제한 token 의
-- 행이 표에 남는다. 통 unique 를 걸면 한 번 해제한 token 을 그 기기가 영영 다시 등록하지
-- 못한다 - FCM 은 재설치·재로그인 뒤에도 같은 token 을 그대로 내줄 수 있다.
--
-- enabled 와 deleted_at 은 다른 사건이다.
--   deleted_at    = 사용자·앱이 스스로 해제했다(로그아웃, DELETE /api/me/push-token)
--   enabled=false = provider 가 UNREGISTERED 라고 답해 우리가 껐다(Phase 5 PR3)
-- 껐다고 지우지 않는다. 그 수를 세야 하고(PR7 지표), 같은 token 이 다시 등록되면 되살려야 한다.
--
-- token 은 개인식별에 준해 다룬다. 로그·telemetry·metric tag 에 싣지 않는다(REQUIREMENTS 6장).

CREATE TABLE user_push_token (
    id           bigint generated by default as identity primary key,
    created_at   timestamp(6) not null,
    updated_at   timestamp(6) not null,
    deleted_at   timestamp(6),
    user_id      bigint       not null references users (id),
    platform     varchar(20)  not null
        constraint user_push_token_platform_check
            check (platform in ('ANDROID', 'IOS')),
    provider     varchar(20)  not null default 'FCM'
        constraint user_push_token_provider_check
            check (provider in ('FCM')),
    token        varchar(512) not null
        constraint user_push_token_token_blank_check
            check (length(btrim(token)) > 0),
    -- iOS 개발 빌드는 APNs sandbox token 을 받는다. 운영 설정으로 보내면 실패하므로 구분해 둔다.
    environment  varchar(20)  not null default 'PRODUCTION'
        constraint user_push_token_environment_check
            check (environment in ('PRODUCTION', 'DEVELOPMENT')),
    enabled      boolean      not null default true,
    last_seen_at timestamptz  not null
);

-- token 하나는 살아 있는 행 하나. 재등록 upsert 의 ON CONFLICT 중재자이기도 하므로
-- 술어(WHERE deleted_at IS NULL)가 upsert 문의 추론 절과 글자 그대로 같아야 한다.
CREATE UNIQUE INDEX uq_user_push_token_token
    ON user_push_token (token)
    WHERE deleted_at IS NULL;

-- 발송 대상 조회 경로(Phase 5 PR2·PR3). 사용자 한 명의 살아 있는 enabled token 전부.
CREATE INDEX idx_user_push_token_user_enabled
    ON user_push_token (user_id)
    WHERE enabled = true AND deleted_at IS NULL;
```

컬럼 집합은 `journey-navigation/PLAN.md:177` 이 확정한 것과 동일 — user, platform,
provider(FCM), token, environment, enabled, lastSeenAt.

`varchar(512)`: FCM registration token 실측 150~350자, 상한 미문서. DTO `@Size(max = 512)` 와
**정확히 같게** 유지한다(어긋나면 400 이 아니라 500 `22001 value too long`). btree 인덱스 항목
상한(~2704 bytes) 아래라 unique 인덱스도 안전.

### 4.3 `domain/push/repository/UserPushTokenRepository.java`

```java
public interface UserPushTokenRepository extends JpaRepository<UserPushToken, Long> {

    /**
     * 등록·교체를 한 문장으로 한다.
     *
     * <p>같은 token 이 이미 살아 있으면 소유자를 이 사용자로 바꾼다. 기기를 물려주거나 같은 폰에서
     * 계정을 바꿔 로그인하는 경우가 실제로 있고, 그때 앞선 소유자를 떼어 내지 않으면 한 기기에 두
     * 사람의 알림이 간다.
     *
     * <p>찾고 나서 저장하는 방식을 쓰지 않는 이유. 새 token 을 두 요청이 동시에 등록하면 둘 다
     * "없음"을 읽고 둘 다 INSERT 해 한쪽이 unique 위반으로 죽는다. 트랜잭션이 이미 rollback-only 라
     * 그 자리에서 되살릴 수도 없다. ON CONFLICT 는 그 충돌을 SQL 안에서 흡수한다
     * ({@code BusAlertNotificationRepository#enqueue} 와 같은 이유).
     *
     * <p>ON CONFLICT 뒤의 WHERE 는 중재 인덱스 추론 절이다. uq_user_push_token_token 의 술어와
     * 글자 그대로 같아야 한다 - 다르면 "no unique or exclusion constraint matching" 으로 실패한다.
     *
     * <p>enabled 를 true 로 되돌린다. provider 가 UNREGISTERED 라고 해서 껐더라도, 앱이 지금 이
     * token 으로 등록하고 있다는 사실이 그 판정보다 새롭다.
     *
     * <p>JPA auditing 을 타지 않으므로 created_at·updated_at 을 직접 넣는다.
     *
     * <p>{@code @Modifying} 이 아니다(RETURNING). 반드시 {@code @Transactional} 안에서 부른다.
     *
     * <p>남은 위험: READ COMMITTED 에서 중재 행이 동시에 DELETE 되는 좁은 경우 unique 위반이
     * 여전히 날 수 있다(PostgreSQL 문서화된 코너 케이스). 앱 실행당 1회 호출이라 확률이 무시할
     * 수준이므로 재시도 루프를 두지 않는다.
     */
    @Query(value = """
            INSERT INTO user_push_token
                (user_id, platform, provider, token, environment, enabled, last_seen_at,
                 created_at, updated_at)
            VALUES (:userId, :platform, :provider, :token, :environment, true,
                    :seenAt, :now, :now)
            ON CONFLICT (token) WHERE deleted_at IS NULL
            DO UPDATE SET user_id      = EXCLUDED.user_id,
                          platform     = EXCLUDED.platform,
                          provider     = EXCLUDED.provider,
                          environment  = EXCLUDED.environment,
                          enabled      = true,
                          last_seen_at = EXCLUDED.last_seen_at,
                          updated_at   = EXCLUDED.updated_at
            RETURNING id
            """, nativeQuery = true)
    Long register(@Param("userId") Long userId, @Param("platform") String platform,
                  @Param("provider") String provider, @Param("token") String token,
                  @Param("environment") String environment,
                  @Param("seenAt") Instant seenAt, @Param("now") LocalDateTime now);

    /** 해제. 소유자를 조건에 넣는다 - 남의 token 을 꺼 버릴 수 있으면 안 된다. 0행이어도 정상. */
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query(value = """
            UPDATE user_push_token
               SET deleted_at = :now, updated_at = :now
             WHERE user_id = :userId AND token = :token AND deleted_at IS NULL
            """, nativeQuery = true)
    int unregister(@Param("userId") Long userId, @Param("token") String token,
                   @Param("now") LocalDateTime now);

    /** 발송 대상(Phase 5 PR2·PR3). enabled 이고 살아 있는 token 전부 - 조건이 둘 다 필요하다. */
    List<UserPushToken> findByUserIdAndEnabledTrueAndDeletedAtIsNull(Long userId);
}
```

Javadoc 에 후속 과제 한 줄: **계정 삭제(탈퇴) 경로가 생기면 그 사용자의 모든 행을 soft delete
해야 한다**(`journey-navigation/PLAN.md:627`). 지금은 탈퇴 서비스가 코드베이스에 없으므로
(`grep -ri "탈퇴\|withdraw\|deleteAccount" src/main` 무결과) 죽은 메서드를 만들지 않는다.

`register` 반환이 `Long`(단수)인 이유: `DO UPDATE` 는 항상 1행. `enqueue` 는 `DO NOTHING` 이라
0행이 가능해서 `List<Long>` 이다.

@Service
@RequiredArgsConstructor
public class PushTokenService implements RegisterPushTokenUseCase, UnregisterPushTokenUseCase {

    private final UserPushTokenRepository repository;
    private final Clock clock;                    // common/config/ClockConfig

    @Override @Transactional
    public void register(Long userId, RegisterPushTokenCommand command) {
        Instant now = clock.instant();
        repository.register(userId, command.platform().name(), command.provider().name(),
                command.token(), command.environment().name(),
                now, LocalDateTime.now(clock));
    }

    @Override @Transactional
    public void unregister(Long userId, String token) {
        repository.unregister(userId, token, LocalDateTime.now(clock));   // 0행이어도 성공
    }
}

`@Pattern` 없음 — FCM 이 token 알파벳을 문서화하지 않아 정규식은 미래 포맷을 막는다.
trim 은 `toCommand()` 에서, DB `btrim` 체크가 최후 보루.

```java
/**
 * 푸시 token 등록·해제.
 *
 * <p>token 은 URL 에 담지 않는다. 경로·쿼리는 접근 로그와 프록시 로그에 그대로 남는다.
 * DELETE 가 본문을 받는 이유가 그것이다(REQUIREMENTS 6장).
 *
 * <p>사용자 ID 는 JWT 에서만 온다. 본문으로 받으면 남의 계정에 token 을 심을 수 있다.
 */
@RestController
@RequestMapping("/api/me/push-token")
@RequiredArgsConstructor
@Tag(name = "[앱] 푸시 토큰")
public class PushTokenController {

    private final RegisterPushTokenUseCase registerPushTokenUseCase;
    private final UnregisterPushTokenUseCase unregisterPushTokenUseCase;

    @PutMapping
    public ResponseEntity<Void> register(@AuthenticationPrincipal Long userId,
                                         @Valid @RequestBody RegisterPushTokenRequest request) {
        registerPushTokenUseCase.register(userId, request.toCommand());
        return ResponseEntity.noContent().build();
    }

    @DeleteMapping
    public ResponseEntity<Void> unregister(@AuthenticationPrincipal Long userId,
                                           @Valid @RequestBody UnregisterPushTokenRequest request) {
        unregisterPushTokenUseCase.unregister(userId, request.token());
        return ResponseEntity.noContent().build();
    }
}
```

`unregister` 가 0행이어도 **204**. 멱등이고, 404 를 주면 임의 token 문자열의 존재 여부가 샌다.

## 9. 구현 기록 (플랜과 달라진 것)

1. **`register` 를 트랜잭션 밖에서 부르면 실패한다는 테스트를 뺐다.** 실제로는 실패하지 않는다 —
   Spring Data 가 `@Query` 메서드에 read-only 트랜잭션을 열어 주고, PostgreSQL 세션이 실제로
   read-only 로 설정되는 것은 아니라 native INSERT 가 그대로 통과한다. 계약이 아닌 것을 잠그는
   테스트라 제거했다. 레포지토리 Javadoc 의 "`@Transactional` 안에서 부른다" 지침은 유지
   (`BusAlertNotificationRepository#enqueue` 와 같은 관례).
2. **검증 실패 응답 코드는 `COMMON_VALIDATION_ERROR`.** 플랜에 `COMMON_INVALID_REQUEST` 로 적었으나
   `GlobalExceptionHandler#validationResponse` 가 실제로 쓰는 값은 `VALIDATION_ERROR` 다.
3. **보안 가드 실효성을 실측했다.** `SecurityConfig` 의 `/api/me/**` 줄을 임시로 지우고 돌리면
   401 테스트 두 개가 정확히 깨진다(그 외 9개는 통과). 규칙이 있어야만 통과하는 테스트임을 확인.

전체 `./gradlew test` 통과(2분 50초).
