## 0. 이 칸이 하는 일

②③④가 만든 것은 전부 **제안**이다. 아직 아무 여정도 바뀌지 않았다. ⑤는 사용자가 고른 제안
하나를 받아 **실제로 안내 경로를 갈아끼운다.** 사다리에서 처음으로 여정이 바뀌는 칸이다.

바뀌는 것이 다섯이다 — 개정본(`journey_revision`), 단계(`journey_leg`), 노선 후보
(`journey_leg_route_option`), 환승(`transfer_connection`), 그리고 **지도에 그려지는 geometry**.
다섯이 어긋나면 화면이 조용히 틀린다. 그래서 한 트랜잭션이다.

## 1. 확정 결정

| # | 결정 | 한 줄 근거 |
|---|---|---|
| D1 | **전용 엔드포인트**(`POST …/reroute-proposals/{proposalId}/accept`). 이벤트 경로(`ApplyJourneyEventRequest`)로 받지 않는다 | 수락은 앱이 관측한 사실이 아니라 사용자의 의사결정이다. 같은 통로로 받으면 GPS 가 보낸 전이와 같은 재전송 규칙을 태우게 된다 |
| D2 | 요청은 `proposalId` **와 `candidateId`** 를 함께 받는다. 없으면 거절 | 사용자가 고르지 않은 경로로 여정이 바뀌는 것이 이 기능에서 가장 나쁜 사고다 |
| D3 | 새 개정본은 **전체 단계를 복제**한다. 남은 구간만 넣지 않는다 | 여정 조회가 `(journeyId, routeRevision)` 로 단계 전부를 읽는다. 남은 구간만 넣으면 사용자 화면에서 **지나온 길이 통째로 사라진다** |
| D4 | 교체 시작점은 후보의 `fromLegIndex`(③은 `waitLegIndex`). **`fromLegIndex < currentLegIndex` 면 409** | 이미 지나간 지점부터 갈아끼우면 진행 중인 단계가 사라진다. 같으면(그 대기 단계가 지금 단계) 아직 안 탔으므로 유효하다 |
| D5 | **개정본 스냅샷은 합성한다** — 옛 스냅샷의 앞 구간 + 후보 경로. 후보 경로만 저장하지 않는다 | geometry·④의 좌표 찾기가 전부 "스냅샷을 다시 쪼개면 저장된 단계가 나온다"에 기대고 있다(§3) |
| D6 | geometry 원천을 `JourneySession.routeSnapshot` → **`ACTIVE` `JourneyRevision.routeSnapshot`** 으로 옮긴다 | 세션 스냅샷은 시작 시점 원본이고 **영원히 안 바뀐다.** 그대로 두면 수락해도 지도에 옛 경로가 계속 내려간다 |
| D7 | 수락 트랜잭션에서 넷을 다시 본다 — 제안 `ACTIVE` · 만료 · `baseCommandVersion` · `routeRevision`. 하나라도 어긋나면 **409 + 최신 스냅샷** | 제안이 만들어지고 사용자가 누르기까지 최대 2분이 있다. 그 사이 버스를 타고 여정은 움직인다 |
| D8 | 동시 수락은 **제안 상태 조건부 update 한 문장**으로 한 번만 통과시킨다 | 두 요청이 동시에 통과하면 개정본이 두 번 올라 단계가 두 벌 생긴다. 잠금 대신 이미 있는 상태 칸을 쓴다 |
| D9 | 같은 `(proposalId, candidateId)` 재전송은 **200 + 최신 스냅샷**. 다른 `candidateId` 면 409 | 네트워크 재시도로 개정본이 두 번 오르면 안 되지만, 이미 자기가 고른 그대로 반영된 것을 오류로 돌려주면 앱이 되돌릴 방법이 없다 |
| D10 | `journey_revision.reason` 어휘는 **`ROUTE_OPTION_ACCEPTED` · `REMAINING_PATH_ACCEPTED`** 둘 | 엔티티 주석이 "Phase 6 이 정한다"고 비워 뒀다. 종류를 못 가르면 "왜 경로가 바뀌었나"를 운영에서 못 읽는다 |
| D11 | 이전 개정본의 **pending 알림을 취소**하고 제안을 전부 접는다. 평가는 즉시 다시 걸린다 | Phase 5 가 넣어 둔 `route-changed` 취소 규칙이 **처음으로 실제 동작하는 자리**다 |
| D12 | 상태머신의 `REROUTE_ACCEPTED` 는 **계속 거절**로 둔다. 대신 수락 트랜잭션이 `journey_event` 를 직접 남긴다 | 이벤트 통로를 여는 것은 D1 을 무르는 일이다. 이력은 남겨야 "왜 이 시각에 경로가 바뀌었나"를 나중에 물을 수 있다 |

## 2. 왜 전용 엔드포인트인가 (D1)

`ApplyJourneyEventRequest` 는 **앱이 관측한 사실**을 보내는 통로다 — "3번 단계에서 4번 단계로
넘어갔다", "여정을 취소했다". 그 값들은 GPS 엔진이 만들고, 재전송·중복 판정 규칙(`eventId` 멱등)이
그 성질에 맞춰져 있다.

수락은 성질이 다르다. **사용자가 화면에서 고른 것**이고, 고른 대상(`candidateId`)이 있으며, 서버가
그 순간 외부 데이터 없이 되짚어야 할 조건이 넷이다(D7). 이것을 이벤트 payload 에 욱여넣으면
`JourneyCommand` 에 재탐색 전용 칸이 생기고, 상태머신이 "후보 하나를 골라 경로를 다시 만드는 일"까지
알게 된다. 상태머신은 **단계 경계를 옮기는 기계**로 두는 편이 낫다.

그래서 통로는 따로 두되, **이력은 같은 곳에 남긴다**(D12). `journey_event` 에 `REROUTE_ACCEPTED`
행이 남아야 여정 하나의 시간축이 한 줄로 읽힌다.

## 3. 합성 스냅샷 — ⑤에서 가장 조용히 틀릴 곳 (D5)

### 무엇이 문제인가

`journey_revision.routeSnapshot` 은 경로 원본(`PathResult`) 하나다. 이 값을 쓰는 곳이 둘인데
**둘 다 "다시 쪼개면 저장된 단계가 그대로 나온다"를 가정한다.**

- `JourneyNavigationGeometryService` — 스냅샷을 `compileDetailed` 로 쪼개 **단계 번호 → 원본 구간
  번호** 표를 만들고, 그 구간의 좌표로 지도를 그린다
- `JourneyWaypointResolver`(④) — 같은 방법으로 환승 정류장의 좌표를 찾는다

새 개정본의 스냅샷에 **후보 경로만** 넣으면 그 표가 어긋난다. 후보 경로는 환승 지점부터 시작하므로
쪼개면 0번부터 번호가 매겨지는데, 저장된 단계는 앞 구간을 포함해 `fromLegIndex` 부터 이어진다.
그러면 지도는 **3번 단계 자리에 0번 구간의 좌표**를 그린다 — 오류 없이, 조용히.

### 그래서 합성한다

```
새 스냅샷.subPaths = 옛 스냅샷.subPaths[0 .. p)  +  후보 경로.subPaths[전부]
                     └ 교체 시작 단계가 쓰는 원본 구간 앞까지
```

`p` 는 `compileDetailed(옛 스냅샷).subPathIndexOf(fromLegIndex)` 다. 이미 있는 표를 그대로 쓴다 —
단계 번호로 원본 구간 번호를 묻는 것이 이 표의 존재 이유다.

**합성 결과가 만족해야 하는 계약은 하나다.**

> 새 스냅샷을 `JourneyCompiler.compile` 한 단계 목록이, 이 트랜잭션이 저장한 `journey_leg` 와
> **번호·종류가 하나도 어긋나지 않는다.**

이것이 깨지면 지도·④·⑤가 각자 다른 경로를 본다. 그래서 이 계약은 **시험이 지킨다** — 수락 직후
저장된 단계와 새 스냅샷을 다시 쪼갠 결과를 맞대 본다.

### 걷지 않는 환승이 만드는 함정

계산기는 "앞뒤가 같은 정류장인 0초 걷기"를 **단계로 만들지 않는다**(`emitWalk` 의 `skippedWalk`).
즉 원본 구간과 단계는 1:1 이 아니다. 그래서 자르는 위치를 **단계 번호로 세지 말고** 위의 표로
물어야 한다. 손으로 세면 걷기 하나가 빠진 경로에서 한 칸씩 밀린다.

### `PathInfo` 는 다시 계산하지 않는다

`info`(총 소요·환승 수 등)는 geometry 도 단계 쪼개기도 쓰지 않는다. 쓰는 곳은 여정 시작의
목적지 이름 한 줄뿐이고 그 값은 세션이 이미 들고 있다. 합성본의 `info` 는 **후보 경로의 것을
그대로 둔다** — 억지로 합산하면 "앞 구간을 포함한 총 소요"처럼 보이는 틀린 숫자가 생긴다.

## 4. 지금 진행 중인 단계가 어느 쪽이냐 (D4)

PHASE-6 이 "⑤의 PLAN 에서 확정할 항목"으로 남긴 것이다. 세 경우가 있다.

| 지금 단계 | 예 | 판단 |
|---|---|---|
| 교체 시작점 **앞** (`currentLegIndex < fromLegIndex`) | 아직 버스에 타고 있다. 다음 정류장에서 갈아탈 예정 | **기본 경우.** 그대로 적용한다. 하차 지점부터 새 경로다 |
| 교체 시작점과 **같음** (`== fromLegIndex`) | 정류장에 서서 기다리는 중 | **적용한다.** 아직 차를 타지 않았으므로 갈아끼울 수 있다. 새 단계의 상태를 `ACTIVE` 로 잇고 `activatedAt` 을 승계한다 |
| 교체 시작점을 **지났음** (`>` ) | 이미 그 버스를 탔다 | **409.** 사용자가 할 수 있는 일이 없는 제안이다 |

②의 적격성 판정이 이미 "지나간 환승"을 거르지만, **거기서 걸러졌다는 사실이 여기서의 안전을
보장하지 않는다.** 제안이 만들어진 뒤 사용자가 버스를 탈 수 있고, 그 사이가 최대 2분이다.

## 5. 새 개정본을 어떻게 짓는가

```
1. 사용자 행 잠금 → 여정을 다시 읽는다            (동시 요청을 한 줄로)
2. 제안을 ACTIVE → ACCEPTED 로 조건부 update       (여기가 유일한 통과 관문, D8)
3. 넷을 확인한다: 만료 · baseCommandVersion · routeRevision · currentLegIndex  (D7·D4)
4. 후보의 apply 로 새 경로를 만든다
   - REMAINING_PATH: compile(path) → enrich → fromLegIndex 부터 번호 매김
   - ROUTE_OPTION:   구조는 그대로. 대기·주행 단계의 선택 노선만 바꾼다
5. 앞 구간(< fromLegIndex)을 복제한다 — 상태·진행·증거·시각을 전부 보존
6. 새 개정본 행을 만들고 옛 개정본을 SUPERSEDED 로 내린다 (flush 순서 주의)
7. 단계 → 노선 후보 → 환승 순으로 저장 (시작 흐름과 같은 순서)
8. 세션: routeRevision +1, commandVersion +1, 즉시 재평가 예약
9. 이전 개정본의 pending 알림 취소 · 남은 제안 전부 접기
10. journey_event 에 REROUTE_ACCEPTED 를 남긴다
```

**앞 구간을 "복제"한다는 것이 핵심**이다(D3). 새로 만드는 것이 아니라 옛 행의 값을 그대로 옮긴다 —
`state`·`activatedAt`·`completedAt`·진행도·증거까지. 진행 중인 단계의 진행도를 잃으면 앱의 GPS
엔진이 그 단계를 처음부터 다시 시작한다.

`uq_journey_active_revision` 이 여정당 `ACTIVE` 개정본 하나를 강제하므로, **옛 개정본을 먼저 내리고
flush 한 뒤** 새 행을 넣는다(여정 시작의 `replaceOrReject` 가 같은 이유로 `saveAndFlush` 한다).

## 6. 동시성과 재전송 (D8·D9)

세 가지가 동시에 올 수 있다.

- **같은 제안을 두 번 누름(더블 탭)** — 조건부 update 가 한 번만 1행을 바꾼다. 두 번째는 이미
  `ACCEPTED` 이고, `candidateId` 가 같으면 200 + 최신 스냅샷(D9)
- **다른 제안 두 개를 동시에 수락** — 첫 번째가 `routeRevision` 을 올리므로 두 번째는 D7 에서
  409. 제안의 `route_revision` 은 만들어진 개정본을 가리키기 때문이다
- **수락과 단계 전이가 동시에** — 사용자 행 잠금이 둘을 한 줄로 세우고, 진 쪽은
  `baseCommandVersion` 불일치로 409

**낙관적 락을 세 겹으로 두는 이유**는 각각이 다른 사고를 막기 때문이다. 제안 상태는 중복 수락을,
`commandVersion` 은 "그 사이 사용자가 움직였다"를, `routeRevision` 은 "그 사이 경로가 바뀌었다"를
막는다. 하나로 줄이면 나머지 둘이 조용히 통과한다.

## 7. 기각한 대안

| 대안 | 왜 기각했나 |
|---|---|
| 남은 구간만 새 개정본에 넣는다 | 여정 조회가 개정본 하나의 단계 전부를 읽는다. 지나온 길이 화면에서 사라진다(D3) |
| 새 개정본 스냅샷 = 후보 경로 원본 | 단계 번호와 원본 구간 번호가 어긋나 지도가 조용히 틀린다(§3) |
| geometry 원천은 세션 스냅샷으로 두고 개정본만 올린다 | 수락해도 지도와 진행 엔진에 옛 경로가 계속 내려간다. ⑤를 해도 사용자 화면은 그대로다 |
| 수락을 이벤트(`ApplyJourneyEventRequest`)로 받는다 | 상태머신이 경로 재구성까지 알게 된다. 재전송 규칙도 성질이 다르다(§2) |
| `candidateId` 없으면 1번 후보를 적용 | 사용자가 고르지 않은 경로로 여정이 바뀐다. 이 기능 최악의 사고다 |
| 비관적 잠금으로 제안 행을 잠근다 | 상태 칸 하나로 같은 보장을 얻는다. 잠금은 대기를 만들고, 수락은 사용자가 화면에서 기다리는 요청이다 |
| 재전송(같은 후보)을 409 로 | 앱이 되돌릴 방법이 없다. 이미 사용자가 고른 그대로 반영돼 있다(D9) |
| 앞 구간 단계를 새로 만든다(복제하지 않고 재컴파일) | 진행도·증거·시각을 잃는다. GPS 엔진이 진행 중인 단계를 처음부터 다시 센다 |

## 8. 리스크

- **합성 스냅샷이 유일한 외줄이다.** 저장한 단계와 다시 쪼갠 결과가 어긋나면 지도·④가 함께 틀리고
  **오류는 나지 않는다.** 시험으로 못 박는다(§3)
- **geometry 원천 이동은 이미 머지된 화면을 건드린다.** 1번 개정본에서 세션 스냅샷과 개정본
  스냅샷이 같은 값이라는 것으로 회귀를 막는다 — 그래서 선행 PR 로 뗀다(PLAN §PR-1)
- **앞 구간 복제에서 값 하나를 빠뜨리면 조용히 손실된다.** 단계 칸이 스무 개가 넘고, 빠뜨린 칸은
  "다음 평가에서 다시 채워지는" 것이 대부분이라 시험에서도 안 보인다. 복제는 손으로 나열하지 말고
  **칸 목록을 시험이 세게** 한다
- **`ROUTE_OPTION` 수락은 구조가 안 바뀌므로 쉬워 보이지만**, 개정본을 올리는 것은 같다. 두 종류를
  다른 흐름으로 짜면 한쪽만 알림 취소를 빠뜨리는 식으로 갈라진다
- 수락 후 첫 평가까지의 공백 — 즉시 재평가를 예약하지만 실제 평가는 워커가 집어야 돈다. 그 사이
  화면의 ETA 는 새 경로의 계획값(정적)이다
