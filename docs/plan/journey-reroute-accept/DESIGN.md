## 0. 이 칸이 하는 일

②③④가 만든 것은 전부 **제안**이다. 아직 아무 여정도 바뀌지 않았다. ⑤는 사용자가 고른 제안
하나를 받아 **실제로 안내 경로를 갈아끼운다.** 사다리에서 처음으로 여정이 바뀌는 칸이다.

바뀌는 것이 다섯이다 — 개정본(`journey_revision`), 단계(`journey_leg`), 노선 후보
(`journey_leg_route_option`), 환승(`transfer_connection`), 그리고 **지도에 그려지는 geometry**.
다섯이 어긋나면 화면이 조용히 틀린다. 그래서 한 트랜잭션이다.

## 1. 확정 결정

| # | 결정 | 한 줄 근거 |
|---|---|---|
| D1 | **전용 엔드포인트**(`POST …/reroute-proposals/{proposalId}/accept`). 이벤트 경로로 받지 않는다 | 수락은 앱이 관측한 사실이 아니라 사용자의 의사결정이다 |
| D2 | 요청은 `proposalId` **와 `candidateId`** 를 함께 받는다. 없으면 400 | 사용자가 고르지 않은 경로로 여정이 바뀌는 것이 이 기능 최악의 사고다 |
| D3 | 새 개정본은 **전체 단계를 복제**한다. 남은 구간만 넣지 않는다 | 여정 조회가 `(journeyId, routeRevision)` 로 단계 전부를 읽는다. 남은 구간만 넣으면 화면에서 **지나온 길이 사라진다** |
| D4 | 교체 시작점은 후보의 `fromLegIndex`. **`fromLegIndex < currentLegIndex` 면 409** | 이미 지나간 지점부터 갈아끼우면 진행 중인 단계가 사라진다 |
| D5 | **스냅샷을 먼저 합성하고, 새 단계는 그 합성본을 다시 쪼개서 얻는다.** 후보를 따로 쪼개 번호만 미는 방식은 기각 | 쪼개기 규칙이 **앞뒤 구간을 함께 본다**(§3). 따로 쪼개면 경계에서 종류·개수가 달라져 스냅샷과 단계가 어긋난다 |
| D5-b | 합성본을 쪼갠 결과의 **앞 구간이 저장된 단계와 다르면 수락을 거절**한다 | 경계에서 도보 종류가 바뀌는 경우가 실제로 있다(§3). 조용히 진행하면 지나온 길의 종류가 바뀐 채 저장된다 |
| D6 | geometry 원천을 `JourneySession.routeSnapshot` → **그 개정본의 `JourneyRevision.routeSnapshot`** 으로 옮긴다. **폴백은 1번 개정본에만** | 세션 스냅샷은 시작 시점 원본이고 영원히 안 바뀐다. 2번 개정본에서 폴백하면 **반드시 옛 경로를 그린다** — 그때는 조용히 틀리느니 실패해야 한다 |
| D7 | 수락 트랜잭션은 **여정 세션 행을 잠근다**(`findByIdAndUserIdForUpdate`). 사용자 행이 아니다 | 단계 전이(`JourneyCommandService`)가 잠그는 것이 세션 행이다. 다른 것을 잠그면 두 흐름이 직렬화되지 않는다 |
| D8 | 잠금 순서는 **세션 → 제안**. 제안 조건부 update 는 세션을 잠근 뒤에 한다 | 반대로 하면 기존 흐름과 순서가 뒤집혀 교착이 난다 |
| D9 | 재확인 넷(제안 `ACTIVE`·만료·`baseCommandVersion`·`routeRevision`)이 어긋나면 **예외로 롤백**한다. 정상 return 으로 409 를 내지 않는다 | 조건부 update 를 통과한 뒤 그냥 409 를 돌려주면 **제안만 소모되고 여정은 그대로**인 상태가 커밋된다 |
| D10 | 수락한 **후보 ID 를 제안 행에 저장**한다(`accepted_candidate_id`, **V43**) | 저장하지 않으면 재전송이 왔을 때 "같은 후보라 200"과 "다른 후보라 409"를 가를 근거가 없다 |
| D11 | 같은 `(proposalId, candidateId)` 재전송은 **200 + 최신 스냅샷**. 다른 후보면 409 | 이미 자기가 고른 그대로 반영된 것을 오류로 돌려주면 앱이 되돌릴 방법이 없다 |
| D12 | `journey_event.event_id` 는 **서버가 결정론으로 만든다** — `reroute-accept:{proposalId}:{candidateId}` | 수락 요청에는 앱이 만든 `eventId` 가 없다. 결정론이면 unique 인덱스가 곧 멱등 장치가 된다 |
| D13 | **교체 지점 이후의 평가·알림 흔적은 초기화**한다(단계의 예측·증거·진행도, 환승의 판정·알림 표시). 그 앞은 그대로 복제 | 노선이 바뀌었는데 옛 예측이 남으면 화면이 옛 ETA 를 보여 주고, 알림 표시가 남으면 **새 위험을 알리지 못한다** |
| D14 | 이전 개정본 pending 알림은 **`route-changed` 사유로** 취소한다. 기존 `journey-ended` 고정 메서드를 쓰지 않는다 | 사유가 곧 운영 신호다. 끝나지도 않은 여정을 "끝났다"로 세면 그 지표가 죽는다 |
| D15 | **progress 경로에 개정본 가드를 넣는다.** 단계 갱신·평가 번호 증가·지하철 보호를 개정본 조건부로 | progress 는 여정 행을 잠그지 않는다. 수락이 개정본을 올린 직후 들어온 progress 가 **옛 단계**를 갱신하고 새 세션에 보호 시각을 씌운다 |
| D16 | `journey_revision.reason` = **`ROUTE_OPTION_ACCEPTED` · `REMAINING_PATH_ACCEPTED`** | 엔티티 주석이 "Phase 6 이 정한다"고 비워 뒀다 |
| D17 | 상태머신의 `REROUTE_ACCEPTED` 는 **계속 거절**. 이력은 수락 트랜잭션이 직접 남긴다 | 이벤트 통로를 여는 것은 D1 을 무르는 일이다 |

## 2. 왜 전용 엔드포인트인가 (D1)

`ApplyJourneyEventRequest` 는 **앱이 관측한 사실**을 보내는 통로다 — "3번 단계에서 4번 단계로
넘어갔다", "여정을 취소했다". 그 값들은 GPS 엔진이 만들고, 재전송 규칙(`eventId` 멱등)이 그 성질에
맞춰져 있다.

수락은 성질이 다르다. **사용자가 화면에서 고른 것**이고, 고른 대상(`candidateId`)이 있으며, 서버가
그 순간 되짚어야 할 조건이 넷이다. 이것을 이벤트 payload 에 욱여넣으면 상태머신이 "후보 하나를
골라 경로를 다시 만드는 일"까지 알게 된다. 상태머신은 **단계 경계를 옮기는 기계**로 둔다.

그래서 통로는 따로 두되 **이력은 같은 곳에 남긴다**(D17). 다만 앱이 `eventId` 를 주지 않으므로
서버가 결정론으로 만든다(D12) — `journey_event.event_id` 는 필수이고 unique 라, 결정론적 값이면
재전송이 두 번째 삽입에서 걸린다. 그것이 곧 두 번째 안전장치다.

## 3. 합성 스냅샷 — ⑤에서 가장 조용히 틀릴 곳 (D5)

### 무엇이 문제인가

`journey_revision.routeSnapshot` 은 경로 원본(`PathResult`) 하나다. 이 값을 쓰는 곳이 둘인데
**둘 다 "다시 쪼개면 저장된 단계가 그대로 나온다"를 가정한다.**

- `JourneyNavigationGeometryService` — 스냅샷을 `compileDetailed` 로 쪼개 **단계 번호 → 원본 구간
  번호** 표를 만들고, 그 구간의 좌표로 지도를 그린다
- `JourneyWaypointResolver`(④) — 같은 방법으로 환승 정류장의 좌표를 찾는다

### 후보를 따로 쪼개서 번호만 미는 방식은 성립하지 않는다

`JourneyCompiler` 의 쪼개기는 **구간 하나만 보고 결정하지 않는다.**

- 도보 구간의 종류는 **앞뒤에 교통수단이 있는지**로 갈린다 — 양쪽에 있으면 `TRANSFER_WALK`,
  아니면 `WALK`
- 앞뒤가 같은 정류장이고 길이가 0이면 **단계를 아예 만들지 않는다**(`skippedWalk`)
- 환승 연결(`transfer`)은 **인접한 두 교통수단 구간**을 보고 만들어진다

즉 후보 경로를 홀로 쪼갠 결과와, 앞 구간에 이어 붙여 쪼갠 결과가 **다를 수 있다.** 후보의 첫
도보는 홀로 보면 `WALK` 지만 이어 붙이면 `TRANSFER_WALK` 가 되고, 앞 구간의 끝과 같은 정류장이면
**단계가 사라져 뒤 번호가 통째로 한 칸씩 밀린다.** 접합부에 생겨야 할 환승도 후보 안에서는 보이지
않는다.

### 그래서 순서를 뒤집는다

```
1. 스냅샷을 먼저 합성한다
   새 스냅샷.subPaths = 옛 스냅샷.subPaths[0 .. p) + 후보 경로.subPaths[전부]
   p = compileDetailed(옛 스냅샷).subPathIndexOf(fromLegIndex)

2. 새 단계·환승은 그 합성본을 compile 해서 얻는다   ← 따로 쪼개지 않는다
3. 앞 구간(legIndex < fromLegIndex)이 저장된 단계와 같은지 확인한다 (D5-b)
4. 앞 구간은 저장된 엔티티를 복제하고, fromLegIndex 부터를 새 단계로 저장한다
```

이렇게 하면 **정의상** "새 스냅샷을 쪼갠 결과 = 저장된 단계"가 된다. 접합부 환승도 자동으로 생긴다.

### 앞 구간이 달라질 수 있다는 것을 인정한다 (D5-b)

합성으로 뒤가 바뀌면 **앞 구간의 마지막 도보 종류도 바뀔 수 있다.** 예: 후보가 걷기만으로 목적지에
닿는 경로면 그 앞 도보의 "뒤에 교통수단이 있다"가 거짓이 되어 `TRANSFER_WALK` → `WALK` 가 된다.
드물지만 실제로 생기고, 그대로 두면 **지나온 길의 종류가 바뀐 채 저장된다.**

판단: 그런 후보는 **수락을 거절한다**(409, `snapshot-mismatch`). 앞 구간을 다시 쓰는 것은 D3
("지나온 길은 그대로 보존")과 정면으로 충돌하고, 그 대가로 얻는 것은 드문 경로 하나뿐이다. 거절
빈도를 지표로 세어 실제로 잦으면 그때 다시 판단한다.

### `PathInfo` 는 다시 계산하지 않는다

`info`(총 소요·환승 수)는 geometry 도 단계 쪼개기도 쓰지 않는다. 합성본의 `info` 는 후보 경로의
것을 그대로 둔다 — 억지로 합산하면 "앞 구간을 포함한 총 소요"처럼 보이는 틀린 숫자가 생긴다.

## 4. 지금 진행 중인 단계가 어느 쪽이냐 (D4)

| 지금 단계 | 예 | 판단 |
|---|---|---|
| 교체 시작점 **앞** | 아직 버스에 타고 있다 | **기본 경우.** 그대로 적용. 하차 지점부터 새 경로다 |
| 교체 시작점과 **같음** | 정류장에서 기다리는 중 | **적용한다.** 아직 차를 타지 않았다. §4-b 의 승계 규칙을 따른다 |
| 교체 시작점을 **지났음** | 이미 그 버스를 탔다 | **409.** 사용자가 할 수 있는 일이 없는 제안이다 |

### 4-b `currentLegIndex == fromLegIndex` 의 승계 규칙

새 첫 단계에 무엇을 잇고 무엇을 버릴지 **칸 단위로 정한다.** 애매하게 두면 옛 경로의 진행도가
새 geometry 위에서 해석돼 "이미 절반 왔다"가 된다.

| 값 | 규칙 | 이유 |
|---|---|---|
| `state` | 옛 단계가 `ACTIVE` 면 잇는다 | 사용자는 계속 그 자리에 서 있다 |
| `activatedAt` | **단계 종류가 같을 때만** 잇는다. 다르면 지금 시각 | 옛 `WAIT` 의 시작 시각을 새 `WALK` 의 출발 시각으로 쓰면 보행 ETA 가 과거에서 시작한다 |
| `progress*`·`lastProgressId`·`remaining*` | **전부 버린다** | 진행도는 geometry 위의 좌표다. 경로가 바뀌면 그 좌표가 가리키는 지점이 달라진다 |
| `predictedEndAt`·`evidence*` | **전부 버린다** | 옛 노선의 예측이다. 다음 평가가 즉시 다시 채운다(D13) |

버리는 대가는 "다음 progress 가 올 때까지 그 단계의 진행도가 없다"이고, 그 값은 15초 안에 다시
온다. 잘못 이어 붙인 진행도는 **틀린 채로 계속 남는다.**

## 5. 잠금과 순서 (D7·D8·D9)

### 잠그는 것은 여정 세션 행이다

`JourneyCommandService.apply` 는 `findByIdAndUserIdForUpdate` 로 **세션 행**을 잠근다. 수락이
사용자 행을 잠그면 두 흐름은 서로를 기다리지 않고, 아직 커밋되지 않은 단계 전이를 못 본 채
`baseCommandVersion` 검사를 통과한다. 그래서 **같은 행을 같은 순서로** 잠근다.

```
세션 행 잠금  →  제안 조건부 update  →  넷 재확인  →  개정본 재구성
```

제안을 먼저 잡고 세션을 잠그면 기존 흐름(세션 → 제안)과 순서가 뒤집혀 교착이 난다.

### 거절은 예외로 한다 (D9)

조건부 update 는 이미 제안을 `ACCEPTED` 로 바꾼 뒤다. 그 상태에서 "409 를 return" 하면 그 변경이
**커밋된다** — 제안은 소모됐는데 여정은 그대로인, 사용자가 다시 누를 수도 없는 상태가 남는다.
그래서 재확인 실패는 `BusinessException` 으로 던져 트랜잭션을 통째로 되돌린다. 제안은 다시
`ACTIVE` 로 남고, 만료 전이면 사용자가 다시 누를 수 있다.

### 조건부 update 를 통과하지 못한 쪽 (D10·D11)

동시 수락에서 진 요청은 "이미 `ACCEPTED`" 를 본다. 그때 **무엇으로 수락됐는지**를 알아야 같은
후보의 재전송(200)과 다른 후보(409)를 가른다. 지금 표에는 그 칸이 없으므로 **`accepted_candidate_id`
를 더한다**(V43). 마이그레이션 한 건이 이 구분의 값이다.

## 6. 갈아끼운 뒤의 뒷정리 (D13·D14·D15)

- **단계·환승의 판정값**: 교체 지점 **이후**는 초기화, 그 앞은 복제. `ROUTE_OPTION` 수락도
  마찬가지다 — 구조는 그대로여도 **노선이 바뀌었으므로** 그 환승의 예측·알림 표시는 죽은 값이다.
  남겨 두면 옛 ETA 가 화면에 남고, `lastNotifiedStatus` 때문에 **새 위험을 알리지 못한다**
- **알림 취소 사유**: `route-changed`. 기존 `cancelPendingByJourneyId` 는 사유를
  `journey-ended` 로 고정하므로 그대로 쓰면 지표가 "끝난 여정"으로 오염된다
- **남은 제안**: 새 개정본 기준으로 `resolveStale` 을 태워 `route-changed` 로 접는다
- **평가**: 즉시 재평가를 예약한다. 소유권 CAS 가 진행 중이던 낡은 평가를 버린다
- **progress 경합**(D15): progress 는 여정 행을 잠그지 않고 개정본을 한 번만 확인한다. 수락이
  그 사이 개정본을 올리면 옛 단계를 갱신하고, 새 세션에 지하철 보호 시각을 씌울 수 있다. progress
  쪽에 개정본 조건을 넣어 **옛 개정본의 갱신이 새 상태를 건드리지 못하게** 한다

## 7. 기각한 대안

| 대안 | 왜 기각했나 |
|---|---|
| 후보를 따로 쪼개 번호만 민다 | 쪼개기가 앞뒤를 함께 본다. 경계에서 종류·개수가 달라진다(§3) |
| 남은 구간만 새 개정본에 넣는다 | 여정 조회가 개정본 단위다. 지나온 길이 화면에서 사라진다 |
| 새 개정본 스냅샷 = 후보 경로 원본 | 단계 번호와 원본 구간 번호가 어긋나 지도가 조용히 틀린다 |
| geometry 원천은 세션 스냅샷으로 두고 개정본만 올린다 | 수락해도 지도에 옛 경로가 계속 내려간다 |
| 개정본이 없으면 언제나 세션 스냅샷으로 폴백 | 2번 개정본부터는 **반드시 옛 경로를 그린다.** 폴백은 1번에만(D6) |
| 수락을 이벤트 통로로 받는다 | 상태머신이 경로 재구성까지 알게 된다 |
| `candidateId` 없으면 1번 후보 적용 | 사용자가 고르지 않은 경로로 여정이 바뀐다 |
| 사용자 행을 잠근다 | 단계 전이는 세션 행을 잠근다. 다른 행을 잠그면 직렬화되지 않는다(D7) |
| 재확인 실패를 정상 409 로 돌려준다 | 제안만 소모되고 여정은 그대로인 상태가 커밋된다(D9) |
| `accepted_candidate_id` 없이 재전송을 구분한다 | 무엇으로 수락됐는지 알 방법이 없다. 마이그레이션 한 건이 더 싸다 |
| 앞 구간을 재컴파일로 다시 만든다 | 진행도·증거·시각을 잃는다 |
| 경계에서 앞 구간이 달라지면 그것까지 갈아끼운다 | "지나온 길은 보존한다"와 정면으로 충돌한다. 거절이 낫다(D5-b) |

## 8. 리스크

- **합성이 여전히 외줄이다.** 순서를 뒤집어(먼저 합성 → 다시 쪼개기) 계약을 정의상 참으로 만들었지만,
  그 계약을 지키는 코드가 한 곳이라 거기서 틀리면 지도·④가 함께 틀린다. **앞 구간 일치 검사(D5-b)가
  마지막 그물**이다
- **복제에서 칸 하나를 빠뜨리면 조용히 손실된다.** `JourneyLeg` 는 빌더가 진행도·예측·완료 시각을
  받지 않으므로 **복제 전용 API 를 엔티티에 만들어야 한다.** 만들지 않고 빌더로 옮기면 그 칸들이
  전부 null 이 되는데, 대부분 다음 평가가 다시 채워 시험에서도 안 보인다
- **`ROUTE_OPTION` 수락은 쉬워 보이지만 뒷정리는 더 위험하다.** 구조가 그대로라 옛 판정값이 전부
  그 자리에 남고, 그중 `lastNotifiedStatus` 는 새 위험 알림을 막는다
- **progress 경합은 확률이 낮고 증상이 이상하다.** 수락 직후 몇 초 안에 들어온 progress 하나가
  지하철 보호 시각을 잘못 세우면, 그 뒤 평가가 몇 분간 조용해진다
- 수락 후 첫 평가까지의 공백 — 즉시 재평가를 예약하지만 워커가 집어야 돈다

## 9. 후속 과제

- **⑥ 제안 알림** — 이 PR 이 끝나면 사다리에서 남는 것은 알림뿐이다
- **수락 되돌리기(undo)** — 개정본이 `SUPERSEDED` 로 남아 데이터는 있지만, 되돌림의 의미
  (진행도·알림)를 따로 정해야 한다
- **경계에서 앞 구간이 달라지는 후보를 살리는 길** — 지금은 거절한다. `snapshot-mismatch` 지표가
  잦으면 그때 다시 판단한다
- **여정 시작과 수락의 개정본 생성 코드 통합** — 세 번째 소비자가 생기면 뽑는다
