# 같은 정류장 다른 버스 후보 (Phase 6 ③)

## 뭘 하나

환승 버스를 못 탈 것 같을 때 사용자가 앱에서 "다른 길 찾기"를 누르면, **같은 정류장에 서는 다른 버스**
중 목적지에 5분 이상 빨리 닿는 것을 최대 3개 찾아 저장한다. 정류장이 그대로라 ODsay 경로 검색을
한 번도 부르지 않는다. 지금은 이 API 가 무조건 409 로 거절되는데, 그 거절도 이 PR 에서 푼다.

## 왜

②가 제안 저장소와 API 를 만들었지만 **저장할 후보를 만드는 코드가 없어** 항상 빈손이다. ③이 그
자리를 채워야 Phase 6 이 처음으로 실제 결과를 낸다.

## 핵심 결정

- **제안은 사용자가 누를 때만 만든다.** 위험 감지 코드(①)는 계속 숫자만 센다 — 자동 생성해도 알릴
  통로(⑥)가 없어 아무도 못 본다
- **비교 기준은 목적지 도착 시각.** 단, 이후 환승의 대기 시간은 검색 결과에 없어 0으로 둔다. 모든
  후보에 똑같이 빠져 개선폭은 정확하고, 절대 도착 시각만 낙관적이라 그때는 신뢰도를 낮춰 표시한다
- **기존 경로도 같은 순간에 다시 잰다.** 저장된 30초 전 값과 방금 값을 빼면 개선폭이 가짜가 된다
- **탈 수 있다고 확인된 예측만 후보로 올린다.** 예측 API 는 탈 차가 없으면 이미 지나간 차를 돌려주기도 한다
- **재요청 잠금을 용도별로 가른다.** 지금은 감지 코드와 사용자 요청이 같은 잠금을 써서, 아무 일도 안
  하는 감지가 사용자 요청을 2분간 막는다
- **버스 목록은 DB 에서 바로 읽는다.** Redis 사본 대신 설계 문서(TECHNICAL_DECISIONS §4·SC-10)의 캐시
  문장을 고쳐 코드와 맞춘다

## codex 리뷰로 바뀐 것

초안의 네 군데가 머지된 코드와 어긋났다. 전부 코드로 확인하고 고쳤다.

1. **이후 구간 소요가 없으면 포기**하려 했는데, 대기 단계 소요는 **언제나 비어 있다**(검색 결과에 없다).
   그대로 갔으면 환승이 둘 이상인 여정에서 제안이 영원히 0건
2. **적격성 검사가 지나간 환승도 통과**시켰다. 요청 본문이 비면 첫 환승으로 채워지므로 옛 앱 버전이
   이미 지난 환승 제안을 만들 수 있었다 → 진행 단계로 거른다
3. **후보를 만드는 사이 여정이 바뀌어도 그대로 저장**했다 → 저장 직전에 여정 상태·버전을 다시 본다
4. **탈 수 없는 예측을 유효한 후보로** 봤다 → `boardable` 확인 추가

## 리스크

- 후보마다 실시간·ML 조회가 나간다. 평가 상한 3개 + 요청 전체 3초 예산 + 재요청 잠금으로 막지만,
  발생률을 아직 못 잰 상태다(①이 VPS 에 배포 안 됨) — 그래서 기능 스위치는 계속 꺼 둔다
- 지금 경로로 아예 못 타는 상황에서는 ③이 빈손을 낸다(개선폭을 잴 기준이 없다). 그 경우는 사다리
  다음 칸인 ④가 받는다. 빈도는 지표로 관측
- ②가 만든 인터페이스 둘(적격성 판정, 저장)의 시그니처를 바꾼다. 소비자가 아직 하나뿐이라 지금이 제일 싸다

## 검증법

`POST .../reroute-proposals` 가 제안 1건을 저장하고 그 과정에서 **ODsay 호출 0회**. 환승이 둘 이상인
여정에서도 제안이 나온다. 지나간 환승 요청·저장 직전 여정 변경·탈 수 없는 예측은 전부 거절 또는 빈
결과. 감지 코드가 방금 잠금을 태워도 사용자 요청은 통과. `./gradlew build` 전체 통과.
