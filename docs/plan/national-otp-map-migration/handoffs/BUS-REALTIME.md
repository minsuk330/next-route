# 모바일 인계 — 버스 실시간 도착: 경기·지방까지 열렸다

**한 줄**: 버스 구간의 `startLocalStationID` + `lanes[].busLocalBlID` 가 **서울뿐 아니라 경기·지방 38개 지역에서도 채워진다**.
앱은 지금처럼 **두 값을 가공하지 말고 그대로** `GET /api/arrivals/bus/{stopId}/{routeId}` 에 넣으면 된다.
어느 기관에 물어볼지는 서버가 id 모양을 보고 정한다. **엔드포인트·응답 형식은 그대로**다.

⚠️ 유일한 주의점: 지방 버스 id 는 **영문 3글자로 시작하는 문자열**이다(`BSB167850202`). 숫자로 파싱하거나 숫자만 허용하는 검증이 있으면 지방 구간에서 호출이 막힌다.

---

## 1. 무엇이 바뀌었나

OTP 길찾기 응답의 버스 구간(`subPath.trafficType == 2`)에서, 전에는 서울 노선만 채워지던 칸이 이제 지역별로 이렇게 채워진다.

| 지역 | `startLocalStationID` / `endLocalStationID` | `lanes[].busLocalBlID` | 서버가 묻는 곳 |
|---|---|---|---|
| 서울 노선 | 숫자 9자리 (`123000001`) | 숫자 9자리 (`100100209`) | 서울시 버스 API (변경 없음) |
| **경기 노선** (서울 안을 지나도 포함) | 숫자 9자리 (`123000001`) | 숫자 9자리 (`228000184`) | **경기도 버스 API** (신규) |
| **지방 38개 지역** | **영문3 + 숫자** (`BSB167850202`) | **영문3 + 숫자/하이픈** (`BSB5200186000`, `GMB171-110`) | **국토교통부 TAGO** (신규) |
| 농어촌 버스·미지원 지역 | `null` | `null` | 호출하지 않는다 |

- 경기 노선은 **서울 정류장에서 타도** 경기 id 로 나온다. 예: 잠실역에서 타는 5600번 → `123000001` / `228000184`.
  (같은 정류장의 서울 노선 2412번은 `123000001` / `100100209` — 정류장 id 는 같고 노선 id 로 갈린다.)
- `null` 이면 지금처럼 실시간 호출을 하지 않으면 된다.

### 지방 38개 지역

부산 · 대구 · 인천 · 광주 · 대전/계룡 · 울산 · 세종 ·
안동 · 아산 · 천안 · 충주 · 청주 · 창원 · 김천 · 김해 · 구미 · 공주 · 계룡 · 곡성 · 군산 · 경산 · 함평 ·
제천 · 진주 · 전주 · 경주 · 광양 · 나주 · 남원 · 포항 · 사천 · 순천 · 서산 · 원주/횡성 · 영천 · 영덕 · 여수 · 양산

아직 null 인 곳: 농어촌 버스(시·군 통합), 보은 · 칠곡 · 거제 · 목포 · 밀양 · 옥천 등 일부 — 서버가 지역 코드를 확인하는 대로 추가한다(앱 수정 불필요).

## 2. 호출 (변경 없음)

```
GET /api/arrivals/bus/{startLocalStationID}/{lanes[i].busLocalBlID}
```

```
GET /api/arrivals/bus/123000001/100100209        ← 서울 2412 (잠실)
GET /api/arrivals/bus/123000001/228000184        ← 경기 5600 (잠실)
GET /api/arrivals/bus/BSB167850202/BSB5200186000 ← 부산 186 (영도대교)
GET /api/arrivals/bus/GMB119/GMB171-110          ← 구미 171-1 (하이픈 그대로)
```

- **URL 경로에 그대로** 넣는다. 영문·숫자·하이픈뿐이라 인코딩해도 값이 바뀌지 않는다.
- 노선이 여러 개(`lanes` 가 여러 개)면 lane 마다 따로 부른다 — 기존과 같다.

## 3. 응답 (형식 동일, 값의 뜻도 서울과 맞췄다)

```jsonc
[
  {
    "routeId": "228000184",
    "arrivalMsg1": "4분후[2번째 전]",   // 표시용 문구
    "predictTime1": 240,              // 초
    "congestionNum1": 4,              // 혼잡도 코드
    "arrivalMsg2": "29분후[19번째 전]",
    "predictTime2": 1740,
    "congestionNum2": 6
  }
]
```

| 필드 | 서울 | 경기 | 지방(TAGO) |
|---|---|---|---|
| `predictTime1/2` | 초 | 초 (서버가 분→초 변환) | 초 |
| `arrivalMsg1/2` | 서울 원문 (`2분26초후[0번째 전]`, `곧 도착`, `운행종료`, `출발대기`) | 서버 생성: `곧 도착` / `N분후[M번째 전]` / `운행종료` / `출발대기` / `도착 정보 없음` | 서버 생성: `곧 도착` / `N분후[M번째 전]` / `도착 정보 없음` |
| `congestionNum1/2` | 0 정보없음 · 3 여유 · 4 보통 · 5 혼잡 · 6 매우혼잡 | 같은 코드로 변환 | **항상 0** (원천에 혼잡도 없음) |

- 문구 형식이 서울은 `분초`, 경기·지방은 `분`까지라 미세하게 다르다. **시간 계산은 `predictTime`(초)으로** 하는 것을 권한다.
- 두 번째 버스가 없으면: `arrivalMsg2` = `도착 정보 없음` 또는 `운행종료`/`출발대기`, `predictTime2` = `null`.

### 빈 배열 `[]` 이 오는 경우 (오류 아님 — "지금 보여줄 도착 정보 없음")

- 다가오는 버스가 없다 (특히 지방은 버스가 없으면 0건으로 온다)
- 그 정류장에 그 노선이 서지 않는다
- 서버가 외부 API 를 잠시 못 불렀다(한도·일시 오류) — 15초쯤 뒤 다시 부르면 된다
- 지원하지 않는 지역 id

화면에서는 "도착 정보 없음" 처리 + 기존 폴링 주기 유지면 충분하다. **HTTP 상태는 언제나 200** 이다.

## 4. 폴링

- 서버는 같은 (정류장, 노선)을 **15초 동안 캐시**한다. 15초보다 자주 불러도 값은 같다 → **15~30초 주기**를 권한다.
- 외부 API 일일 한도가 있다(경기 10,000회/일). 화면에 안 보이는 구간은 폴링을 멈춰 주면 좋다.

## 5. 검색 응답의 `transferArrivals` 는 그대로다

검색 응답 안의 `transferArrivals[]`(서버가 미리 붙이는 환승 대기 예측)는 **서울 노선만** 다룬다. 경기·지방 구간은 거기서
`routeId: null`, `status: STOP_MAPPING_FAILED` 또는 `UNSUPPORTED_ROUTE` 로 남는다.
→ 경기·지방은 **`lanes[].busLocalBlID` 로 위 도착 API 를 부르는 경로**를 쓰면 된다(앱이 이미 `transferArrivals[].routeId` → `lanes[].busLocalBlID` 순으로 폴백하고 있다면 추가 작업 없음).

## 6. 확인용 체크리스트

- [ ] 잠실역 → 테크노마트 검색 → 5600 구간 `startLocalStationID=123000001`, `busLocalBlID=228000184` 로 도착 정보가 뜬다
- [ ] 부산 구간(예: 영도대교 186) → `BSB…` id 로 호출되고 도착 정보가 뜬다
- [ ] 구미 `GMB171-110` 처럼 **하이픈 들어간 노선 id** 가 그대로 전달된다
- [ ] id 가 `null` 인 구간은 호출하지 않는다
- [ ] `[]` 응답에서 앱이 깨지지 않고 "도착 정보 없음" 으로 보인다
- [ ] 지방 구간 혼잡도 표시가 0(정보 없음)일 때 자연스럽다
