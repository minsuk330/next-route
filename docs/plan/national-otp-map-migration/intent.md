# 수도권 OSM·OTP 전환 의도

작성일: 2026-09-07.
이 문서는 사용자가 이번 작업에서 이루려는 목적과 범위를 기록한다.
기존 [PLAN.md](PLAN.md) 및 Phase 문서와 충돌하면 아래 최신 의도를 기준으로 구현 계획을 조정한다.
의도 기록과 문서 검토를 완료한 상태이며, 변환 코드 구현이나 운영 전환 완료를 뜻하지 않는다.

## 0. 현재 확정 범위

운영 전환 범위는 **수도권으로 제한**한다. 전국 graph build·부하 측정은 용량과 대안 엔진을 확인하기 위한 실험 결과일 뿐, 이번 서비스 범위나 배포 목표가 아니다.

- OSM 도로 범위: 기존 수도권 bbox `west=126.5, south=37.2, east=127.4, north=38.0`
- 대중교통 범위: 수도권에서 검증된 서울·인천·경기 버스와 수도권 도시철도
- 여기서 수도권은 위 bbox 기준이며 서울·경기·인천 행정구역 전체를 뜻하지 않는다.
- bbox 밖은 운영 대상에서 제외한다. 경계 밖 정류장을 삭제해 가짜 단축 trip을 만들지 않는다.
- 다른 도시 철도와 범위 밖 trip은 운영 graph에서 제외하고 OUT_OF_SCOPE 사유를 기록한다.
- 전국 graph 관련 측정값은 `capacity-report.md`의 역사적 참고 자료로만 남긴다.

## 1. 교체 이유와 도달할 상태

ODsay API 호출 제한이 빡빡해졌기 때문에 OSM 데이터와 OTP 기반으로 길찾기를 전면 교체한다.
OTP 도입 여부를 다시 판단하는 실험이 아니라, 이미 선택한 엔진으로 서비스의 검색·재탐색을 변환하는 작업이다.
전환 후 정상 길찾기가 ODsay 호출 가능량에 의존하지 않아야 한다.

ODsay는 필요하면 전환 결과를 몇 건 비교하는 용도로 사용할 수 있다.
장기간 이중 호출이나 상시 shadow 시스템 구축은 이번 작업의 필수 조건이 아니다.
배포 시 일시적 복구 수단을 두는 것과 ODsay를 상시 운영 의존으로 남기는 것은 구분한다.

## 2. 수도권 길찾기와 기존 제한 해제

교체하면서 길찾기 범위는 수도권으로 확정한다.
기존 API 호출량을 줄이기 위해 수도권 안에서 제한했던 기능·검색 범위·호출 정책은 모두 찾아 해제하는 것이 목표다.
기존 정책이라는 이유만으로 새 OTP 구조에 그대로 복사하지 않는다.

구현 시 제한마다 도입 이유와 영향을 조사해 제거 대상을 명시한다.

- 지역/prefix 필터 등 검색 범위를 축소한 제한.
- ODsay 호출 절약을 위한 재탐색 억제, 대안 평가 축소, 기능 비활성화.
- 후보 수·재검색 횟수·cooldown 중 외부 호출 비용만을 이유로 둔 제한.
- 자동 재탐색/제안 보류가 호출량 때문이었다면 해당 기능 복원도 전환 범위에 반영한다.

구체적인 설정값과 복원 대상은 사용처 확인 후 확정한다. 모든 cooldown이나 상한의 목적이 동일하다고 가정하지 않는다.
캐시·SingleFlight는 기능을 제한하지 않고 중복 연산을 줄일 수 있으므로 삭제가 목표는 아니다.
OTP 자원 보호, 잘못된 경로 차단, 중복 알림 방지 등 다른 목적의 제약은 별도 판단한다.
서울 실시간 API·TMAP 등 남는 외부 API의 쿼터가 OTP 도입으로 사라지는 것은 아니므로 공급자별로 구분한다.

수도권 검색 확대가 수도권 전 구간의 실시간 데이터나 미구현 철도 네비를 자동으로 제공한다는 뜻은 아니다.
실제 원천/엔진 지원 범위를 응답에 정확하게 표현하면서 인위적인 호출량 절감용 검색 제한을 없앤다.

## 3. GTFS 입력

이번 변환의 기준 입력은 **202503_GTFS_DataSet**이다.
2024 데이터나 기존 제한된 benchmark ZIP을 수도권 전환의 기준으로 사용하지 않는다.

로컬에서 확인한 디렉터리:

```text
/Users/wa/Downloads/대중교통GTFS(2025년 기준)/202503_GTFS_DataSet
```

파일 시스템에서는 한글 경로의 Unicode 정규화가 다를 수 있으므로 실제 경로를 확인해서 사용한다.
이번 확인은 디렉터리 존재 확인이며, 내부 파일 전체의 내용 검증을 완료했다는 뜻은 아니다.

정규화·graph 생성은 이 입력을 기준으로 수행하고 원천 식별자·시각표·파일 정보를 보존한다.
과거 benchmark의 calendar/shapes 분석 결과를 이 데이터에도 동일하다고 가정하지 않는다.
새 입력의 구조 확인과 변환 무결성 확인은 실제 변환 과정에 포함한다.

## 4. 검증 범위

사용자는 기존 테스트를 이미 수행했으며 이번에는 변환 작업을 진행하기를 원한다.
기존 실험 결과를 활용하고 엔진 선택·대규모 품질 비교·용량 실험을 처음부터 반복하지 않는다.

필요한 확인은 변경한 코드와 새 입력의 연결이 정상인지에 집중한다.

- GTFS 정규화 무결성, graph load 및 실제 검색 smoke.
- 검색·재탐색 DTO 변환, ID/시간/geometry 연결.
- 기존 여정 유지와 전환된 검색의 기본 흐름.
- 필요하면 ODsay와 몇 건 비교. 권장 3~5개 공통 지원 OD를 한 번씩 확인하고 노선/환승/시간 차이를 기록한다.

ODsay가 지원하지 않는 수도권 경로는 ODsay와의 일치율로 판단하지 않는다.
비교를 위해 상시 shadow dispatcher나 새 운영 표본 수집 시스템을 먼저 만들 필요는 없다.
기존 테스트 수행 사실은 사용자 전제로 기록하며, 새 코드·새 데이터가 이미 검증됐다고 표시하지 않는다.

## 5. 지도 표시 정책 — Naver 우선, 호환성 부족 시 전환

확정된 것은 ODsay 길찾기를 OSM 데이터 + OTP로 전면 교체하는 것이다.
OSM은 데이터이며 지도 SDK 선택을 자동으로 정하지 않는다.
버스·도시철도 형상은 검증한 OSM route relation을 사용한다. 정류장 직선/도보 대체 형상을 만들지 않고 결측은 품질/지원 범위로 표시한다.

Naver는 시인성이 좋고 한국에 특화된 지도이므로 기존 SDK/타일을 우선 유지한다.
OTP가 반환한 경로 geometry를 Naver 지도 위에 표시하는 것이 기본 구현이다.
다만 OTP 경로와의 호환성이 좋지 않으면 지도도 OSM 기반으로 교체한다. Naver 유지를 절대 조건으로 두지 않는다.

호환성은 좌표 변환 후 경로 표시, 배경지도와의 정합성, 긴 경로 렌더링 성능, 현재 leg 강조 등 실제 사용 기준으로 판단한다.
기존 검증 결과와 소수 대표 경로를 먼저 활용한다. 단순한 좌표 변환 오류나 원천 geometry 누락은 지도 교체로 해결되는지 구분한다.
표시 조정 후에도 호환성 문제가 남으면 OSM 기반 지도 전환을 진행한다. MapLibre는 SDK 후보이며, 타일 공급 방식은 전환 시 확정한다.
장소 검색 공급자 교체 역시 이번 요청에서 명시되지 않았다.

## 6. 에이전트 문서 반영 상태

| 결정 | 담당 |
|---|---|
| bbox·202503 GTFS | P0 입력 확인, P1 변환 |
| 비용 절감용 제한 해제 | P0 목록, P2 구현, P7 누락 확인 |
| 기존 시험 재사용·소수 비교 | P4. 상시 shadow/장기 비교 의무 제거 |
| OSM relation 형상 | P3. 정류장 직선/도보 대체 금지 |
| Naver 우선·실제 호환성 | P3 지도 연결과 조건부 전환 |
| 기존 실시간/ML 보존 | P2. 신규 공급자는 P8 후속 |

## 7. 세부 계획을 다시 정리할 때의 순서

1. 기존 실험 결과와 202503 입력을 연결하고 GTFS/OSM → OTP graph 변환.
2. 최초 검색·남은 경로 검색을 OTP로 연결하고 ID·시간·geometry·snapshot 변환.
3. 호출량 절감 때문에 막아둔 기능/정책 목록을 만들고 제거·복원.
4. 앱 응답/지도 연결과 변경 구간 회귀 확인, 선택적으로 ODsay 3~5건 비교.
5. 전환 배포와 필요한 복구 경로 확인 후 ODsay 정상 호출 의존 제거.

에이전트 실행/인계 기준은 [IMPLEMENTATION.md](IMPLEMENTATION.md)와 [AGENT-GUIDE.md](AGENT-GUIDE.md)에 정리했다. 문서 정리는 구현·배포 완료를 뜻하지 않는다.
