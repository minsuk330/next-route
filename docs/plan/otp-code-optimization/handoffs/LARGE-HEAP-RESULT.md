# 큰 heap(8g) 실험 결과 — "메모리 넉넉하면 원본이 낫나"

실행일: 2026-09-11. 계획: [../LARGE-HEAP.md](../LARGE-HEAP.md). 배경: [../UNDERSTANDING.md](../UNDERSTANDING.md) §4.3.
상태: **COMPLETE (로컬 전 동시성 3쌍 관측 완료).** 판정 = 이 로컬 코퍼스에서는 동시성 1 + 큰 heap에서 트레이드오프가 보였고, 동시성 2·4에서는 H+F가 지연·메모리 모두 우세했다. 모든 실제 서빙 부하로 일반화하지 않는다.

> 2026-09-12 정정: 이 문서의 수치는 유효한 로컬 관측값이지만, 일부 run에서 호스트 swap I/O가 증가했으므로 차이를 순수 GC 효과로만 귀속하지 않는다. GC 유형 재집계와 인과 표현은 [후속 계획](LARGE-HEAP-FOLLOWUP.md)을 기준으로 한다. 별도 [VPS 관측](VPS-OBSERVATION-RESULT.md)에서는 A도 c4까지 OOM 없이 동작했고, H+F의 RSS·GC·c4 p95 우위가 재관측됐다.
>
> 2026-09-12 raw 재집계에서 c4 A와 HF 모두 swap I/O 증가가 확인됐다. 기존 8GB run은 완료된 관측 자료이지, swap-free 큰-heap 비교를 대신하지 않는다. run별 GC 종류·marker 구간·heap·swap은 [재집계 보고서](LARGE-HEAP-REANALYSIS.md), PR 검증 계획은 [후속 계획](LARGE-HEAP-FOLLOWUP.md)을 기준으로 한다.

## 0. 결론 한 줄

로컬에서 heap을 3.5g → 8g로 키운 뒤에도 동시성 4에서는 원본이 GC에 26~35초, H+F가 1초 미만을 썼고 H+F의 지연·RSS가 더 낮았다. 다만 일부 run의 host swap 영향이 분리되지 않았으므로 "heap 상한과 무관한 순수 GC 병목"으로 단정하지 않는다. 운영 VPS 1회 관측에서도 c4의 H+F 우위는 같은 방향으로 나타났다.

## 1. 환경

- graph `8b597d8b…`, JAR A `914d9a58…` / H+F `54bbdbcf…`. `-Xmx8g -XX:+UseStringDeduplication`, G1.
- 로컬 Docker VM 14.9G / 11 CPU / aarch64. OTP 한 대만 실행. warmup 100 + measured 100 / OD, 예열 안정 게이트 적용.
- 개선율 = `(A - H+F) / A × 100`, 양수 = H+F 가 빠름/가벼움. 동시성별 3쌍 AB/BA paired bootstrap(seed 20260911). 3.5g 최종 결과는 [../PLAN.md](../PLAN.md) 참조.

## 4. 왜 이런가 — GC 압력과 함께 움직인 차이

원본은 요청마다 pattern 의 `nStops × nTrips` int 배열 2개를 통째 복사한다(단명 쓰레기 대량 생산). H+F 는 원본 `TripTimes` 참조 + offset 만 들어 그 복사가 없다.

- **동시성 1 + 8g**: GC 정지가 작고 A/HF 지연은 거의 비슷했다. 버스 밀집 OD에서 A가 빠른 이유로 H의 추가 조회 비용을 의심하지만 CPU·조회 계측 전에는 가설이다.
- **동시성 2**: 두 검색이 동시에 쓰레기를 뿜어 GC 가 잦아진다(A 4.3~5.4s vs H+F 0.3~0.6s). 그 4~5초 차이가 p50 +18% 의 정체. heap 은 안 참(GC 후 살아있는 heap A 1.5G / H+F 0.8G).
- **동시성 4**: GC 스래싱(A 26~35s vs H+F <1s). RSS 9G(heap 8g 초과). 모든 노선에서 H+F +59~66%.

핵심 관측은 H+F에서 요청 할당량·RSS·GC 정지가 함께 감소했고 동시성이 높을수록 지연 차이가 커졌다는 것이다. 요청별 복사 제거가 주요 설명이지만, 로컬 스왑과 CPU·메모리 접근 비용의 기여는 직접 계측으로 더 분리해야 한다.

## 5. §1 판정 규칙 적용

| 동시성 | 규칙 | 판정 |
| ---: | --- | --- |
| 1 | 전체 median [-5%, 0), 구간 0 포함 + 일부 OD 회귀 | 미확정(전체) / **H-trade**(버스 OD) |
| 2 | 전체·OD median 양수, 3연속 회귀 없음 | **H-dom** |
| 4 | 전체·OD median 크게 양수 | **H-dom** |

종합: **측정한 코퍼스에서는** 좁은 조건(동시성 1 + 큰 heap + 버스 밀집 OD)에서 A 우세가 나타났고, 나머지 측정 조건에서는 H+F가 우세했다.

## 6. 포폴·PR 에 쓰는 문장

- 정직한 프레임: "이 최적화는 메모리 절약이 아니라 할당량 절감이다. 단일 검색에 메모리를 넉넉히 주면 원본이 버스 밀집 노선에서 최대 14% 빠르다. 그러나 동시 요청이 하나라도 겹치면 원본의 복사가 GC 스래싱을 유발해, 동시 2건 +18%, 동시 4건 +59% 로 H+F 가 지연·메모리 모두 앞선다. 실제 서빙은 동시 요청이 상수이므로 H+F 를 택했다."
- 이 표는 "메모리냐 성능이냐" 질문을 없앤다. 답 = "우리 부하 형태(동시성)에서는 둘이 같은 방향".
- 헤드라인은 c4(+59% 지연, +66% 메모리, 모든 노선). c1 트레이드오프는 정직하게 부록으로.
