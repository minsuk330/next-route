# 무슨 일이 일어났고 왜인가 — 8g 실험 raw 를 끝까지 파본 기록

작성일: 2026-09-11. 데이터: [LARGE-HEAP-RESULT.md](LARGE-HEAP-RESULT.md)(요약표) + `/private/tmp/otp-lh8-*/gc.log·requests.jsonl` 직접 추출. 기초 개념: [../UNDERSTANDING.md](../UNDERSTANDING.md).

> 2026-09-12 정정: 이 문서의 raw 관측은 보존하되 원인에 대한 단정은 낮춘다. 로컬 8GB 일부 run에서 호스트 swap I/O가 증가했고, 기존 Mixed 횟수에는 Prepare Mixed가 합산돼 있었다. 별도 [VPS 관측](VPS-OBSERVATION-RESULT.md)은 완료됐으며 A도 c4까지 OOM 없이 동작했다. 정정된 후속 기준은 [LARGE-HEAP-FOLLOWUP.md](LARGE-HEAP-FOLLOWUP.md)를 따른다.
>
> 2026-09-12 raw 재집계: [LARGE-HEAP-REANALYSIS.md](LARGE-HEAP-REANALYSIS.md)에 marker 구간별 GC·heap·swap을 기록했다. c4 세 쌍의 A는 host swap-in/out이 각각 약 13–23GiB 증가했고 HF도 약 0.4–2.7GiB 증가했다. 따라서 기존 c4 지연 우위는 관측값이지만 swap-free 비교로 인용하지 않는다. marker 구간에서 A c4의 GC 후 heap 사용량 중앙값은 3.57–3.74GiB였으며 live set과 동일시하지 않는다.

## 0. 한 줄 결론

원본은 검색 요청마다 전체 pattern을 대상으로 시각표 배열을 만들고 H+F는 이 대형 배열 복사를 제거한다. 로컬 8GB 실험에서는 H+F의 할당량·GC 후 heap·GC 정지·c4 지연이 모두 낮았다. 요청당 약 400MB, old 승격, 조회 비용은 이 차이를 설명하는 **추정 모델**이며 객체별 할당·CPU 계측으로 완전히 분리된 결론은 아니다. 측정한 동시성 1·2·4에서 H+F 메모리가 평평했지만 모든 동시성에서 상수라고 일반화하지 않는다.

비유: 원본은 손님이 올 때마다 도서관 책을 대량 복사해 손님 책상에 쌓는 방식이고, H+F는 원본 서가를 참조하는 방식이다. H+F도 검색 상태를 만들지만 측정에서는 복사 더미와 청소(GC) 부담이 훨씬 작았다.

## 1. 무슨 일이 일어났나 — 숫자로

### 1.1 지연 (측정 100건/OD × 4 OD = 400건, ms)

| 동시성 | A p50 | HF p50 | A p95 | HF p95 | 개선(p50) |
|---:|---:|---:|---:|---:|---:|
| 1 | 378~389 | 364~391 | 472~497 | 458~501 | -1.6% |
| 2 | 489~508 | 398~490 | 723~888 | 562~762 | +18.2% |
| 4 | 804~1,429 | 506~574 | 1,844~2,711 | 779~1,068 | +58.3% |

A 는 동시성 1→4 에서 p50 이 **3.7배**, HF 는 **1.4배** 늘었다. 호스트에 CPU 11개가 있다는 사실만으로 CPU 경합을 배제할 수는 없다. GC·CPU·스케줄링·swap의 기여가 함께 남아 있다.

### 1.2 GC (gc.log 전체 구간, 예열 포함)

| run | 할당 총량 | 할당률 | GC 후 heap 중앙값 | Young 정지 | **Prepare Mixed+Mixed 정지** | 정지 >100ms 횟수 | 최대 정지 |
|---|---:|---:|---:|---:|---:|---:|---:|
| A c1 | 430~620 GB | 1.0~1.4 GB/s | 1.0~1.3 G | 1.3~2.9 s | 1.7~5.0 s | 0~2 | 52~109 ms |
| A c2 | 515~653 GB | 1.8~2.1 GB/s | 2.1~2.3 G | 2.7~4.0 s | 4.4~7.8 s | 3~10 | 146~304 ms |
| A c4 | 600~1,294 GB | 1.7~2.1 GB/s | **3.8~3.9 G** | 22~28 s | **41~58 s** | **299~432** | **712~1,357 ms** |
| HF c1 | 176~288 GB | 0.6 GB/s | 0.77 G | 0.1~0.5 s | 0.7~0.8 s | 0 | 48~60 ms |
| HF c2 | 184~236 GB | 1.0~1.1 GB/s | 0.79 G | 0.3~0.5 s | 0.7~1.0 s | 0 | 58~67 ms |
| HF c4 | 202~331 GB | 1.3~1.6 GB/s | **0.81 G** | 0.9~2.2 s | 0.7~1.0 s | 0~1 | 68~123 ms |

두 열이 이 실험의 핵심이다.
- **GC 후 heap**: 이 표는 예열을 포함한 전체 gc.log의 이전 요약이다. 정확한 marker 구간 재집계에서 GC 직후 heap 사용량 중앙값 범위는 A가 동시성 1/2/4에서 0.99–1.51 / 2.10–2.19 / 3.57–3.74GiB, HF가 0.75–0.76 / 0.76–0.77 / 0.79–0.80GiB였다. 어느 쪽도 live set의 직접 측정값이 아니다.
- **Prepare Mixed+Mixed 정지**: 표의 41~58초는 두 GC 종류를 합한 값이다. 예를 들어 A c4 p1은 Prepare Mixed 90회·11.086초와 Mixed 223회·29.656초다. 이후 보고에서는 분리한다.

### 1.3 기각한 가설

- **거대 객체(G1 Humongous)**: 배열이 region 절반(2MB)보다 커서 humongous 로 잡혀 GC 를 강제하는 줄 알았다. 확인 결과 humongous region 은 A/HF 모두 최대 30개(=120MB, 그래프의 정적 구조)로 동일. **차이의 원인이 아니다.** Humongous Allocation 으로 시작된 GC 는 양쪽 다 run 당 1~2회뿐.
- **Full GC**: 로컬 8GB run에서는 0회였다. 이것만으로 heap·호스트 메모리 압박이 없었다고 결론내릴 수는 없다.

## 2. 추정 원인 사슬 — 다섯 단계

### ① 요청마다 pattern 전부 복사, OD 와 무관 (상수 비용)

`RaptorRoutingRequestTransitDataCreator.merge()` 는 출발·도착지를 보지 않는다. 검색 날짜에 운행하는 **모든** pattern(수도권 그래프 3,936개)에 대해 `TripPatternForDates` 를 만든다. 원본은 각각 `nStops × nTrips` int 배열 2개를 채운다.

실측 추정: A 요청당 할당 ≈ 668MB, HF ≈ 273MB로 차이는 약 395MB다. 이는 H+F 전체 차이이므로 F의 기여·예열·집계 오차가 포함될 수 있다. pattern 수와 배열 크기를 이용한 계산과 규모가 비슷하지만, 전부를 시각표 복사분으로 확정하지 않는다.

### ② 할당률이 2.5배 → Young GC 가 잦아진다

A 1.4~2.1 GB/s vs HF 0.6~1.5 GB/s. G1 은 Eden 이 차면 Young GC 를 한다. A 는 초당 1.4GB 를 쓰니 Young GC 가 수백 ms 마다 일어난다.

### ③ 복사본이 오래 살아 old 세대로 승격된다 — Mixed GC 의 정체

복사 배열이 검색 동안 참조되고 일부가 old 세대로 승격돼 Mixed GC 부담을 키웠을 가능성이 높다. 다만 일반 GC 로그만으로 어떤 배열이 승격됐는지 직접 식별할 수 없으며, 기존 41~58초는 Prepare Mixed와 Mixed를 합친 값이다. 객체 age·old 영역·allocation 프로파일로 보강해야 한다.

기존 313~511회 표기는 Prepare Mixed와 Mixed를 합친 수치다. 두 유형을 분리해 보고하며, A c4에서 두 유형 모두 HF보다 많았다는 방향성만 현재 근거로 사용한다.

### ④ GC 후 heap 증가 모델

동시성 1/2/4에서 A의 GC 후 heap 중앙값은 약 1.2/2.2/3.9G, HF는 약 0.8G였다. 요청별 복사본이 겹친다는 모델과 방향이 맞지만 정확한 선형식이나 요청당 400MB를 증명한 것은 아니다. HF도 요청별 검색 상태가 있으므로 동시성이 메모리에 영향을 주지 않는다고 일반화하지 않는다.

### ⑤ heap 8g 도 소용없는 이유

8GB에서도 A의 높은 할당률과 GC 정지가 남았고 H+F 우위가 관측됐다. 그러나 일부 run에서 호스트 swap I/O도 증가했으므로 p95 차이를 G1만의 효과로 분리하지 않는다. 큰 heap이 요청별 할당 구조를 제거하지는 않지만, heap 크기별 효과를 일반 법칙으로 확정하려면 swap 통제 반복 측정이 필요하다.

## 3. 동시성 1 에서 왜 뒤집히나 — 비용 모델

동시성 1 에서는 A 의 GC 정지가 run 전체 4~5초, 최대 60ms 미만. 요청당으로 나누면 몇 ms. 즉 **복사 비용이 거의 공짜**가 된다(GC 가 여유 있게 따라감). 남는 것은 H 의 새 비용이다.

```
H 의 순이득 ≈ (복사 절감: OD 무관 상수)  −  (조회 횟수 × 간접참조 비용)
```

| OD | 성격 | A p50 | HF p50 | 차이 | 해석 |
|---|---|---:|---:|---:|---|
| cityhall-gangnam | 버스 3환승, 도심 | 398 | 456 | **+58ms 손해** | 도심 버스 pattern 수백 개를 라운드마다 훑음 → 조회 횟수 큼 |
| cheonggye-sadang | 버스+지하철 | 352 | 373 | +21ms 손해 | |
| bupyeong-gangnam | 지하철+버스 | 391 | 388 | ≈0 | |
| bupyeong-seoul | 1호선 단독 | 211 | 186 | **-25ms 이득** | pattern 몇 개만 봄 → 조회 적음 → 복사 절감이 남음 |

H는 배열 복사 대신 원본 `TripTimes`를 간접 조회하고 offset을 더한다. 이것이 c1 일부 OD 손해의 유력 가설이지만 실제 조회 횟수·캐시 미스·CPU 비용은 아직 직접 측정하지 않았다. JIT 인라인 여부도 확인 대상이다.

**현재 가설**: 트레이드오프의 경계에 동시성과 조회 밀도가 함께 작용한다. c2에서 버스 OD가 +12%로 돌아선 것은 이 가설과 일치하지만, 경계를 확정하려면 조회 횟수·CPU·GC를 함께 계측해야 한다.

## 4. 3.5g 결과의 재해석

PLAN.md 의 3.5g 최종표(c1 +7.8%, c2 +22.7%, c4 +40.7%)를 8g 와 나란히 놓으면:

| | c1 | c2 | c4 |
|---|---:|---:|---:|
| 3.5g p50 | +7.8% | +22.7% | +40.7% |
| 8g p50 | -1.6% | +18.2% | +58.3% |

- c1: 같은 heap 조건에서 H+F의 할당 감소로 얻은 차이이므로 코드 효과가 맞다. 다만 3.5GB에서는 heap 여유가 작아 효과가 더 크게 나타났을 가능성이 있으며, 8GB c1에서는 전체 차이가 불확정이었다.
- c4: 3.5g 에서는 A 살아있는 heap 3.9G > 3.5g 라 사실상 OOM 직전 스래싱. 8g 는 담기긴 하지만 Mixed GC 폭주. 둘 다 A 가 무너지는 이유는 같고(구조 ④), 8g 에서 개선율이 더 큰 것은 HF 가 더 좋아진 게 아니라 A 가 더 오래 버티며 더 많은 정지를 겪어서다.

## 5. 평가 — 무엇이 증명됐고 무엇이 아닌가

**관측으로 확인된 것**
1. 로컬 8GB의 동시성 1·2·4에서 A의 할당량과 GC 후 heap이 증가했고 H+F는 훨씬 낮고 평평했다.
2. A c4의 GC 정지와 p95가 H+F보다 컸다. VPS 1회 관측에서도 H+F의 RSS·GC 정지·c4 p95 우위가 같은 방향으로 나타났다.
3. c1 일부 버스 OD에서 H+F 지연 손해가 관측됐다.
4. 두 변형의 humongous region 규모가 비슷했고 로컬 8GB에서 Full GC는 없었다. 따라서 humongous/Full GC를 주된 차이로 볼 근거는 없다.

**증명 안 된 것 / 한계**
1. **OD 4개뿐.** 버스 밀집 2, 혼합 1, 지하철 단독 1. "조회 밀도" 모델은 4점으로 맞춘 것. 코퍼스 확장 필요.
2. **H 의 조회 비용을 직접 재지 않았다.** 잔차(전체 차이 − 복사 절감)로 추정. JFR CPU 프로파일로 `arrivalTime/departureTime` 의 self time 을 A/HF 비교해야 확정.
3. **ARM64 로컬만.** x86·다른 캐시 계층에서 간접참조 비용은 다를 수 있다. VPS 관측이 절대값을 준다.
4. **실시간 업데이터 없는 그래프.** `RealTimeTripTimes` 가 섞이면 H 의 가상호출이 bimorphic 이 되어 조금 더 느릴 수 있다.
5. **요청당 400MB 는 전 구간 평균.** 예열 포함이라 정확한 요청당 값은 아니다. 크기 규모만 신뢰.
6. F 의 단독 기여는 여전히 분리 안 됨.
7. 로컬 일부 run에서 host swap I/O가 증가했다. OTP 단독 원인인지 알 수 없고 GC와 swap의 기여도 분리되지 않았다.

## 6. 앞으로의 방향

### 6.1 지금 바로 (순서대로)

1. **VPS 관측 완료** ([VPS-OBSERVATION-RESULT.md](VPS-OBSERVATION-RESULT.md)). A/H+F 모두 c4까지 성공했다. c4 peak RSS 4.07G/1.98G, p95 2,224/1,750ms, GC 총정지 6,240/449ms가 관측됐다.
2. **운영 전환** (PHASE-6). H+F JAR로 OTP를 띄우고 provider를 전환한다. Prometheus RSS·p95·GC 추세 관측은 통제된 soak를 보완한다.
3. **원인 검증** ([LARGE-HEAP-FOLLOWUP.md](LARGE-HEAP-FOLLOWUP.md)). 8GB raw 재집계는 [LARGE-HEAP-REANALYSIS.md](LARGE-HEAP-REANALYSIS.md)에 완료했다. swap-free `-Xmx10g` 반복 측정과 JFR allocation/CPU 계측은 별도 단계다.
4. **PR 제출** — 관측과 가설을 구분하고 c1 트레이드오프와 VPS 1회 관측 한계를 함께 기록한다.

- 포폴의 운영 근거는 VPS 관측값을 사용한다: **"동일 VPS·4500m 상한에서 H+F는 c4 peak RSS를 4.07G→1.98G, p95를 2,224ms→1,750ms, GC 총정지를 6,240ms→449ms로 낮췄다."** 단, 각 조건 1회 관측임을 함께 밝힌다.
- 그림 한 장: x축 동시성(1/2/4), y축 GC 후 heap 또는 peak RSS — 측정 범위에서 A는 증가하고 HF는 평평했다. live set과 동일한 값이라고 쓰지 않는다.
- 정직 부록: "동시성 1의 일부 도심 버스 OD에서는 원본이 더 빨랐던 run이 있었다. H의 조회 비용이 원인이라는 가설은 후속 CPU·조회 계측 대상이다." 단, 로컬 8GB run은 swap I/O가 증가해 수치만으로 swap-free 상태의 성능을 주장하지 않는다.
- 면접 예상 질문에 답 추가: "heap 늘리면 되지 않나?" → "8GB로 늘려도 요청별 할당은 남았고 c4에서 H+F 우위가 관측됐다. heap은 압박 시점을 늦출 수 있지만 할당 구조 자체를 제거하지 않는다."

### 6.4 측정 방향

- OD 코퍼스 15개로 확장: 도심 버스 5 / 지하철 단독 5 / 혼합 5. 조회 밀도 모델 검증.
- upstream speed test(norway 등) 재현 준비 — PR 리뷰어가 요구할 것.
- VPS x86 관측은 완료됐지만 1회 관측이고 다른 변수가 함께 바뀌었다. 간접참조 비용의 아키텍처 의존성을 확인한 실험으로 사용하지 않는다.
