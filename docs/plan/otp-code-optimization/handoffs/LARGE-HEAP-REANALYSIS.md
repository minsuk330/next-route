# 8GB raw 재집계 — 큰 heap 결과의 신뢰 범위

작성일: 2026-09-12. 입력: `/private/tmp/otp-lh8-*` 18개 run. 목적: 10GB 재측정 전에 기존 8GB 결과의 실행 구성·GC 측정 구간·호스트 swap을 run별로 대조한다.

## 결론

기존 8GB raw는 **측정된 지연/RSS/GC 결과로 보존**한다. 그러나 c4의 A뿐 아니라 HF도 호스트 swap I/O가 늘었고, c2 A 일부도 증가했다. 따라서 기존 결과로 “스왑 없는 큰 heap에서도 A보다 HF가 빠르다”는 PR 주장을 증명할 수 없다. A c4의 swap이 더 컸다는 사실은 관측됐지만, macOS 전역 카운터라 OTP와 다른 프로세스의 기여를 분리할 수 없다.

10GB gate는 별도로 진행한다. 여기 결과는 방향성·실패 이력이지 10GB 표본으로 합치지 않는다.

## 실행 조건과 식별

- 18개 run 모두 동일 수도권 graph SHA-256 `8b597d8bbc1c8588acf0c829735da7ff22ea9d160bd7cb272e23a11ea3002385`를 사용했다.
- A JAR SHA-256 `914d9a58c016d2ff1a697e2d6fb8d9d8dec7d93dada747d8162acd8a3da225b1`, HF JAR SHA-256 `54bbdbcf7b6df4b110b7e7621eeea3f49d653b51248b59fa367a43bc2ec0db7f`.
- 컨테이너 이미지 digest `sha256:d67198007bb4441b07d45587320f83154de80ece3608f80408ef14c6ea847753`, Java `25.0.4`, G1, `-Xmx8g`, `UseStringDeduplication`.
- run마다 예열 100건/OD + 측정 100건/OD, OD 4개, 측정 요청 400건(모두 HTTP 성공), warmup stability gate 활성. 3개 pair 라벨은 p1/p2/p3.
- 원 계획은 `-Xmx10g`였지만 이 raw의 실제 JVM 옵션은 모두 `-Xmx8g`다. A c4 p2만 stability timeout 900초였고 나머지 17개 run은 600초였다.
- swap delta는 `run_isolated.py`가 Docker 컨테이너 시작 직전과 measured 요청 완료 직후 수집한 macOS 전체 카운터 차다. 표의 KST 시각은 benchmark manifest 시작 시각이므로 swap 관측 구간은 컨테이너 startup/예열 및 종료 일부를 더 포함한다.
- 아래 RSS는 측정 구간 100ms polling의 최고 관측값(정확한 순간 최대치 아님). GC는 측정 start/end marker 안에서 완료된 pause만 세었고, start 경계를 넘어온 pause는 제외했다. GC 총정지는 사용자 요청 처리 중 pause 합계이며 concurrent GC 시간을 뜻하지 않는다.
- KST 실행 순서는 raw의 `summary.json.manifest.startedAt`으로 재구성했다. c1은 세 pair 모두 A→HF라 AB/BA 균형이 아니다. c2와 c4는 pair suffix 기준 A→HF / HF→A / A→HF다. c4의 p2/p3 실제 실행 시각은 suffix 순서와 달랐다.

## GC 집계 정정

측정구간 안에서 A c4의 GC pause를 종류별로 나누면 다음과 같다. 기존 설명처럼 Prepare Mixed와 Mixed를 합산해 한 종류인 양 다루지 않고 별도 보고한다.

| Run | Young Normal | Concurrent Start | Prepare Mixed | Mixed | Remark | Cleanup | 총정지 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A c4 p1 | 84 / 10.38s | 32 / 4.60s | 31 / 4.46s | 100 / 14.26s | 32 / 0.89s | 32 / 0.02s | 34.60s |
| A c4 p2 | 45 / 3.44s | 31 / 2.19s | 31 / 3.09s | 47 / 4.70s | 31 / 0.58s | 31 / 0.01s | 14.00s |
| A c4 p3 | 66 / 7.87s | 30 / 2.88s | 30 / 5.35s | 73 / 9.41s | 30 / 0.75s | 31 / 0.01s | 26.27s |

수치는 OTP JVM 로그의 완료 pause 행만 계산했다. `Prepare Mixed`는 Mixed pause와 별도 유형이다. JDK 로그 분류/집계는 OTP 저장소 `test/performance/seoul-metro/summarize_run.py`의 측정 marker 해석에 맞춰 run별 `gc.log`를 재파싱했다. 표의 수 합은 기존 `metrics.json.gcCompletedPauseCount`와 일치한다.

GC 후 heap 분포도 측정 marker 안의 각 완료 pause 행에서 `before->after`의 after 값을 다시 모았다. run별 중앙값 범위 / p95 범위는 다음과 같다.

## Pair별 원 관측 개선율

개선율은 `(A - HF) / A × 100`; 양수면 HF가 더 낮다. 3개 pair만 있어 여기서 새 통계적 우월성 주장을 만들지 않는다.

| 1 | p1 / p2 / p3 | -2.07% / +6.32% / -1.62% | -3.18% / +5.35% / -0.86% | +24.75% / +10.98% / +15.87% |
| 2 | p1 / p2 / p3 | +18.21% / +21.60% / -0.08% | +14.23% / +22.33% / +15.03% | +53.66% / +40.55% / +50.51% |

관측된 방향은 기존 요약과 같다. 다만 A c4 세 run 모두 swap-in/out이 각각 약 13–23GiB 증가했고 HF c4도 약 0.4–2.7GiB 증가했다. 그러므로 이 결과는 **swap-free 상태의 직접 증거가 아니다**. c1 A p1과 c2 A p1/p2 또한 swap-out이 크게 증가했다. 소량의 swap-in만 있는 run도 0은 아니므로 macOS 전역 지표만으로 OTP 귀속·미세한 배경 잡음을 확정할 수 없다.

3. 10GB gate 시작 전에 host/docker 상태, 수집 가능한 swap counter, 중단 기준을 run manifest에 명시한다. 환경 swap I/O가 관측되거나 수집이 누락된 run은 PR 판정에서 제외하되 raw와 실패 사유는 보존한다.
