> 해석 원칙: 아래 수치는 각 조건 1회 관측이다. 운영 후보 선택에는 사용하지만 통계적 일반화나 특정 객체의 인과 증명에는 사용하지 않는다.

## 0. 한 줄 결론 (예측 정정 포함)

**예측은 "원본은 8G VPS 에 못 들어간다" 였다. 틀렸다.** 컨테이너 메모리 상한 4500m에서 원본도 동시 4건까지 OOM 없이 동작했다. 진짜 차이는 "들어가나 마나"가 아니라 **원본은 상한에 가까운 RSS를 사용하고(peak 4.07~4.08G) H+F는 절반 수준만 쓴다(1.98~2.09G)**는 것, 그리고 원본의 동시 4건 GC 총정지가 6.2초(H+F 0.45초)였다는 것이다.

## 1. 환경

- VPS: x86_64, 4 CPU, RAM 7,901MB, 관측 시작 시 available ~5,050MB. 기존 컨테이너 11개(api/worker/postgres/redis/ml-serve/observability) 정상 가동 중 — **프로덕션 라이브 상태에서 관측**.
- 격리: OTP 는 포트 18081, 컨테이너 메모리 상한 `--memory/--memory-swap 4500m`(호스트 OOM killer 가 이웃 죽이지 않게). 기존 컨테이너 무접촉.
- graph: 원본 실험 graph(`8b597d8b`)가 `/private/tmp` 정리로 유실 → baseline JAR(2.10.0-SNAPSHOT, commit `02c0b4b5`)로 **재빌드**(`24d5331b`, 229MB, patterns 3,936·stops 43,783 동일). 입력·config·OTP 버전·구조는 같지만 SHA가 다르므로 동일 graph 반복 실험은 아니다.
- JAR: A `914d9a58`, H+F `54bbdbcf`(로컬 실험과 동일 해시, VPS 에서 재대조 완료).
- image: x86 `maven:3.9-eclipse-temurin-25` digest `31618505…`. `-Xmx3500m -XX:+UseStringDeduplication`, G1.
- 부하: OD 4개 × warmup 25 + measured 20 = 80건/run. 쿼리 시각 `2026-09-15T08:00+09:00`(재빌드 graph 서비스 기간 [09-11, 11-12] 안). 전 run routingError 0.
- **주의: x86 4CPU VPS 는 로컬 ARM 11CPU 보다 느리다.** 절대 latency 를 로컬(A c1 378ms)과 비교 금지. A vs HF 대비와 RSS 절대값만 유효.

## 3. 읽는 법 — 무엇이 보이나

### 3.1 원본도 상한 안에서 돈다 (예측 정정)

로컬 8g **무제한**에서 A는 c4 peak 9.0G였다. VPS는 상한 4500m을 줬고 A는 peak 4.07G로 동작했다. 동시에 GC 총정지와 최대 정지가 크게 증가해, 메모리 상한 아래에서 GC 비용을 치른 관측과 일치한다. 다만 상한의 효과만 분리한 실험은 아니다.

→ 배포 논거를 "원본은 못 뜬다" 에서 **"원본은 상한을 꽉 채운다"** 로 정정해야 한다.

### 3.2 진짜 차이는 RSS 헤드룸

- A 는 c1 부터 3.48G, c2·c4 는 4.07~4.08G(상한 4500m 에 근접). HF 는 동시성 무관 1.98~2.09G.
- HF의 warmup 완료 RSS 1.98~2.09G에는 graph뿐 아니라 JVM heap·native·metaspace·GC 구조가 모두 포함된다. 따라서 이 값만으로 graph 자체가 1.9G라고 분리할 수 없다.
- A와 HF의 1.4~2.1G 차이는 요청별 시각표 복사·승격 가설과 일관되지만, 이번 RSS 측정만으로 객체별 기여를 직접 증명하지는 않는다.
- 이 VPS 의 실제 여유는 ~5G 이고 다른 컨테이너와 나눠 쓴다. 3000m 상한에서는 HF가 더 유리할 가능성이 높지만, A의 c2 OOM 여부와 HF의 c4 성공 여부는 아직 측정하지 않았으므로 예측으로만 남긴다.

### 3.3 GC 와 latency

- A 의 GC 총정지: c1 766ms → c2 4,461ms → c4 6,240ms. HF: 266 → 282 → 449ms. c4 에서 **14배** 차이.
- A 의 GC 최대 정지: c4 545ms(요청 하나가 1.5초인데 그중 0.5초가 한 번의 GC 정지). HF 는 20ms.
- latency 대비: c4 에서 HF 가 p50 1,301 vs A 1,552(+16%), p95 1,750 vs 2,224(+21%). c1/c2 는 거의 동률(저동시성 = GC 여유 = 큰 heap 실험의 c1 과 같은 양상).

## 4. 로컬 실험과 교차 확인

| 관측 | 로컬 8g | VPS 4500m 상한 | 일치? |
|---|---|---|---|
| A의 GC 후 heap/RSS가 동시성과 함께 증가 | 1.2→2.2→3.9G | 3.48→4.08→4.07G | ✅ 방향 일치, VPS는 c2부터 상한 근접 |
| 측정 범위의 HF 메모리가 평평 | 0.8G | 1.98~2.09G | ✅(절대값은 graph·JVM·아키텍처 차이 포함) |
| A GC 가 동시성에 폭증 | c4 26~35s(무제한) | c4 6.2s(상한서 억제) | ✅ 방향 일치 |
| 저동시성 latency 비슷 | c1 ±0 | c1/c2 ±수% | ✅ |
| 고동시성 HF 우세 | c4 p50 +58% | c4 p50 +16% | ✅ 방향 일치, 폭은 작음(상한이 A 를 강제로 억제 + x86) |

VPS c4 개선폭(+16%)이 로컬(+58%)보다 작다. 4500m 상한이 A의 메모리 증가를 제한해 GC 패턴을 바꿨을 가능성이 있지만, x86/ARM·CPU 수·graph SHA·실서버 이웃 부하도 함께 달라 원인을 하나로 분리할 수 없다.

## 5. 결론 — 배포 논거 (정정판)

1. **둘 다 8G VPS 에서 동작한다.** 원본도 상한 4500m 안에서 c4 까지 OOM 없이 돈다. "원본은 못 뜬다" 는 틀린 예측이었다.
2. **원본은 메모리를 두 배 쓴다.** peak 4.07G vs 1.98G. 이 VPS 는 여유 5G 를 여러 컨테이너가 나눠 쓰므로, OTP 에 4.1G 를 상시 내주는 것은 부담이다. H+F 는 2G 로 절반이다.
3. **원본은 동시성에서 GC 로 값을 치른다.** c4 GC 6.2초·최대 정지 545ms. H+F 0.45초·20ms.
4. **운영 후보는 H+F로 결정한다.** 근거는 "원본이 안 뜬다"가 아니라 동일 서버의 이번 관측에서 확인된 절반 수준의 RSS, 훨씬 짧은 GC 정지, c4의 더 나은 tail latency다. 반복 관측 전에는 모든 부하에서 같은 개선율을 보장한다고 표현하지 않는다.

포폴 문장(정정): "실서버(8GiB x86, 라이브)에서 원본과 최적화본을 컨테이너 4.5G 상한으로 띄웠다. 둘 다 동작했지만 원본은 상한을 꽉 채우고(4.07G) 동시 4건에서 GC 정지 6.2초를 겪은 반면, 최적화본은 2.0G·0.45초였다. 여유 메모리를 이웃 컨테이너와 나눠 쓰는 환경이라 메모리 절반이 곧 배포 근거였다."

## 6. 한계

- OD 4개 × 20건/run = 통계 아님, 절대값 1회 관측. p50/p95 는 참고.
- x86 4CPU VPS 라 latency 절대값을 로컬·다른 환경과 비교 불가. A/HF 대비만.
- 재빌드 graph(SHA 다름, 구조 동일). 원본 실험 graph 와 바이트 동일 아님.
- 상한 4500m 는 관측용. 실제 운영 상한(예상 3000m)에서의 A OOM 경계는 재보지 않음 — 다음에 확인 가능.
- 30분 soak·다중 쌍 없음(계획대로 관측 1회). 운영 전환 후 Prometheus 추세 관측은 이를 보완하지만 통제된 soak를 대체하지 않는다.
