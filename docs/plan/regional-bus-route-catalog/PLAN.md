# 경기·TAGO 노선 정류장 표 + TAGO 노선 단위 도시코드 (#267)

티어 M · 브랜치 `feat/tago-route-city-mapping` (fresh main `493af781`) · 관련 #264(이 표를 읽는 쪽), #265, #252

## 목표

1. 경기·TAGO 노선별 정류장 순서를 **실시간 API 와 같은 순번 체계**로 적재하는 표 `regional_bus_route_stop` 과 월 1회 적재 배치.
2. TAGO 도시코드를 접두사 단위 표(`TagoCityCodes`, 38개)에서 **노선 단위**(이 표의 노선 → city_code)로 바꿔 지방 실시간 커버율을 올린다.

#264 가 쓸 조회(정류장 id → 실시간 순번)는 이 PR 범위가 아니다. 표와 적재만 만들고 #264 가 읽는다.

## 실측 근거 (2026-10-06~07, issue #264·#267 댓글)

- TAGO `getRouteNoList?cityCode=` 를 `routeNo` 없이 부르면 그 도시 노선 전체. 138개 도시 → **21,393 노선, 도시 간 중복 0** → routeId → cityCode 는 함수다. 양양군만 0건.
- 접두사 50종. `TSB` 6,983 / `GGB` 2,158(경기도 TAGO 에 있음, 31개 시) / 이번에 처음 본 `CCB`·`ISB`. 기존 표의 `ADB`(2도시)·`YDB`(3도시)·`DJB`·`WJB` 는 다도시 → **접두사 단위 표는 구조적으로 틀림**.
- 노선 id 모양: `[A-Z]{3}` + 숫자뿐 아니라 `BSB5201002F00`(영문), `GMB171-110`(하이픈)도 있다. `TagoCityCodes.cityCodeOfId` 의 `^[A-Z]{3}\d+$` 는 이것들을 조용히 버린다.
- 노선 목록 139회 = 130초(호출당 약 0.94초, 직렬).
- 경기 `getBusRouteStationListv2`: `stationSeq`·`turnYn`·`turnSeq`·`stationName` 등. 경유 가상점은 이름에 `(경유)`(예: `의왕터널진입(경유)`), `mobileNo` 없음.
- TAGO `getRouteAcctoThrghSttnList`: `nodeid`·`nodenm`·`nodeord`·`updowncd`·`gpslati`·`gpslong`. 가상점 표시 칸 없음.
- 경기 도착 `locationNo` = 실시간 순번 차이(경유 가상점 포함). TAGO `arrprevstationcnt` 는 미측정.
- 한도: TAGO 노선정보 일 500,000 / 경기 노선 일 10,000 / 포털 키 동시 세션 30(GBIS·TAGO 도착·TAGO 지하철과 공유, `TagoBusArrivalAdapter` 주석).

## 설계

### 표 — `V56__create_regional_bus_route_stop.sql`

```sql
CREATE TABLE regional_bus_route_stop (
    id          bigint generated by default as identity primary key,
    provider    varchar(8)   not null check (provider in ('GG', 'TAGO')),
    route_id    varchar(32)  not null,   -- 실시간 API 원본 id. 경기 9자리, TAGO 접두사 포함(DJB30300151)
    route_no    varchar(64),
    city_code   varchar(8),              -- TAGO 도시코드. 경기 노선도 TAGO 목록에서 온 값을 둔다(참고용)
    stop_id     varchar(32)  not null,   -- 경기 stationId / TAGO nodeid
    stop_name   varchar(100),
    seq         int          not null,   -- 경기 stationSeq / TAGO nodeord (실시간 순번 공간)
    turn        boolean,                 -- 경기 turnYn. TAGO 는 null
    up_down     smallint,                -- TAGO updowncd. 경기는 null
    waypoint    boolean,                 -- 경기: 이름 '(경유)'. TAGO: null(판별 미정, #264 실측 후)
    lat         double precision,
    lon         double precision,
    loaded_at   timestamptz  not null,
    CONSTRAINT uq_regional_bus_route_stop UNIQUE (provider, route_id, seq)
);
CREATE INDEX idx_regional_bus_route_stop_stop ON regional_bus_route_stop (provider, stop_id);
```

- JPA 엔티티를 두지 않는다. `BaseEntity` 상속 엔티티는 `deleted_at` 칼럼이 없으면 스키마 검증에서 부팅이 죽고(M7 PR-5b 함정), 이 표는 노선 단위 통째 교체라 JdbcTemplate 이 맞다(선례: `PostgisBusRouteSegmentPolylineAdapter`).
- **VPS 수동 배치 필요**(V18+ untracked convention). 운영은 v55.

### 원천 포트 / 어댑터

`application/regionalbus/port/out/RegionalBusRouteSourcePort.java`
```java
public interface RegionalBusRouteSourcePort {
    List<TagoCity> tagoCities();                                    // getCtyCodeList
    List<TagoRoute> tagoRoutes(String cityCode);                    // getRouteNoList 전 페이지
    List<RegionalRouteStop> tagoRouteStops(String cityCode, String routeId);   // getRouteAcctoThrghSttnList
    List<RegionalRouteStop> gyeonggiRouteStops(String routeId);    // getBusRouteStationListv2 (9자리)
}
```
- 실패는 예외 대신 결과 타입으로: `SourceException` 하나를 던지되 `blocking`(포털 공통 오류 20/22/30~33 — 그날 계속 실패) 여부를 싣는다. 배치는 blocking 이면 즉시 중단, 아니면 그 노선만 건너뛴다.
- `infrastructure/adapter/out/api/tago/TagoBusRouteAdapter.java`, `infrastructure/adapter/out/api/gyeonggi/GyeonggiBusRouteStationAdapter.java` — 같은 포트의 두 어댑터 대신 **한 어댑터 클래스가 포트를 구현**하고 내부에서 두 base-url 을 쓴다(`RegionalBusRouteSourceAdapter`). 파싱 규칙은 `TagoBusArrivalAdapter` 와 같다: `items: ""` = 0건, `item` 단일 객체 = 1건, `header.resultCode` "00" 정상 / "99" 동시 세션(일시, 재시도) / `OpenAPI_ServiceResponse.returnReasonCode` 20/22/30~33 = blocking.
- 경기 응답: `response.msgHeader.resultCode` 0 정상, 4 = 결과 없음(0건). `busRouteStationList` 단일 객체/배열 둘 다.
- 키: TAGO·경기 모두 같은 포털 키(`tago.api.bus-key`, `gyeonggi.api.bus-key` — 운영은 같은 값).
- URL: `tago.api.bus-route-base-url: https://apis.data.go.kr/1613000/BusRouteInfoInqireService`, `gyeonggi.api.bus-route-base-url: https://apis.data.go.kr/6410000/busrouteservice/v2`. 값은 `enc()` 로 인코딩(하이픈·영문 id).
- `numOfRows=1000`, totalCount 로 페이지 반복.

### 적재 서비스 — `application/regionalbus/service/RegionalBusCatalogLoadService.java`

1. `tagoCities()` → 도시별 `tagoRoutes()` → `routeId → (cityCode, routeNo)` 전체 목록(약 2.1만, 약 140회).
2. 노선마다:
   - 접두사 `GGB` → `gyeonggiRouteStops(routeId.substring(3))` 로 provider=GG, route_id=9자리, waypoint=`stop_name.contains("(경유)")`, turn=`turnYn=='Y'`, city_code=TAGO 목록 값.
   - 그 밖 → `tagoRouteStops(cityCode, routeId)` 로 provider=TAGO.
   - 결과 0건이면 그 노선은 건너뛴다(기존 행 유지, `empty` 카운트).
   - 성공하면 `RegionalBusRouteStopStore.replaceRoute(provider, routeId, rows, loadedAt)` — **한 트랜잭션에서 그 노선 행 삭제 + 일괄 삽입**. 노선 단위로 원자적이라 중간에 죽어도 다른 노선은 옛 값 그대로.
3. 병렬도 `concurrency`(기본 3) 고정 스레드풀 + 노선별 작업. "99" 는 최대 3회, 1초·2초 대기 후 재시도.
4. blocking 오류 → 남은 작업 취소, 실행 실패로 기록.
5. 중단되지 않았으면 **이번 노선 목록에 없는 노선만 삭제**(폐선 정리). 0건·실패 노선은 목록에 있으니 옛 값이 남는다. 노선 목록은 한 번이라도 실패하면 실행 전체를 멈추므로 정리는 온전한 목록일 때만 돈다. (초안의 "loaded_at < 실행 시작 + 실패율 1%" 기준은 0건·실패 노선까지 지워서 폐기 — 구현 노트 참조)
6. 결과 로그 한 줄: 노선 수 / 성공 / 0건 / 실패 / 삭제 / 소요. 마지막에 `TagoCityCodeLookup.refresh()`.

### 도시코드 조회 — `application/route/mapping/TagoCityCodeLookup.java` (@Component)

- 메모리 스냅샷: `Map<routeId, cityCode>`(약 1.9만) + 알려진 TAGO 접두사 집합. 부팅 시 1회 + 6시간마다 + 적재 직후 `refresh()`. api 와 worker 둘 다 같은 DB 를 읽는다(api 는 적재를 안 하므로 주기 갱신으로 따라감).
- `Optional<String> cityCodeOfRoute(String routeId)`: 표 → 없으면 `TagoCityCodes.cityCodeOfId` 폴백(표가 비어 있는 배포 직후·적재 실패 시 지금과 같은 동작).

- `TagoCityCodes` 는 **폴백으로 남긴다**(삭제는 표가 운영에서 안정화된 뒤 별건).

## 계약 (경계 리뷰 대상)

- DB: `regional_bus_route_stop` 스키마(위). `seq` 는 실시간 API 순번 — #264 가 의존.
- 동작: 표에 노선이 있으면 그 city_code, 없으면 기존 접두사 표. 표가 비어도 지금과 같은 동작.
- 플래그 기본값: `REGIONAL_BUS_CATALOG_ENABLED=false` → 켜기 전엔 적재 0회, 조회는 폴백만.
- 실패 경로: blocking 오류·목록 실패 = 실행 중단·삭제 없음 / 노선 실패·0건 = 그 노선 옛 값 유지 / 폐선 = 목록에 없는 노선만.

## 배포

- V56 VPS 수동 배치 → 이미지 배포(api·worker) → worker env `REGIONAL_BUS_CATALOG_ENABLED=true` → 부팅 시 표가 비어 있으므로 1회 적재(약 2.15만 호출, 병렬 3이면 약 2시간 예상).
- 적재 완료 후 api 는 6시간 안에 스냅샷 갱신(즉시 반영하려면 api 재시작).
- 확인: 대전 이외 다도시 접두사(TSB) 정류장 도착 실호출, `ADB`·`YDB` 의 두 번째 도시 노선 실호출.
