# 버스 GTFS 탑승 시간 실측 보정 (L 티어, slug `bus-runtime-calibration`)

## Context

2026-10-13 강남 → 서울역 대조에서 버스 421 탑승 시간이 OTP 23~25분, ODsay 34분이었다. 조사 에이전트 3개로 확인한 결과는 다음과 같다(원자료·스크립트 = `research/`).

**결론**: OTP 버스 탑승 시간은 GTFS(KTDB 2025-03) 시간표 그대로이고, 이 시간표는 실측이 아니라 추정치다. 서울에서는 실측보다 약 42% 짧다(실측 = GTFS × 1.74). 짧게 잡힌 버스가 지하철보다 앞에 서고, 버스가 들어간 경로의 ETA·알림 시각도 같이 앞당겨진다.

### 확인한 사실
1. **시간표 성격** (`research/gtfs/`)
   - KTDB 교통접근성 보고서 p.119~120: 버스 stop_times = 수집 시각표의 출발 시각 + "시간대별 구간 속도 DB × 거리"로 만든 정류장 사이 시간 + 정차 10초 고정.
   - 구간 속도 원천: 서울·경기·부산 BIS, TAGO 지방 3월 1주 버스 위치, 그 밖 Google. 실측 운행 기록이 아니다.
   - 우리 `prepare_gtfs.py` 는 시각을 바꾸지 않는다. `apply_gbis_routes.py` 는 경기 정류장 사이를 거리로 보간하지만 총 소요는 그대로 둔다.
   - 출처별 시간대 변화(최장/최단): 서울 1.18, 경기·인천·마을·공항 같은 공통 곡선(±5%), 시외 93%는 변화 없음.
   - 06~21시 상업 속도 KTDB/공식(e-나라지표 2025): 서울 1.46, 울산 1.45, 대구 1.14, 광주 1.15, 대전 1.10, **부산 0.68**(오히려 느림). → 지역마다 방향과 크기가 달라 전국 단일 계수는 쓸 수 없다.
2. **우리 실측 대비** (`research/measured/`, 서울 208개 노선, 2026-06·09~10)
   - 데이터: `bus_arrival_label_event`(운영 8일 보존) + VPS 아카이브 parquet `/srv/nextroute/ml-data/bus_label` + 로컬 `ml/data/bus_label`. 라벨은 `POSITION_STOP_FLAG_CORRECTED`(high_provisional)만 썼다. `ARRIVAL_API_ETA` 는 도착 뒤 찍힌 값이라 뺐다.
   - 평일 실측/GTFS 중앙값: SHORT(4~8정류장) 1.74 [1.49–2.03], LONG(10~20정류장) 1.74 [1.58–1.94], FULL 1.76.
   - 시간대: 04-06 1.59, 06-09 1.75, 09-16 1.77, 16-20 1.80, 20-24 1.69. 주말·공휴일 1.52~1.70.
   - 유형: 간선 1.71, 지선 1.78, 마을 1.72(1.15~2.35로 퍼짐), 광역 1.45(노선 1개).
   - 6월과 9~10월이 같다(1.740 / 1.744).
   - 교차 검증: 라벨을 거치지 않고 `bus_position_raw` section_order 진행만으로 다시 재도 1.7.
   - 421 강남→서울역: 실측 38~44분, GTFS 22~27분, ODsay 34분 — 실측이 ODsay보다도 길다.
   - 보정 효과(평일 오차 중앙값): 원본 42.6% → 서울 전역 ×1.74 10.3% → 노선×시간대 8.8%(같은 데이터로 맞춘 값이라 낙관적).
3. **ODsay 대비** (`research/odsay/`, 14시 2km 이상 172쌍)
   - OTP/ODsay: 서울 0.63, 경기 0.69, 인천 0.67, **부산 1.01**.
   - 간선 0.64, 지선 0.67, 광역·직좌 0.87~0.95(표본 11).
   - 짧은 구간일수록 OTP가 더 짧다(2km 미만 0.43, 6~10km 0.79).
   - OTP 시간표의 08·18시는 14시보다 3% 길 뿐이다.
   - 한계: ODsay도 추정치다. 지방 광역시·중소도시는 ODsay 일일 쿼터 소진으로 표본 0(남은 28 OD = `research/odsay/ods_pending_quota.txt`).
4. **OTP 쪽 수단**
   - 포크(2.11-SNAPSHOT)에는 transit 이동 시간 배율이 없다. 있는 것은 board/alightSlack(탑승마다 고정 초)과 reluctanceForMode(순위만, 표시 시간 불변)뿐이다.
   - 지금 앱 쿼리의 버스 reluctance 1.3 은 이 편향을 순위에서만 일부 메운다.
   - GTFS-RT TripUpdates 는 검색에 실시간이 섞여 정적 원칙에 어긋나고, KTDB trip(`_OrdNNN`)과 실제 차량을 잇는 키도 없다.

## 설계

### 방향 = 그래프 빌드 전 stop_times 전처리
- 새 단계 `calibrate_bus_runtimes.py`
  - 넣는 자리: `build_otp_graph.sh` 의 2b(GBIS) 다음, 2c(가상 역) 전. 2c는 stops.txt만 바꾸므로 순서는 무관하다.
  - 입력: GTFS 디렉터리 + 계수표(JSON/CSV) → 출력: stop_times.txt 만 바꾼 피드.
  - 대상: 버스 노선(route_type 3, 계수표에 있는 출처·노선)만. 지하철·철도·시외(ACC3)는 건드리지 않는다.
  - trip 마다 첫 정류장 출발 시각은 그대로 둔다. 수집 시각표에서 온 값이라 배차·첫차·막차가 유지된다.
  - 정류장 사이 주행 시간 = 원래 주행 시간 × 계수(노선, 출발 시간대). 정차 시간은 원래 값(10초)을 둔다. 실측에 정차가 포함되는지는 1단계에서 확인한다.
  - 계수 우선순위: 노선×시간대 → 노선 → 출처×유형×시간대 → 출처×시간대 → 1.0(보정 안 함).
  - 시간대 경계에서는 trip 출발 시각 기준으로 한 계수를 쓴다. 구간마다 바꾸지 않는다.
- **가드**
  - 같은 패턴 안에서 추월이 없어야 한다(OTP `TripPattern` 가정). 보정 뒤 같은 패턴 trip 의 정류장별 도착 순서가 바뀌면 그 패턴은 단조가 되도록 고친다. 고친 수를 리포트에 남긴다.
  - 자정 넘김(24:00+) 허용. 계수 범위는 [0.8, 2.5] 밖이면 빌드를 실패시킨다.
  - 리포트(JSON): 노선·trip 수, 계수 분포, 총 소요 변화, 추월 수정 수, 계수 출처별 비중.
- **reluctance 재조정**: 보정 뒤 버스 reluctance 1.3 → 1.0~1.1 을 코퍼스로 다시 고른다. 보정 안 한 지역은 그대로라 하향 폭은 신중히 정한다.

### 계수 데이터원 (단계)
1. **서울(1단계)**
   - 열린데이터광장 OA-21217 "노선별 정류장 구간별 평균 운행시간"(TOPIS, 1시간 단위, 2022-01~ 월별 zip) → 전 노선 노선×시간대 계수.
   - KTDB id 가 서울 id 그대로라 매핑이 쉽다(`BR_TAGO_SEB100100409`=421).
   - 확인할 것: ID 형식, 정차 포함 여부, 최신 월.
   - 우리 실측(208개 노선)은 검증 세트로 쓴다. 기간을 나눠 맞춤과 평가를 분리한다(예: 6월로 맞추고 9~10월로 평가).
   - OA-21217 이 안 되면 대안: 서울 전역 시간대·유형 계수(실측 표 그대로, 평일 1.6~1.8 / 주말·심야 1.5~1.6).
2. **경기·인천(2단계)**
   - 공개 구간 시간 데이터를 찾지 못했다. ODsay 비율(0.67~0.69)이 서울(0.63)과 비슷하니 같은 방향일 가능성이 높다.
   - 실측 수집: GBIS 버스 위치 API로 표본 노선 1~2주 → 계수. 그 전에는 보정하지 않는다(1.0).
3. **지방(3단계)**
   - 부산은 ODsay와 같고 공식 통계보다 느려서 보정하지 않는다.
   - 대구·대전·광주·울산 등은 ODsay 남은 표본 + TAGO 버스 위치(키 동시 30세션 공유 제약) 표본으로 도시별 판단.

### 영향 범위(경계 리뷰 대상)
- OTP 계획 시간을 쓰는 곳이 모두 바뀐다(의도):
  - 검색 응답 소요·도착 시각과 정렬(`ItineraryRanker`, `LegacyRouteResponseMapper`)
  - 여정 계획 시간(`JourneyCompiler`, `JourneyLegDraft`)
  - 정적 진행 ETA(`StaticGeometryProgressEtaCalculator`, `BoardingChainEtaCalculator`, `RemainingPathEtaComposer`)
  - 재탐색 후보(`RemainingPathCandidateProvider`)
  - 알림 소요 추정(`RouteSearchTravelTimeEstimator` → `BusAlertDispatchService`)
- 실시간 원천(도착 API·위치·링)은 그대로. 정적 시간과 실시간 차이가 줄어드는 쪽이다.
- 앱 계약(DTO) 불변. 마이그레이션 없음. 그래프 재빌드·배포 필요(release-manifest 에 계수표 sha 기록).

## 변경 (2026-10-14, 사용자 목표 = ODsay·네이버 대비 버스 탑승시간 차이 10% 이하)
목표가 "실측"에서 "ODsay·네이버와 같은 값"으로 바뀌어, 계수 원천을 OA-21217 → **ODsay sectionTime** 으로, 모델을 곱셈 → **거리 + 정류장 재계산** 으로 바꿨다. 근거·스크립트 = `research/calibration/`.

- **모델**: 버스 구간(정류장→다음 정류장) 시간 = (secPerMeter × 구간 m + secPerHop) × trip 시간대 계수. 첫 출발·정차(10초)는 그대로.
  - 기각: 곱셈(×1.6). GTFS 구간 속도와 ODsay 구간 속도의 상관이 0.07이라, KTDB 구간 시간을 늘려도 구간별 차이가 남는다(LOO 오차 17.0% vs 11.6%).
  - 시간대 계수 = trip 원래 주행시간 / 같은 패턴의 10~16시 trip 중앙값(0.7~1.4로 자름). KTDB의 출퇴근 모양은 유지된다.
- **ODsay 의 한계**: sectionTime ≈ 구간당 고정 약 285초 + 거리 + 정류장(이 공식으로 오차 2.5%). 1정류장도 6분이다. 고정항은 시간표로 표현할 수 없고, 우리 실측에는 없다(SHORT·LONG 비율 1.74 동일). 그래서 짧은 구간(3정류장 미만·2km 미만)은 ODsay보다 짧게 남는다(의도).
- **계수**(`config/otp-national/bus-runtime-coefficients.json`, 3정류장 이상 구간 최소제곱)

  나머지 지역, 시외(ACC3), 농어촌(KPTI), 똑버스(GGTR)는 그대로 둔다. 광주·청주·전주·창원 16 OD는 ODsay 쿼터(하루 30회) 때문에 다음 날 받는다(`research/calibration/ods_pending_quota2.txt`).
- **도구**: `runner/calibrate_bus_runtimes.py` + 테스트 13개, `build_otp_graph.sh --bus-runtime-coefficients`(2d, 2b 다음·2c 전). 추월 가드는 패턴 안에서 앞 trip보다 먼저 도착하지 않게 계수를 올리고, 쓴 뒤 다시 검사한다(남으면 빌드 실패).

## 변경 2 (2026-10-14, 네이버 대조 반영 — 서울 TOPIS 구간 시간)
네이버 기록값(사용자 확인 2026-10-12) 5개를 대조하니 ODsay 공식 맞춤만으로는 막히는 축(잠실→강남 테헤란로·송파대로)이 20% 짧았다. 우리 실측 360 잠실→강남 32.9분 = 네이버(36 − 도보 3)라서, 네이버는 실제 막힘을 반영한 값이다. ODsay 는 막힘 없는 공식이다.

- **원천**: 서울 열린데이터 OA-21217 Open API `tpssRouteSectionTime`(TOPIS, 최근 30일, 정류장 쌍 × 시간대 평균 운행 초, 서울 노선 + 서울 안 경기 노선). `runner/fetch_seoul_section_times.py` 로 최근 평일 N일(기본 3)을 받아 쌍×시간 중앙값 CSV 를 만든다(키 `SEOUL_BUS_USE`, 출력 안 함).
- **적용**: 정류장 쌍이 표에 있으면 구간 = `sectionTimes.scale` × 그 버스가 정류장을 떠나는 시간대 값(없으면 전체 중앙값). 시간대 계수는 곱하지 않는다(값이 이미 시간대별). 공식 대비 0.2~5배 밖이면 버리고 공식을 쓴다. 나머지 구간은 기존 공식.
- **scale 0.935**: 우리 위치 라벨 실측(서울 208 노선, 평일 전 기간)과 비율 1.0 이 되는 값.
- **추월 가드 변경**: 시간대별 구간 시간은 trip 마다 모양이 달라, 정류장마다 앞 trip 보다 먼저 도착·출발하면 나머지 구간을 그만큼 미룬다. 다시 검사해 남으면 빌드 실패.
- **기각**: 우리 실측 정류장 쌍으로 혼잡 계수(60초 폴링 잡음이 1~1.5분 구간보다 커서 10월 표본 밖 검증에서 오차 증가), 구간 거리 꺾은선, 빠른 버스 별도 그룹.
- **빌드**: `build_otp_graph.sh --bus-runtime-coefficients … --bus-section-times <csv>`. CSV 는 커밋하지 않고 sha 를 manifest 에 남긴다.
