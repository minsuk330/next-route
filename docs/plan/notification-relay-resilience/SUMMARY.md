# 알림 발송 relay 내구성 (#451) — 느린 FCM·장애·강제 종료에도 제때·한 번만·빠짐없이

## 뭘 하나
여정 알림 발송기(relay)를 **"큰 배치를 잡고 다 끝날 때까지 기다리는"** 구조에서 **"워커마다 조금씩 계속 집어 가는"** 구조로 바꾼다. 동시 발송 수를 늘리고, 급한 알림을 먼저 보내고, 처리 중인 행은 살아 있다는 신호를 주기적으로 남겨 회수를 빠르게 하고, 재시도는 짧게 시작해 점점 늘리면서 무작위로 흩뜨린다.

비유: 우체국 창구 4개가 200통을 한꺼번에 받아 다 처리할 때까지 문을 닫던 것을, 창구를 늘리고 급한 등기부터 한두 통씩 계속 받게 바꾼다. 창구 직원이 쓰러지면 3분이 아니라 30초 안에 다른 직원이 이어받는다.

## 왜 (#446 실측, 여정 2,000·폭주 700건)
- **느린 FCM(2~5초):** 처리량이 워커 4 ÷ 왕복 시간 ≈ 1.1건/초. relay 몫 p95 270초, 362건 미발송. 배치 하나가 175~190초 걸려 회수 기준 3분에 붙음(중복 위험)
- **줄 서는 순서가 들어온 순서뿐:** 긴급 p95 203초 ≈ 여유 296초
- **worker 강제 종료:** 잡아 둔 110행이 3분간 묶임. 회수 3분 = 만료 바닥 3분이라 1건 만료(잃음)
- **고정 재시도 60초 × 3회:** 일시 오류 20%에서 DEAD 2건, 장애가 끝나면 재시도가 한꺼번에 몰림(10초에 427건), 견딜 수 있는 장애는 약 120초

## 핵심 결정
1. **당겨 가는 워커(pull):** 워커 N개가 각자 "k건 claim → 보냄 → 기록"을 반복한다. 다른 워커를 기다리지 않는다. claim 해 둔 행이 워커 큐에서 오래 기다리지 않으므로 회수와 겹칠 일이 없다.
2. **동시 발송 수를 설정값으로:** 기본 4에서 32로 올린다. 왕복 3.5초면 초당 약 9건, 평소(수백 ms)면 초당 100건 이상이다. 전역 속도 제한(Redis)은 만들지 않는다. FCM 한도(프로젝트당 분당 60만)가 우리 규모보다 수백 배 커서 묶이지 않고, 재시도 몰림은 6번이 푼다.
3. **급한 것 먼저:** 알림 행에 `priority` 칼럼(V70)을 둔다. 적재 때 등급(긴급 0, 주의 1, 여유·기타 2)을 적고, claim 은 `priority, scheduled_at` 순으로 한다.
4. **살아 있다는 신호(heartbeat):** 발송 중인 행의 `processing_started_at` 을 10초마다 갱신하고, 회수 기준을 3분에서 **45초**로 줄인다. 부팅 검증으로 "회수 기준 < 만료 바닥 − 재시도 여유"와 "발송 타임아웃 × 2 < 회수 기준"을 확인한다.
5. **회수된 행의 늦은 기록 막기:** claim 할 때마다 바뀌는 증서(`attempt_count`)를 기록 조건으로 쓴다. 회수돼 다른 워커가 다시 잡은 뒤에 원래 워커가 늦게 SENT·실패를 쓰지 못하게 한다(조건부 UPDATE).
6. **재시도:** 첫 재시도 5초, 이후 ×2, 상한 60초, ±20% 지터. 횟수 상한 대신 만료 안에서 계속하되, 안전 상한으로 최대 8회를 둔다.
7. **Redis 가 죽어도 변화 감지는 계속:** 수집기가 스냅숏을 Redis 에 저장하다 실패해도 변화 피드는 부른다.
8. **플래그:** `journey.notification.relay.mode=BATCH|PULL`, 기본 BATCH 다(지금 그대로). 우선순위 정렬·재시도 정책도 각각 플래그로 두고 기본은 지금 동작이다. 측정으로 PULL 이 낫다는 근거가 나오면 기본값을 바꾼다.

## Opus 검토로 바뀐 것
- 상태 기록은 전부 "증서가 맞을 때만 바꾸는" 조건부 UPDATE로 한다. 엔티티 저장이 증서를 낡은 값으로 덮기 때문이다.
- 늦은 기록이면 울릴 권리 반납까지 되돌린다(롤백). 그렇지 않으면 두 번 울린다.
- FCM 요청에 연결·읽기 타임아웃을 걸고 SDK 자체 재시도를 묶는다. 지금의 5초 타임아웃은 기다리기만 멈출 뿐, 요청은 뒤에서 계속 돈다.
- 우선순위는 알림 종류(놓침·빠듯 > 접근 > 나머지)로 정한다. 시각은 DB now() 를 쓰고, 회수는 자기 heartbeat 가 살아 있을 때만 한다.
- 워커는 하나씩 연쇄로 깨운다. DB 커넥션이 몰리는 것을 막기 위해서다.

## 사람이 볼 곳 (경계 리뷰)
- **상태 전이:** PENDING → PROCESSING(claim, 증서 +1) → SENT·FAILED·DEAD·PENDING(재시도). 회수는 heartbeat 가 45초 끊긴 행만 PENDING 으로 되돌린다. 기록은 증서가 일치할 때만 한다.
- **실패 경로:** 워커가 죽으면 heartbeat 가 멈춰 45초 뒤 회수된다. 발송 타임아웃 5초 × 2 < 45초다. 늦게 도착한 기록은 0행 갱신으로 버리고 지표로 센다.
- **스키마:** V70 `journey_notification.priority smallint not null default 2`, claim 인덱스를 `(priority, scheduled_at) where status='PENDING'` 로 바꾼다. Flyway 자동 적용이다.
- **플래그 기본값:** 모두 지금 동작이다. 끄면 지금과 같은 SQL·같은 순서다.

## PR
- **PR-1:** 당겨 가는 워커 + 동시 발송 수 + heartbeat·45초 회수 + 증서 조건부 기록
- **PR-2:** 우선순위 칼럼(V70)과 정렬
- **PR-3:** 지수 백오프 + 지터 + 만료 안 재시도, 변화 피드를 Redis 저장에서 분리
- **PR-4:** #446 같은 칸(①·③a·③b·③c·③c'·④a)을 다시 측정한 전후 비교 문서

## 리스크
- 동시 발송이 늘면 FCM HTTP 연결도 는다. SDK 연결 풀 상한(JDK 기본 keep-alive 5)에 막히면 TLS 핸드셰이크가 매번 일어난다. PR-1 에서 전송 계층을 확인하고 측정한다.
- heartbeat 는 DB 쓰기를 늘린다. 10초마다 진행 중인 행 묶음 UPDATE 1번이라 작다.
- "최소 한 번"은 그대로다. 접수와 기록 사이에 죽으면 중복이 생긴다. 회수가 3분에서 45초로 빨라질 뿐이고, 울림 억제(기기 쪽)는 이번 범위 밖이다.

## 검증법
계약 테스트:
- 회수된 행에 늦게 온 SENT·실패 기록은 무효
- heartbeat 중인 행은 회수되지 않음
- heartbeat 가 끊긴 행은 45초 뒤 회수
- 긴급이 여유보다 먼저 claim 됨
- 백오프 수열·지터 범위·만료 넘는 재시도는 취소
- PULL 모드에서 워커 하나가 느려도 다른 워커는 계속 보냄
- 플래그 끔이면 SQL·순서가 같음
- Redis 저장 실패에도 변화 피드 호출
