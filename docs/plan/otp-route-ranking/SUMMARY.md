# OTP 경로 후보 정렬 (버스 편향 수정)

## 뭘 하나
OTP 검색 후보를 앱에서 다시 줄 세운다: 같은 노선 반복을 하나로 묶고 OTP 일반화비용 순으로 정렬해 5개만 보인다.
OTP 요청에 탐색 창 30분과 버스 가중치 1.3 을 넣는다.

## 왜
OTP 는 "도착시각 순 출발편 타임라인"을 주고 GTFS 버스 시간이 10~30% 짧아서, 상위 5개를 버스가 차지해 지하철이 묻힌다.

## 핵심 결정
- 정렬 = OTP 일반화비용 순 — 환승·도보 벌점이 들어가 있음. "소요시간 우선"(옛 TODO)은 실험상 지하철을 더 밀어내서 기각
- 같은 노선 묶기 = 노선 ID 순서 기준, 가장 이른 편 1개. 5개가 안 되면 다음 출발편으로 채움
- 탐색 창 30분 — 반복 편이 줄고 OTP 응답이 약 절반으로 빨라짐
- 버스 가중치 1.3 — 데이터 보정 전 임시 처방. 표시 시간은 그대로(#386)
- 재탐색은 개수만 5개로 자름 — 자체 ETA 정렬이 있어서 정렬은 안 바꿈

## 건드는 곳
planConnection.graphql, OtpRoutingProperties, OtpRoutingAdapter, OtpPlanConnectionMapper, RoutingItinerary, ItineraryRanker(신규), RouteSearchService, RemainingRouteSearchService, 테스트 5개

## 리스크
- 재탐색 후보도 창·가중치 때문에 조금 바뀜(개수·정렬 규칙은 그대로)
- 모드 목록을 주면 그 모드만 탐색 → 전체 모드를 나열해야 함. 운영 OTP 로 오류 없는지 확인 필요
- 후보 20개로 OTP 응답이 커짐 → 실측 후 과하면 10~15 로 낮춤

## 검증법
관련 단위 테스트 통과 + 운영 OTP 에 새 쿼리로 6개 구간 호출해 오류 없음, 강남→홍대·신촌→강남 2호선 1위 재현.
배포 후 운영 검색 API 로 같은 결과 확인.
