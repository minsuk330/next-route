# 지하철 링 지연 단축 (#371)

## 뭘 하나
링이 실제 열차보다 35~62초 늦게 움직이는 것을 원천 사건 대비 +20초 이내로 줄인다. PR은 3개로 나눈다.
- PR-1: 도착·위치 두 원천 중 더 새로운 쪽을 채택한다.
- PR-2: 직선의 시작점을 원천 사건 시각으로 옮긴다.
- PR-3: 주기를 줄인다.

## 왜
운영 프레임(journey 225)에서 확인했다. 도착은 +46~59초, 출발은 +35초 늦었다. 그 결과 실제 도착 순간 링은 0.5~0.58이었고, 열차가 출발한 뒤에도 "정차 중"으로 남았다.

## 핵심 결정
- 위치 API가 도착 행보다 새로우면 위치를 쓴다. 전역 도착·출발도 근거로 삼는다. 계산기는 그대로 두고 리더가 PREV_* 관측으로 바꿔 넘긴다.
- 앵커는 원천 시각으로 하되, 30초 넘게 늦은 원천은 서버가 본 시각 − 30초로 상한을 둔다. 2분 늦은 원천에서 바로 늦음이 뜨던 202 회귀를 막기 위해서다.
- 이슈 #4(도착 tick에서 바로 다음 구간으로)는 기각한다. 1.00 프레임이 사라지기 때문이다. 대신 tick을 5초에서 2초로 줄인다.
- 위치 수집 15초→5초는 키 일일 한도를 확인한 뒤 정한다. 도착 API 주기는 유지한다.
- 채택 원천과 지연을 로그·메트릭으로 남겨 다음 여정에서 바로 확정한다.

## 건드는 곳
SubwayRingSignalReader, SubwayRingObservation, SubwayRingCalculator, SubwayRingUpdateService, JourneySubwayRingProperties, application.yaml, SubwayRingReplayIT, 관련 단위 테스트

## 리스크
- 원천 앵커로 예정이 당겨지면 감지가 늦는 구간에서 LATE가 늘 수 있다. 그래서 PR-1을 먼저 배포하고 late-grace 30초를 유지한다.
- 위치 API의 방향·역 오표기 노선(9호선·공항철도 전례)에서는 잘못된 "새 사건"을 채택할 수 있다. 같은 열차·방향·체인 역으로만 매칭해 이를 막는다.

## 검증법
- 단위 테스트와 링 IT 5종이 통과해야 한다.
- 재생에서 원천 대비 반영 지연과 도착 순간 진행률을 변경 전후로 비교한다(목표 0.8 이상).
- 운영 다음 여정에서 detect.lag p50이 20초 이하여야 한다.
