# 알림 효과 계측 (Phase 5 ⑦, L)

> PHASE-5 표는 M 이었으나 API·스키마 신설이 붙어 **L 로 승격**했다.
> codex 설계 리뷰 반영 완료(2026-08-11) — 지적 12개의 처분은 [PLAN.md](./PLAN.md) §11.

## 뭘 하나

앱이 "알림을 눌렀다·화면에 들어왔다·행동했다"를 보내 줄 창구
(`POST /api/journeys/{journeyId}/telemetry/batch`)를 만들고, 원본을 새 표
`journey_telemetry_event`(V41)에 쌓는다. 같은 기록이 두 번 와도 한 번만 센다.

## 왜

발송 쪽은 이미 다 잰다. 없는 것은 **받은 뒤**다 — 눌렀는지, 누르고 무엇을 했는지는 폰 안에서만
일어난다. 그 절반이 비면 알림을 늘릴지 줄일지 판단할 근거가 없다. 모바일은 FCM 수신과 선택
콜백까지 이미 구현돼 있어 전송만 붙이면 된다.

## 핵심 결정

- **원본을 저장한다.** alert-to-action 은 두 사건의 시각 차이라 카운터만으로는 상관을 못 낸다
- **공통 컬럼 + `jsonb` 상세.** 전부 컬럼으로 박으면 앱이 이벤트를 하나 늘릴 때마다 서버
  마이그레이션이 모바일 배포와 묶인다
- **`unique(user_id, telemetry_id)` + `ON CONFLICT DO NOTHING`.** 재전송이 예외를 내면 batch 가
  통째로 죽는다. 유일성을 전역으로 두면 기기를 물려받아 계정이 바뀔 때 남의 ID 가 내 이벤트를 삼킨다
- **`alertId` 도 소유권을 확인하고, 수집 시점에 알림 메타를 스냅샷한다.** 확인이 없으면 남의 알림
  id 로 "내가 눌렀다"를 심을 수 있다. 스냅샷이 없으면 알림 행이 지워질 때 상관을 못 낸다
- **모르는 이벤트 종류를 거부하지 않는다.** 앱이 먼저 배포되는 것이 정상 순서다
- **사용자는 토큰에서만 읽고, 좌표·식별자는 받지도 태그로 쓰지도 않는다**
- **best-effort 다.** 이 API 의 실패가 여정·발송·폴링을 흔들지 않는다
- **`detail` 은 이벤트별 허용 키의 스칼라만** 저장한다(4KB·중첩 3단 제한). 좌표가 숨어들 자리를 없앤다
- 보관은 30일이되 기준은 **`received_at`**(기기 시각으로 지우면 시계 조작에 무너진다). **삭제 배치는
  이 PR 밖**이고, 붙일 때 "받아 주는 시각 창"을 함께 정해야 한다 — 지우는 순간 멱등 키가 열린다

## 리스크

- 앱이 보내는 값을 그대로 저장한다 → 허용 키 필터가 좌표 유입을 막는 유일한 방어선
- 기기 시각(`occurred_at`)은 틀어질 수 있다. 지연 계산은 `received_at` 과 함께 본다
- 보관 삭제가 없으므로 표가 계속 자란다(후속 과제로 등록)
