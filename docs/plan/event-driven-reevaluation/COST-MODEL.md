# PR-0 버스 실시간 호출 비용 모델 (#415-3)

> 결론부터: **목표 부하(동시 여정 2,000)에서는 어떤 방식으로 감시하든 서울 버스 API 를 하루 약 100만~200만 회 불러야 한다.** 지금 운영은 하루 8.3만 회다. 공급자 한도 상향은 설계와 무관하게 필요하다. 노선 단위 감시는 같은 감지 주기를 기준으로 키 단위 폴링보다 2~8배 싸고, 사용자가 늘어도 비용이 **서울 노선 수(약 600) × 갱신 주기**에서 멈춘다.

측정일 2026-10-14. 재현 스크립트 = `cost-model/`.

## 1. 실측

### 1.1 공급자 갱신 주기 (`mkTm`)
- 방법: `getArrInfoByRouteAll` 을 노선 4개(143·472·6411·741)에 5초 간격으로 20분(960회, 오류 0) 호출하고, 응답 `mkTm`(공급자 생성 시각)이 바뀌는 간격을 셈. 해상도 5초. 결과 = `cost-model/mktm_result.txt`.
- **갱신 간격**: 중앙값 9초, p90 20초, 평균 10.7초.
- **관측 지연**(받은 시각 − `mkTm`): 중앙값 8~10초, p90 14~20초.
- **판정용 지문이 바뀌는 간격**: 정류장별 (첫 차량, 상태 문구, 도착 초 30초 단위) 지문이 중앙값 10초, 하위 10% 5초마다 바뀜.

함의:
- 감시 주기를 10초보다 짧게 잡아도 새 데이터가 없다 → 감시자 주기 하한 = 10초.
- 버스 긴급 SLO 10초는 **우리가 처음 본 시각부터** 잰다. 공급자 시각부터면 관측 지연(중앙값 약 9초)이 더해져 물리적으로 불가능.
- 지문을 단순 비교하면 거의 매 갱신이 이벤트 → 히스테리시스와 판정 민감도 기준(PLAN §2.4)이 필수.

### 1.2 수요 분포 (서울 버스 승차 데이터)
- 원천: 서울열린데이터 `CardBusTimeNew` 2026년 9월, 42,155행(노선 × 정류장 × 시간대별 승차 인원). 피크 = 18시.
- 운영 여정 데이터(175건, 대부분 시험)는 노선 공유율을 추정하기에 너무 적어 쓰지 않음.

## 2. 모델

- 동시 여정 수 C(피크 시간 기준)는 시간대별 승차량에 비례해 하루 동안 변함.
- 각 여정은 다음 버스 승차 키(노선, 정류장) 하나를 **그 시간대 승차 비중에 비례해** 뽑음.
- 실시간 창(탑승 20분 전) 안에 있는 여정 비율 `in_window` = 0.3 / 0.5 / 0.7 (민감도). 창 안 등급 체류: 긴급 25% · 주의 50% · 여유 25%.
- 비교하는 세 방식 (같은 키·노선은 한 번만 부름 = 캐시·묶기 반영):
  - **현행**: 키 단위, 간격 긴급 15초(캐시 하한)·주의 30초·여유 120초.
  - **같은 주기 키 폴링**: 키 단위, 감시자와 같은 감지 주기(긴급·주의 max(5·15, 10)초, 여유 60초).
  - **노선 감시**: 노선 단위 `getArrInfoByRouteAll`, 노선 주기 = 가장 급한 구독자 등급의 주기.
- 하루 호출 = Σ시간대 Σ(활성 키 또는 노선 ÷ 주기) × 3600.

## 3. 결과 (갱신 주기 10초, `cost-model/cost_runs.txt`)

`in_window = 0.5` (가운데 가정):

| 동시 여정 | 피크 활성 키 / 노선 | 하루 호출: 현행 | 같은 주기 키 폴링 | **노선 감시** |
|---|---|---|---|---|
| 2,000 | 950 / 413 | 158만 | 278만 | **167만** |
| 6,000 | 2,673 / 539 | 456만 | 801만 | **273만** |
| 20,000 | 7,197 / 594 | 1,359만 | 2,366만 | **372만** |

민감도(`in_window` 0.3 ~ 0.7):
- 2,000: 노선 감시 121만~199만, 현행 96만~219만.
- 20,000: 노선 감시 336만~389만, 현행 865만~1,800만.

읽는 법:
- **같은 감지 품질 기준으로 노선 감시는 키 폴링의 약 0.6배(2,000) ~ 0.16배(20,000)**. 노선 하나를 부르면 그 노선의 모든 정류장이 같이 오기 때문이다.
- 2,000에서 현행과 노선 감시의 총량이 비슷한 이유: 현행은 여유 등급을 120초마다 보고(감지 2분+), 노선 감시는 10~60초로 본다. 감시 쪽이 더 자주 보면서도 같은 비용이다.
- **상한**: 노선이 약 600개라 모든 노선을 10초마다 불러도 하루 약 520만 회. 사용자가 몇 명이든 이 이상 늘지 않는다. 키 폴링은 사용자 수에 비례해 끝없이 는다.

## 4. 판정 (PR-B 관문)

1. **한도 상향 신청이 필요하다.** 목표 부하 2,000에서 노선 감시도 하루 120만~200만 회. 지금 앱 안 예산은 검색 5,000 + 수집 60,000이고, 운영 실사용은 하루 8.3만 회(2026-10-14 Prometheus). 이건 이벤트 감시 때문이 아니라 목표 부하 자체의 요구다. 현행 방식도 같은 규모가 필요하다.
2. **PR-B 는 구현하되 잠든 채 배포한다.** 예산 배분기(PLAN §2.6)가 한도 안에서 긴급 → 주의 → 여유 순으로 감시하고, 남는 키는 안전망 폴링으로 돌린다. 한도가 오르면 설정값만 바꾼다.
3. 공급자 한도 요청 근거 = 위 상한(약 520만/일). "사용자 수와 무관한 상한"이 신청서의 핵심 숫자다.

## 5. 한계
- 여정의 승차 키가 승차 비중을 따른다는 가정. 앱 사용자는 특정 노선에 몰릴 수 있다. 몰리면 노선 감시가 더 유리해진다(공유 증가).
- `in_window`·등급 체류 비율은 가정. 운영 여정이 쌓이면 #416 지표로 대체.
- 갱신 주기 실측은 노선 4개 × 20분 × 저녁 1회. 새벽·노선별 편차는 미측정.
- 경기·지방 버스(별도 API·한도)는 제외.
