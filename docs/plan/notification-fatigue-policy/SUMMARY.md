# 여정 악화 알림 정책 (#428) — 경로당 1번·조용한 갱신·할 일 담기

## 뭘 하나
악화 알림이 **경로 버전마다 한 번만 울리게** 한다. 그 뒤에 더 나빠지거나 다른 환승이 나빠지면 새로 울리지 않고 **이미 떠 있는 알림을 조용히 고쳐 쓴다.** 알림 문구는 상태가 아니라 **할 일**을 말한다.

비유: 같은 이야기를 반복해 깨우지 않는 비서. 처음 한 번만 어깨를 두드리고, 그 뒤 바뀐 내용은 메모지를 바꿔 끼워 둔다.

## 왜
- 지금은 환승마다·단계(빠듯/놓침)마다 따로 울려 한 여정에서 여러 번 진동할 수 있다
- 문구가 "환승 시간이 빠듯해요 / 앱에서 새 안내를 확인하세요" — 무엇을 하라는지 없음
- 배포 전이라 전환율은 못 잰다 → 원칙을 세우고 테스트로 보장하는 것이 결과물

## 조사로 확인한 사실
- 앱은 백그라운드에서 **서버 문구를 그대로** 보여 주고, 누르면 안내 화면(재탐색 카드 포함)을 연다 → 문구·횟수는 서버만 고쳐도 바뀐다
- 갱신 열쇠(collapse)는 지금 **환승 단위**라 환승이 여럿이면 안 덮인다. Android 는 `tag` 를 안 넣어 **화면에 떠 있는 알림은 안 바뀐다**(전달 전 것만 합쳐짐)
- 보드 모드(운영 켬)는 위험 알림을 20초 미뤘다가 재탐색 push 가 나가면 위험 알림을 취소 — "합치기" 기반이 이미 있다
- 판정에는 다음 차 도착 시각은 있지만 그다음 차 시각은 없다 → "놓치면 몇 분 늦어요"는 이번 범위에서 뺌

## 핵심 결정
1. **울림 = 경로 버전당 1번.** 그 경로 버전에서 위험(빠듯·놓침)이나 재탐색 push 가 한 번 울렸으면, 이후 악화는 **조용한 갱신**
2. **조용한 갱신**: 갱신 열쇠를 (여정, 경로 버전) 하나로 넓혀 이전 알림을 덮고, iOS 는 `interruption-level: passive`(소리·진동·화면 켜짐 없음), Android 는 `tag` 로 덮고 **조용한 채널** 지정(앱이 채널을 만들어야 함 → 인계)
3. **문구 = 할 일 + 보낸 순간의 숫자**(보드 push 방식, 만료로 낡은 숫자 방지)
   - 빠듯: "2호선이 3분 뒤 와요 — 서두르면 탈 수 있어요"
   - 놓침 + 대안: 재탐색 push 에 합침, 제목 "환승을 놓쳤어요", 본문 "○○에서 7호선 타면 4분 빨라요"
   - 놓침 + 대안 없음: "다음 2호선은 14:32 — 눌러서 안내 보기"
4. **제외**: 접근 알림("갈아탈 차가 곧 도착해요")은 상한·갱신 열쇠와 무관(안내라서). 링은 알림 아님
5. 재탐색 보드의 두 번째 이후 push(더 나은 대안이 새로 생김)는 **조용한 갱신**으로 바꾼다(권장, 확인 필요)

## 건드는 곳
TransferRiskNotifier(경로 버전 울림 확인), JourneyNotificationEnqueuer(조용함 표시·문구 재료), 보드 push(합친 제목·조용함), FcmMessageFactory(문구·갱신 열쇠·조용함), FirebaseAdminMessagingClient(Android tag·채널, iOS interruption-level). 마이그레이션 없음(조용함은 payload 에 표시). 앱 인계: Android 조용한 채널 생성.

## 리스크
- 앱이 조용한 채널을 만들기 전 Android 는 갱신이 울릴 수 있다 → 채널 없으면 서버가 갱신을 **보내지 않는** 안전 기본값(플래그)
- 첫 알림이 만료된 뒤의 갱신은 덮을 대상이 없어 조용히 새로 뜬다 — 의도(진동 없음)
- 플래그로 끄면 지금 동작 그대로

## 검증법
계약 테스트: 악화→개선→악화 = 울림 1 / 빠듯→놓침 = 울림 1 + 조용한 갱신 1 / 환승 2개 악화 = 울림 1 / 놓침+대안 = 합친 알림 1(위험 행 취소) / 재탐색 수락 → 새 경로 버전에서 다시 울림 1 / 접근 알림은 상한 무관 / FCM 메시지: 조용함이면 passive·tag·채널, 아니면 기존. 이후 #427 부하 실험에서 "경로 버전당 울림 2번 이상 = 0" 지표.
