# OTP 경로 다양성 (서로 다른 경로 5개)

## 뭘 하나
본 검색에서 서로 다른 경로가 5개 미만이면 "지하철만" → (아직 부족하면) "버스만" 검색을 더 해서 합친 뒤 비용 순 5개를 낸다.
같은 경로 반복으로 채우지 않는다.

## 왜
OTP 는 지배당한 대안을 탐색 단계에서 버려 부평→서울 1개, 노원→강남 3개만 나온다. 수단별로 따로 물으면 대안이 살아난다(부평 12개).

## 핵심 결정
- 부족할 때만 추가 검색 — 서울 도심 대부분은 본 검색으로 5개라 비용 없음
- 지하철만 먼저(0.05~0.6s, 싸다), 그래도 부족하면 버스만 — 순차, 같은 OTP 허가 안
- 추가 검색 1회 예산 2초 상한, 실패하면 무시하고 본 결과로 응답
- 노선이 실제로 적은 구간(홍천→인제 2개)은 5개 미만 허용 — 채우기는 중복으로 보여 기각
- 재탐색은 그대로(후보 수 = 실시간 평가 횟수)

## 건드는 곳
OtpRoutingProperties, OtpRoutingAdapter, RouteSearchService, 테스트 3개(어댑터·검색 배선·재탐색)

## 리스크
- 고유 경로가 적은 구간은 OTP 호출이 1~2회 늘어 응답이 최대 ~2초 길어질 수 있음
- 수단 제한 검색이 지하철끼리 환승 같은 새 경로를 올려 순위가 바뀜(의도)

## 검증법
단위 테스트 통과 + 배포 후 운영 검색 API 로 부평→서울·노원→강남 5개·중복 0, 강남→홍대는 추가 검색 없이 그대로.
