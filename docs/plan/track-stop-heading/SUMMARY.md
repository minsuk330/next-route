# 트랙 정류장 진행 방향 (#538)

## 뭘 하나
근처 정류장 응답에 `routeNames`, `heading`(대표 방향 패턴 코드, 다음 정류장 1~2개, 방위각)을 추가한다.
노선 방향 응답에 `nextStopNames` 를 추가한다. 추가만 하므로 앱은 필드가 없어도 지금처럼 동작한다.

## 왜
지금은 버스 방면이 종점 이름으로만 나온다. 그래서 길 건너편의 같은 이름 정류장을 구분할 수 없다.

## 핵심 결정
- 대표 방향 = 방위각 ±60° 묶음 다수결(이슈 원안의 다음 정류장 다수결 기각: 운영 실측 대표 포함 72% → 91%)
- 왕복 패턴은 같은 코드가 길 건너편에도 나온다 → 앱이 코드 겹침 + 방위각 차 ≤60° 로 묶는다(이슈 댓글). 80m 보강은 실측상 불필요
- 거리순 앞 12개 묶음만 계산 — 운영 실측에서 15회 호출 합이 121ms 라 순차로 하고 병렬화하지 않음
- 정류장별 실패는 그 정류장만 null, 목록은 200
- 캐시 추가 없음 — 정류장 패턴은 이미 10분 캐시돼 있음
- `PatternStop` 에 좌표를 추가하되 2인자 생성자를 남겨, 기존 13곳은 그대로 둠

## 건드는 곳
trackPatterns.graphql, TransitPatternPort, OtpTransitPatternAdapter, TrackViews, JourneyTrackProperties, TrackStopHeading(신규), TrackSelectionQueryService, 시험

## 리스크
- 교차로에서 꺾는 노선(약 9%)은 대표 방향 밖이다 → 앱 섹션에서 빠진다
- 앱이 방위각 조건을 빼먹으면 왕복 패턴 정류장이 길 건너편과 묶인다

## 검증법
단위·서비스 시험(이슈 테스트 8항목 + 왕복 패턴)을 통과하면 완료다. 배포 뒤 강남역 사거리 응답에서 길 건너편 정류장 쌍이 코드나 방위각으로 갈리는지 확인한다.
