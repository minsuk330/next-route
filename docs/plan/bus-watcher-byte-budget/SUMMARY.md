# 서울 버스 감시자 켜기 준비 — 데이터량 예산 + 노선별 조회 방식 (#415 후속, M)

## 뭘 하나
잠든 채 배포된 버스 노선 감시자(#422)를 켤 수 있게, **호출 수뿐 아니라 받는 데이터량도 하루 예산 안에** 묶는다. 노선마다 "노선 전체를 한 번에" 받을지 "지켜보는 정류장만 따로" 받을지를 두 예산의 남은 양을 보고 고른다.

## 왜
노선 단위 응답은 259KB, 정류장 단위는 2.4KB(약 108배, gzip 없음). 지금 감시자는 노선 단위만 써서, 상한까지 돌면 하루 약 1TB → 서버 수신 월 2TB 를 넘는다. 호출 한도를 아끼려고 대역폭을 태우는 거래라, 대역폭 쪽 계량기가 없으면 켤 수 없다.

비유: 택배를 상자째(노선) 받을지 낱개(정류장)로 받을지. 상자는 배송 횟수(호출)가 적지만 무겁고(바이트), 낱개는 가볍지만 횟수가 많다. 필요한 물건이 몇 개인지 보고 고른다.

## 핵심 결정
- 노선별 비용 = 호출 몫 사용률 + 데이터 몫 사용률. 노선 단위 = 호출 1·바이트 (정류장 수 × 2.3KB), 정류장 단위 = 호출 k·바이트 k × 2.4KB(k = 그 노선에서 지켜보는 정류장 수). 둘 중 남은 예산 대비 싼 쪽
- 바이트는 실제 받은 응답 크기를 센다(추정값 아님). Redis 일 단위 카운터, 호출 몫과 같은 방식
- 데이터 몫이 떨어지면 호출 몫 소진과 똑같이 감시 중단(degraded) → 평가기 간격 폴링이 안전망
- 노선 정류장 수는 첫 노선 응답에서 배우고, 모르면 정류장 단위부터(가벼운 쪽)
- 기본값: 데이터 몫 0(=켜도 아무것도 안 부름). 켜는 값은 운영 수신량 실측 뒤 사용자가 정함

## 건드는 곳
BusRouteWatcher(방식 선택·바이트 몫), SearchTimeBusQueryPort.BusQueryResult(응답 바이트 수), SearchTimeBusAdapter·SeoulBusApiAdapter(본문 크기 기록), ReevaluationProperties·application.yaml(데이터 몫), JourneyReevalMetrics(방식별 호출·바이트 지표). 마이그레이션 없음

## 리스크
- 정류장 단위로 바꾼 노선은 같은 키를 평가기도 부를 수 있음 → 캐시 키가 같아(정류장·노선·순번) 한 번만 부름. 계약 테스트로 확인
- 월 수신 예산의 나머지(지하철 위치 5초 수집 등)가 이미 얼마를 쓰는지 모름 → 데이터 몫 숫자는 운영 측정 전엔 못 정함(사용자)

## 검증법
방식 선택 계약 테스트(k 작음→정류장, k 큼→노선, 데이터 몫 소진→중단, 호출 몫 거의 소진→노선 쪽으로 기움, 정류장 수 모름→정류장), 바이트 계량 테스트, 사다리 2,000 에 가짜 공급자 응답 크기를 실측대로 넣고 감시 켬/끔 비교(감지 p95·호출·바이트). 전체 테스트 기존 무관 12건 외 0.
