# 탑승 때 고른 버스로 추적 (#598)

## 뭘 하나
앱이 "이 버스를 탔다"고 알리는 API 를 추가한다. 서버는 그 노선으로 선택을 바꾸고, 도착 예측과 환승 판정, 차량 추적을 그 노선 기준으로 다시 잰다.

## 왜
지금은 묶음의 첫 노선으로만 추적한다. 다른 묶인 버스를 타면 노선 번호, 실시간 도착, 차량 위치가 틀린다.

## 핵심 결정
- 새 API `POST /api/journeys/{id}/bus/route-selection {routeOptionId, routeRevision, legIndex}`. 지하철 열차 선택 API 와 같은 모양. 탑승 이벤트에 칸을 얹는 안은 재전송 판정이 복잡해져 기각.
- 개정본을 새로 만들지 않고 선택만 바꾼다. 묶인 노선은 서는 정류장이 같아 구간 구조가 안 변하기 때문.
- 바뀌는 값: 선택 노선, 노선 id. 옛 노선으로 잰 도착 예측은 비운다. 탑승 진행도, 소요시간, 정류장은 그대로.
- 명령 번호는 올리지 않는다(올리면 바로 뒤에 오는 탑승 전환이 거절된다). 평가 번호만 올린다.
- 재탐색을 수락해도 고른 노선이 유지된다(전에는 첫 노선으로 되돌아갔다).
- 지도 좌표의 버전 키가 바뀐다. 앱은 선택 뒤 좌표를 다시 받는다.
- 탑승 중에도 다시 고를 수 있다(잘못 골랐을 때). 탑승이 끝난 구간은 거절.
- 응답은 여정 스냅샷 전체. 앱이 그대로 화면에 반영.

## 건드는 곳
새 컨트롤러와 요청 DTO, BusRouteSelectionService/TxService(신규), JourneyLeg, JourneyEventType, RerouteAcceptTxService(선택 규칙 공용화), 앱(jette-app#127)

## 리스크
- 평가 워커와 같은 여정을 동시에 고친다. 이벤트 적용과 같은 잠금 규칙을 따라야 한다.
- 여정 시작 때 후보마다 노선 id 와 정류장 순번이 채워져 있어야 고른 노선의 실시간을 물을 수 있다. 비어 있으면 같이 고친다.
- 다른 지역 노선이 묶인 경우 고른 노선의 실시간 id 가 없을 수 있다(도착 정보 없음으로 표시).

## 검증법
계약마다 테스트: 선택 반영, 옛 값 비움, 재선택 무변화, 다른 구간 후보 422, 낡은 개정본 409, 끝난 탑승 422, 버전 증가, 선택 뒤 평가가 새 노선으로 조회.
