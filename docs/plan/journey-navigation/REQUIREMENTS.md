## 0. 1차 구현 범위

1차 구현은 다음 여섯 가지로 제한한다.

| 순서 | 기능 | 요구사항 연결 |
|---|---|---|
| 1 | Journey 상태머신 | J1~J9, B1~B3 |
| 2 | 실시간 ETA와 환승 가능성 계산 | T1~T9·T11, E1~E7·E9 |
| 3 | 버스 하차 안내·알림 | A1~A5, N3 |
| 4 | 환승 정류장 도착·임박 시 부분 경로 재탐색과 변경 제안 | R1~R8 |
| 5 | 백그라운드 진행·FCM 여정 알림·lease 기반 종료와 복원 | G1~G6 |
| 6 | 이벤트 멱등성·버전 충돌·알림 중복 방지 | C1~C6 |

운영 계측, 데이터 신선도 판정, 개인정보 보호는 위 기능을 안전하게 제공하기 위한 비기능 요구사항이며 별도 제품 기능으로 범위를 확장하지 않는다.

## 1. 제품 정의

Nextroute 내비게이션은 단순한 경로 검색이 아니라 진행 중인 `Journey`를 추적하는 기능이다.
핵심 차별점은 "버스가 몇 분 후 오는가"가 아니라 다음 질문에 답하는 것이다.

> 현재 교통수단에서 하차하고 환승 지점으로 이동했을 때, 다음 버스를 실제로 탈 수 있는가?

서비스는 사용자 환승 준비 시각과 다음 버스 도착 예측을 같이 갱신하고, 환승 가능성·여유시간·다음 행동을 안내한다.

## 2. 적용 원칙

- 0절의 **여섯 가지 1차 구현 범위**를 필수 범위로 고정한다.
- 모든 필수 기능이 인수 기준을 통과해야 1차 기능을 완료한 것으로 본다.
- 자동 탑승·하차 감지는 제외하고, 1차에서는 사용자 확인을 기준 상태로 삼는다.
- 포그라운드는 REST 적응형 폴링, 백그라운드 알림은 Firebase Admin SDK 기반 FCM 단일 sender를 사용한다. iOS 메시지는 FCM을 거쳐 APNs로 전달한다.
- 정상 background에서는 Journey를 유지하고, 모바일 heartbeat가 기본 3분 lease를 연장한다.
- lease가 만료되면 원인과 관계없이 Journey를 `EXPIRED`로 종료하고 평가·알림을 중단한다.
- WebSocket과 SSE는 1차 필수 범위가 아니다. 계측 결과가 도입 임계를 넘을 때만 재검토한다.
- 정밀 위치 궤적은 기본적으로 서버에 영구 저장하지 않는다.
- Journey API는 OAuth 로그인 후 백엔드가 발급한 Nextroute access token 인증을 필수로 한다.
- Journey의 소유자는 OAuth provider와 독립된 내부 `userId`다. Kakao·Google 등의 provider subject는 `auth_identity`로 내부 사용자에 매핑한다.
- access token은 내부 `userId`에 연결한다. Journey API는 `userId`를 클라이언트 입력으로 신뢰하지 않고 인증 정보에서 판별한다.
- 다중 기기는 1차 범위가 아니다. 기기 식별·안내 기기 추적·handoff를 하지 않는다. ([SCOPE-CHANGES.md](./SCOPE-CHANGES.md) SC-1)

## 3. 필수 여정 범위

| ID | 기능 | 인수 기준 |
|---|---|---|
| S1 | 도보 → 버스 | 도보 도착 시각과 버스 도착 예측을 비교한다. |
| S2 | 버스 → 버스 | 현재 버스 하차 ETA와 다음 버스 ETA를 연결한다. |
| S3 | 지하철 → 버스 | 지하철 하차 ETA와 환승 도보 후 버스 ETA를 연결한다. |
| S4 | 버스 → 지하철 | 버스 하차 후 지하철 승차까지의 여정 진행을 안내한다. |
| S6 | 다중 환승 | 하나의 Journey에서 복수 TransferConnection을 순서대로 평가한다. |

다음 버스가 없는 환승에도 여정 상태 추적은 적용하지만, "환승 버스 탑승 가능성"은 다음 leg가 버스인 S1·S2·S3에 적용한다.

#### 환승 상태

| 코드 | 사용자 표현 | 의미 |
|---|---|---|
| `COMFORTABLE` | 여유 있음 | 보수적 버퍼를 포함해도 환승 가능 |
| `CATCHABLE` | 환승 가능 | 정상적으로 이동하면 환승 가능 |
| `AT_RISK` | 환승 주의 | 지연 또는 불확실성으로 실패 가능성 있음 |
| `MISSED` | 환승 실패 예상 | 다음 버스 또는 재탐색 필요 |
| `UNKNOWN` | 판단 불가 | 데이터 누락·stale·매칭 불가 |

#### 핵심 계산값

```text
userReadyAt = currentLegArrivalAt + alightingBuffer + transferWalkingTime
transferSlack = nextBusArrivalAt - userReadyAt
```

`successProbability`는 예측 소스·모델 버전·예측 구간의 실제 오차 분포로 보정한다. 보정 근거가 부족하면 임의 숫자를 표시하지 않고 `UNKNOWN`으로 내린다.

| E1 | 목적지 도착 ETA |
| E2 | 현재 leg 종료 ETA |

| E5 | 클라이언트의 남은 시간 카운트다운 |

### 4.5 알림

| ID | 기능 |
|---|---|
| N1 | 탑승 정류장 접근 알림 |
| N2 | 탑승할 버스 접근 알림 |
| N3 | 하차 임박 알림 |
| N4 | 환승 방법 안내 |
| N5 | 환승 여유시간 안내 |
| N6 | 환승 위험도 상승 알림 |
| N7 | 환승 실패 예상 알림 |
| N8 | 다음 버스 또는 대체 경로 안내 |

- ETA의 작은 변동은 상시 화면만 조용히 갱신한다.
- 사용자 행동이 필요하거나 환승 상태가 하락할 때만 주의 알림을 보낸다.
- 중복 방지 키는 `journeyId:routeRevision:scopeType:scopeId:checkpoint:channel`을 기준으로 한다. 환승 알림의 scope는 transfer, 하차 알림의 scope는 leg다.
- 푸시 페이로드는 식별자·`commandVersion`·`evaluationVersion`·`routeRevision`·deep link만 담고, 앱이 REST로 최신 상태를 재조회한다.

|---|---|

| A2 | 구간별 ETA를 합산한 하차까지 남은 시간 계산 |

하차 알림 체크포인트는 서버가 판정한다. 클라이언트는 서버가 내려준 절대 `predictedAlightingAt`을 로컬에서 카운트다운하되, 자체 카운트다운만으로 새로운 알림 상태를 확정하지 않는다.

### 4.7 백그라운드

| ID | 기능 |
|---|---|
| G1 | 화면이 꺼져도 여정 진행 |
| G2 | 활성 여정 중 백그라운드 위치·heartbeat로 guidance lease 연장 |
| G3 | Android에서 FCM 여정 알림 수신 |
| G4 | iOS에서 FCM을 거쳐 APNs로 전달되는 여정 알림 수신 |
| G5 | ACTIVE lease 동안 서버의 차량 기반 평가·알림 유지 |
| G6 | 알림 선택 시 해당 여정으로 이동하고 최신 스냅샷 조회 |

백그라운드 위치 엔진은 클라이언트 책임이다. 서버는 클라이언트 관측 이벤트와 차량 실시간 데이터를 결합하고, Journey notification outbox를 Firebase Admin SDK로 발송한다. 정상 background에서는 lease를 갱신하며 하차·환승 위험·재탐색 제안 알림을 계속 평가한다.

iOS·Android는 사용자의 강제 종료 사실을 서버에 즉시·확실하게 전달하지 않으므로 heartbeat 중단으로 근사한다. 기본 3분 동안 heartbeat가 없으면 강제 종료·crash·네트워크 단절을 구분하지 않고 `EXPIRED` 처리한다. `EXPIRED` Journey는 재실행 시 복원하지 않는다.

### 4.8 환승 시점 부분 재탐색

| ID | 기능 |
|---|---|
| R1 | 환승 정류장 도착 또는 임박 상태 판정 |
| R2 | 환승 위험도 상승·버스 놓침 감지 |
| R3 | 현재 경로의 남은 구간 ETA 재계산 |
| R4 | 현재 위치 또는 환승 지점을 시작점으로 남은 구간만 부분 재탐색 |
| R5 | 기존 경로와 대안의 도착 ETA·환승 횟수·도보시간·데이터 신선도 비교 |
| R6 | 설정된 최소 도착시간 개선폭을 넘는 대안만 제안 |
| R7 | 동일 조건의 반복 탐색·제안 방지를 위한 cooldown·dedup 적용 |
| R8 | 사용자가 제안을 수락할 때만 새 `JourneyRevision` 활성화 |

재탐색은 여정 전체를 처음부터 다시 계산하지 않는다. 완료된 leg는 보존하고, 환승 지점에서 목적지까지의 남은 경로만 탐색한다. 1차에서 서버가 사용자 확인 없이 선택 경로를 교체하지 않는다. 새 경로는 만료 시간을 가진 `JourneyRevision` 제안으로 저장하고, 사용자가 수락할 때만 활성 revision으로 변경한다.

## 5. 필수 예외 처리

| ID | 상황 | 필수 동작 |
|---|---|---|
| X1 | 실시간 버스 정보 누락 | 신선도를 `UNKNOWN`으로 표시하고 확정적 전이·알림을 보류한다. |
| X2 | 탑승 차량이 실시간 목록에서 사라짐 | 즉시 여정을 실패 처리하지 않고 유예 기간 후 사용자 확인을 요청한다. |
| X3 | GPS 정확도 저하 | 사용자 위치로 leg를 확정하지 않고 차량·사용자 확인 근거를 우선한다. |
| X4 | 앱 process 중단 후 재진입 | lease가 ACTIVE면 최신 snapshot으로 복원하고, `EXPIRED`면 복원하지 않는다. |
| X5 | 푸시 중복·지연·누락 | 최신 Journey의 세 version을 조회해 복구하고 사용자 표시 중복을 방지한다. |
| X10 | 휴대폰·서버 시간 차이 | 서버 시각과 절대 ETA를 기준으로 표시 시각을 보정한다. |
| X11 | 강제 종료·crash·장시간 네트워크 단절 | 3분 heartbeat lease 만료 후 `CLIENT_LEASE_EXPIRED`로 종료한다. |

실시간 정보가 없을 때의 과거 운행기록·정적 시간표 자동 폴백은 1차 필수 범위가 아니다. 1차에서는 잘못된 확신보다 명시적 `UNKNOWN`과 수동 확인을 우선한다.
