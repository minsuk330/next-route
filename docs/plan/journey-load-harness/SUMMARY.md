# 여정 부하 실험 (Phase 4 ⑧, L티어)

## 뭘 하나

ACTIVE 여정을 1,000건·10,000건 만들어 평가기를 돌리고 잰 뒤, 결과를 `RESULTS.md`에 남겼다.

**결과: 게이트 불합격.** 10,000건에서 평가 지연 p95 92초(목표 10초), 적체 2,184 → 9,829 발산.
다만 원인은 claim 조회가 아니라 **선점을 나눠 주는 주기**였다 — 배치 100→500·tick 5초→1초만으로
처리량이 15.6 → 133건/s(8.5배)로 올랐다. 그래서 **Redis ZSET은 도입하지 않는다.**

## 왜

평가기를 운영에서 켜기 전에 "10,000명이 쓰면 버티는가"를 숫자로 답해야 한다. 답은 "지금 설정으로는
아니다"이고, 무엇을 바꿔야 하는지까지 나왔다.

## 핵심 결정

- **Redis ZSET 도입 안 함** — 병목이 "평가할 여정을 찾는 속도"가 아니라 "찾은 여정을 워커에게 넘기는
  속도"였다. 빠른 부분을 더 빠르게 만드는 셈이 된다
- **Gradle IT로 만든다** — `BusAlertEndToEndLoadIT`와 같은 방식(Testcontainers + 규모 env 조정).
  재현 가능하고 provider를 고정할 수 있다. 전체 스위트에서는 env 가드로 skip
- **여정은 JDBC batch insert로 만든다** — `StartJourneyUseCase`로는 준비만 몇 분. 단
  사용자당 ACTIVE 여정 1개 제약이 있어 **사용자 10,000명도 함께** 만들어야 한다
- **지연은 "예정 시각 → 저장 완료"로 잰다**(codex 리뷰) — 워커 실행 시간만 재면 선점·큐 대기가 빠진다.
  이를 위해 claim SQL이 선점 전 시각을 함께 반환하도록 프로덕션 코드를 최소 변경했다
- **⑦의 격리가 데이터로 확인됐다** — 워커를 4→16으로 늘려도 검색 요청 573건 중 LIMITED 0건. 대신
  처리량은 1.4배에 그쳤다(평가기 permit 4가 상한)

## 리스크

- 준비 시간이 측정 시간을 삼킬 수 있다 — 배치 크기 튜닝 + 준비 시간도 결과에 기록
- Mock provider 고정 지연이라 절대 성능치가 아니다. 증명하는 것은 "구조가 규모에서 안 무너진다"는
  성질뿐 — RESULTS.md에 명시
- 부하 IT가 전체 스위트에 섞이면 CI가 몇 분 늘어난다. env 가드를 먼저 넣는다

## 검증법

시나리오 5개가 재현 가능하게 돌고 `JOURNEY_LOAD` 없이는 skip 된다. 동시 선점 겹침 0건, 관심 수 대비
호출 수(관심 100개→평가 20건당 1회, 관심 10,000개→1건당 1회)가 확인됐다. `RESULTS.md`에 표와 게이트
판정이 남았다. 전체 스위트 회귀 0.
