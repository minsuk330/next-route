## 먼저 깨진 것

1. **③a 느린 FCM → relay 처리량.** relay 는 워커 4개가 한 건씩 동기로 보낸다. 처리량 = 워커 ÷ 왕복 시간(3.5초) ≈ 1.1건/초라
   폭주 700건이 10분 넘게 밀린다. 감지·적재는 멀쩡한데(감지 몫 p95 2.4초) relay 몫 p95 270초, 창 끝에 362건이 PENDING·PROCESSING.
   배치 200건을 잡아 놓고 4개로 보내므로 **배치 하나가 175~190초** — 회수 기준(PROCESSING 3분)에 붙었다. 왕복이 조금만 더
   길면 아직 워커 큐에 있는 행을 회수해 다시 잡는다(두 번째 잡힘이 첫 발송과 겹치면 중복). 긴급도 배치 FIFO(발송 예정 순)라
   긴급 p95 203초 ≈ 여유 296초와 크게 다르지 않다.
2. **④a worker 강제 종료 → PROCESSING 고착 3분.** 죽은 worker 가 잡아 둔 110행이 회수 기준 3분이 지나서야 다시 나갔다(relay 몫
   p95 182초). 만료 바닥(빠듯 = 발송 예정 + 180초)이 회수 기준과 같아 **1건이 회수 전에 만료**(잃음). 중복은 이번엔 0.
3. **③b·③c 고정 백오프 60초 × 3회.** 일시 오류 20% 에서 3연속 실패 확률 0.8% → 695건 중 2건 DEAD. 재시도마다 정확히 60초를 더해
   p95 79~94초. 전면 장애 60초는 전부 1번 실패 → 60초 뒤 **한꺼번에** 재시도(10초에 427건) → 장애 끝 27초 뒤 비움, 잃음 0.
   150초 장애는 0·60·120초 세 번 다 장애 안이라 걸린 행이 모두 DEAD(36/79). **장애 허용 한계 ≈ 2 × 백오프(120초).**
4. **④b 최소 한 번의 실제 중복.** 행 36999 가 kill -9 와 같은 초에 FCM 접수(가짜 발송처 기록) → `markSent` 전 사망 → 3분 뒤 회수·재발송.

5. **Redis 없음(④b 90초).** outbox·relay 는 DB 라 그 동안 497건을 그대로 보냈다(울릴 권리도 DB 칼럼이라 영향 없음). 대신
   **수집기가 스냅숏을 Redis 에 쓰다 실패해 변화 피드까지 못 감** → 이벤트 감지가 꺼지고 간격 폴링만 남음(주의·여유 감지 p95 112·134초).

## 지표 설계 (실험 1)

- `journey.notification.e2e{tier,checkpoint,delivery,source}` = FCM 접수 − 처음 본 시각. `journey.notification.hold{checkpoint,delivery}`(적재 때 payload `holdMs`),
  `journey.notification.lost{checkpoint,delivery,reason}`, `journey.notification.sent.after-expiry{checkpoint}`, `journey.notification.e2e.unmeasured{checkpoint}`,
  `journey.notification.detection.stamp{result}`. 하네스는 같은 값을 DB 행(payload `firstSeenAt`·`seenTier`·`seenSource`·`holdMs`)에서 다시 계산한다.
- 처음 본 시각: 수집기가 전 노선 응답을 받은 순간 → 변화 피드가 깨우는(미루는 것 포함) 여정마다 Redis `journey:seen:{id}` SET NX →
  평가 시작에 GETDEL → 위험 알림 payload. ① 폭주에서 feed 551 / evaluation 137 건.
- 한계
  - `evaluation`(표시 없음)은 평가 시작 시각이라 **하한**이다. 이번 하네스에선 프록시가 역별 응답에 폭주를 즉시 반영하고 전 노선 ALL 은
    다음 수집(최대 15초 뒤)에야 보여, 10초마다 폴링되는 긴급 여정이 먼저 본 경우가 많다 — 그때는 평가가 진짜 "처음 본" 순간이다.
  - 접근(N2)·재탐색·보드 push 는 처음 본 시각이 없다(시간·검색이 낳는 알림). 버스 감시자 깨우기도 표시를 안 남긴다.
  - "FCM 접수"는 가짜 발송처의 반환 시각이다 — 기기 도착(FCM → 기기)은 재지 않는다.
  - worker 를 재기동한 칸(④)은 worker 프로세스 지표가 0 부터 다시 쌓여 요약기의 worker 차분이 틀리다 → SLO 는 DB 행·접수 기록으로 셈.

### 지금 먼저 깨지는 것

1. **느린 FCM 에서 relay 처리량(여전히 1등).** PULL 32 워커 ÷ 왕복 3.5초 ≈ 9건/초(실측 94~96건/10초, BEFORE 의 7배). 폭주 700건이 1분 남짓에
   비워져 여유 SLO 는 지키지만 긴급(≤32초)·주의(≤47초)는 못 지킨다(긴급 p95 36~78초). 더 줄이려면 워커 수를 늘리거나
   비동기 발송(#446 후보 1의 나머지)이 필요하다.
2. **긴급을 먼저 보내는 장치가 이 폭주에서 효과 0.** 우선순위는 체크포인트로 정해서(플랜 Opus 6) 빠듯·놓침은 모두 0 이다. 폭주 알림은 전부 빠듯이라
   PRIORITY_FIRST 와 SCHEDULED 의 순서가 같다(③a AFTER 와 PULL 만의 차이는 칸 사이 흔들림 — 두 칸의 처리량이 같다). 우선순위가 일하는 경우는 빠듯·놓침과
   접근·재탐색이 섞여 밀릴 때뿐인데, 이번 하네스는 그걸 만들지 않는다(재탐색·보드 꺼짐).
3. **지수 재시도의 마지막 간격이 만료를 넘으면 그냥 취소된다.** ③c' AFTER 42건: 장애 시작 15초 전에 만들어진 바닥 수명(180 + 보류 17 = 197초) 행이
   0·24·48·60초 뒤 네 번 다 장애 안에서 실패 → 다음 60초가 만료를 넘어 `expired-before-retry`. **장애가 끝나고 만료까지 32초가 남아 있었는데도** 버렸다.
   마지막 시도를 "만료 직전"으로 당기면(간격 = min(다음 간격, 만료 − 여유)) 이 42건은 살릴 수 있었다. BEFORE 의 DEAD 713 에 비하면 크게 줄었지만 0 은 아니다.
4. **60초 장애에서는 지수 재시도가 고정 60초보다 늦다.** 24 + 48 = 72초 > 60초라 장애 직후 첫 기회를 12초 놓친다(relay 몫 p95 62.7 → 81.3초). 잃음은 둘 다 0.
5. **회수된 행은 대기열 맨 뒤로 간다.** ④a' AFTER 에서 회수는 45.6초인데 접수는 85~94초 — 회수가 `scheduled_at` 을 지금으로 다시 써서, 밀려 있는 500행 뒤에 줄을 선다.
   aging(created_at 기준)이 우선순위를 0 으로 올려도 다른 행도 다 0 이라 `scheduled_at` 으로 갈린다.

### 권고

- **기본값 전환: `relay.mode=PULL` + `claim-timeout-seconds=45` 는 바꾼다.** 근거: 느린 FCM 처리량 7배, 미발송 414 → 0, kill 뒤 고착 180초 → 45초(잃음 3 → 0),
  중복 0, 커넥션 대기 변화 없음(풀 20 그대로), DB 시간 몫 +1~4%.
- **`retry-policy=EXPONENTIAL` 도 바꾸되, 마지막 간격을 만료 안으로 당기는 수정을 같이 또는 먼저.** 이득(20% 오류 DEAD 7 → 0, 150초 장애 잃음 713 → 42)이
  손해(60초 장애 relay p95 +19초)보다 크다. 위 3번을 고치면 150초 장애 잃음도 0 에 가까워질 것으로 본다(미측정).
- **`claim-order` 는 SCHEDULED 그대로.** 이번 측정에서 효과가 없었고(위 2번), 효과를 보려면 빠듯 안에서 긴급을 가르는 기준(예: 남은 시간)이 필요하다.
- **`idx_journey_notification_claim_priority` 는 지우는 쪽.** PR-2 EXPLAIN 대로 aging 이 있는 정렬은 이 인덱스를 안 타고, 기본도 SCHEDULED 로 둔다면 쓰는 쿼리가 없다
  (PENDING 부분 인덱스라 비용은 작다 — 급하지 않은 별건 마이그레이션). PRIORITY_FIRST 를 나중에 aging 없이 쓰기로 하면 그때 다시 만든다.

### 한계 (이번 절)

- 노트북 한 대, 칸·설정마다 1회. 같은 설정끼리도 칸 사이에 폭주 노선 여정 수·수집 타이밍이 달라 감지 몫이 흔들린다(① AFTER 감지 p95 36초 vs BEFORE 19초) — relay 몫을 같이 본다.
- ③c'·④a' 는 #446 과 칸 모양이 다르다: ③c' 는 이번엔 아침이라 폭주가 컸고(적재 825), ④a' 는 kill 순간 발송 중인 행이 있도록 느린 FCM 을 얹었다.
- 우선순위 효과는 이 하네스로 못 잰다(전부 빠듯). Redis 장애(④b)는 PR-3 의 변화 피드 분리를 따로 재지 않았다(이번 범위 밖).
