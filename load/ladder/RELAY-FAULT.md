# relay 장애 주입 끔/켬 (#464)

## 결론

- **heartbeat(회수 45초) 는 강제 종료된 worker 의 알림을 만료 전에 되살린다.** 고정 타임아웃 180초는 3회 모두 179~186초에 처음 회수해 17~26건이 만료로 취소됐다. heartbeat 는 3회 모두 44.9~46.7초에 회수했고 잃은 알림은 0건이다.
- **fencing token 은 멈췄다 깨어난 worker 의 늦은 기록을 전부 버린다.** 끔에서는 회차마다 늦은 기록 133~151건이 검사 없이 반영됐고(그중 행을 대기로 되돌린 실패 기록 45~56건), 그 대가로 B 의 정상 기록 62~94건이 거부됐다. 켬에서는 반영 0건, B 거부 0건이다.
- **행 단위 추적: 끔에서 되돌려진 44행 중 11행이 한 번 더 발송됐다(12번). 켬에서 거부된 늦은 실패 기록 38행은 추가 발송 0행.**
- **대가: heartbeat UPDATE 는 DB 실행 시간의 0.98~2.58%.**
- 두 번 접수된 행(끔 72~85, 켬 89~107)은 fencing 으로 줄지 않는다. A 가 멈추기 전에 이미 보낸 알림을 B 가 다시 보내는 몫이고, 최소 한 번 보장에서 생긴다(collapse key 로 기기에서 합치는 쪽).

## 조건

- 노트북 M3 Pro 11코어, st-pg(PostgreSQL 컨테이너) 안 별도 DB `nr464`, worker JVM 2대(-Xmx1g, PULL 128, 포트 8091·8092)
- 적재: 개방형 생성기(relay_load_gen.py)가 outbox 에 직접 넣음, 여정 2,000개
- 가짜 FCM(LoadTestNotificationSender, 프로세스 안). 지연은 장애가 발송 도중에 걸리도록 일부러 길게 잡음(실제 FCM 속도 주장 아님)
- 같은 시간대에 다른 세션의 발송 용량 실험(#461)이 같은 기계에서 돌았다. DB·포트는 분리했고 CPU 는 공유

| 칸 | 장애 | 부하 | 가짜 FCM | 비교 |
|---|---|---|---|---|
| HB | 120초에 A `kill -9`, 8초 뒤 재기동 | 20/s × 420초, 만료 180초·600초 반반 | 2~5초 | 회수 기준 180초 대 45초 |
| FENCE | 60·200·340초에 A `kill -STOP` 60초 | 8/s × 420초, 만료 600초 | 5~15초, UNAVAILABLE 30% | 증서 끔(`relay.loadtest-unfenced`) 대 켬, 회수 45초 |

증서 끔은 #451 이전 코드처럼 "아직 PROCESSING 인가" 조건만 남기고 attempt_count 비교만 뺀다. 이미 끝난 행에 대한 늦은 기록은 끔에서도 상태 조건에 걸려 거부되므로 끔 숫자는 피해의 하한이다.

### 행 단위 추적 (보완 1쌍, relay_fault_trace.py)

A 의 시도는 실패라 접수 기록이 없다. 그래서 늦은 실패 기록이 남은 행에서 정상 발송 1번을 뺀 나머지 접수가 추가 발송이다.

| 회차 | 늦은 실패 기록 | 행별 접수 | 추가 발송 |
|---|---|---|---|
| 끔, 반영된 것 | 45건(44행) | 1번 33 / 2번 10 / 3번 1 | **11행 12번** |
| 끔, 상태 조건에 걸려 거부된 것 | 27건(27행) | 1번 26 / 2번 1 | 1행(73130, 반영된 늦은 기록도 있던 행) |
| 켬 | 38건(38행) 전부 거부 | 1번 38 | **0행** |

끔에서 되돌려진 44행 중 33행이 한 번만 나간 이유: 끔에서는 B 도 증서 없이 기록하므로, 되돌린 직후 B 의 발송 완료 기록이 그대로 덮어써 재발송 전에 SENT 로 끝났다. 그래서 11행도 하한이다.

## 대가

| 칸 | heartbeat UPDATE 몫(pg_stat_statements 상위 30문) | heartbeat 평균 |
|---|---|---|
| HB | 0.98~1.71% | 12~33ms |
| FENCE | 1.16~2.58% | 15~32ms (켬 r3 은 CPU 경합으로 평균 236~263ms, 최대 15초) |

## 한계

- 노트북 한 대, 가짜 FCM 이 프로세스 안. 실제 FCM 왕복·네트워크 분할은 없다
- 3번 접수된 행이 끔(r2 60731, trace 73124)과 켬(r1 57346, r2 63889) 양쪽에 1건씩 나왔다. fencing 과 무관한 경로로 보이며 원인은 미확인
- 증서 끔은 상태 조건을 남긴 하한 재현이다(#451 이전 실제 코드와 같은 조건)
- 기기 쪽 collapse key 합치기는 검증하지 않았다
