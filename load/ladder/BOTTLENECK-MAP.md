# 병목 지도 (#415-5) — 목표 부하에서 어느 단계가 먼저 SLO 를 깨나

측정일 2026-10-14~15. 로컬(앱·Postgres·Redis·k6 한 노트북, Postgres·Redis 는 Docker), 가짜 공급자(운영 7일 평균 지연: 서울 버스 73ms, ML 14ms, 정류장마다 같은 응답). 도구 = 이 폴더(README). 칸마다 시작 전 공급자 몫 카운터를 비우고, 끝나면 심은 여정을 지운 뒤 남은 여정 0 을 확인했다.
**자원 숫자(CPU·메모리)는 운영 사양과 달라 쓰지 않는다** — 단계 간 상대적 포화 순서를 본다. 서버 자원은 운영 동일 사양 서버에서 따로 잰다.

## 측정하며 걸린 것 (재현 시 주의)

- 공급자 몫 카운터(Redis 일 단위)를 비우지 않으면 앞 회차가 몫을 다 써, 평가가 공급자를 못 부르고 바로 끝나 처리량이 거짓으로 빨라진다 → `run_ladder.sh` 가 시작 전 비움.
- Gradle 은 환경 변수를 입력으로 안 봐서, 지우기를 `cleanTest` 없이 부르면 조용히 건너뛴다 → 회차마다 여정이 쌓여 칸 이름보다 큰 부하로 측정됐다(첫 측정 전부 무효, 위 표는 재측정).
- 가짜 도착 응답이 매 호출 무작위면 판정이 늘 "바뀜"이라 조회가 늘 200 → 정류장마다 같은 응답으로.
- 가짜 ML 이 JDK HttpClient 의 chunked 본문(h2c 업그레이드 시도)을 못 읽어 모델 응답이 전부 실패 → chunked 읽기.

## 한계

- 로컬 한 대, 앱 한 JVM(api+worker). 운영은 api·worker 분리 + 다른 사양. 6,000 의 DB 포화는 노트북 Docker Postgres 한계와 섞여 있다.
- 판정이 고정 응답에서도 늘 "바뀜"(실시간 도착 초가 공급자 생성 시각 기준이라 절대 예정 시각이 매번 조금씩 움직이고 `hasChanged` 가 그대로 비교) → 무변화 백오프가 안 걸려 평가 수요가 운영보다 클 수 있다. 운영에서도 버스 여정 평가 번호가 자주 올라 앱 204 비율을 낮추는 별건 관찰.
- 경로 검색(OTP) 제외(운영 단일 엔진) — 읽기 부하로 대체. 지하철·알림 발송 미포함.
- 20,000 칸은 돌리지 않았다 — 6,000 에서 이미 로컬 DB 가 포화.
