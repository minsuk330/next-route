# 발송(relay) 용량 — 한계점과 병목 (#461)

**결론: FCM 이 정상(60ms)일 때 worker 한 대의 발송은 초당 약 1,100~1,300건에서 무너지기 시작했다. 먼저 바닥난 것은 DB 커넥션 풀(20개)이다.** 한계점 단계에서 풀 사용 중 커넥션이 평균 20.0개(가득)였다. 같은 때 Postgres CPU 는 4.2~4.5코어(도커 VM 11코어 중), JVM CPU 는 1코어 미만으로 여유가 있었다. 한계점 아래(800건/초 이하)에서는 3회 모두 잃음·중복·회수가 0이었고 relay 지연 p95 는 0.4초 이하였다.

비유하면 "직원 128명이 계산대 20개를 나눠 쓰는 가게"다. 직원(발송 스레드)은 남고 손님 처리(SQL 실행 자체)도 빠르다. 그런데 직원이 계산대를 잡은 채로 왕복(트랜잭션 시작, 조회, 기록, 커밋)을 여러 번 하니, 계산대가 꽉 차면 나머지 직원은 줄을 선다.

> **이 문서가 판정하지 않는 것**: 운영 사양(VPS)의 절대 숫자, FCM 이 느릴 때(사용자 결정으로 제외 — FCM 정상 가정), 평가기와 같이 돌 때. 노트북 한 대(도커 VM 11코어·8GB)에서 worker·Postgres·생성기가 기계를 나눠 쓴다.

## 병목: 커넥션 풀이다 (DB CPU 가 아니다)

- **풀이 가득 찬 단계 = 한계점 단계**: 3회 모두 무너진 단계에서만 사용 중 커넥션 평균이 19.9~20.0(최대 20)이었다. 바로 아래 단계는 8~14
- **Postgres 는 여유**: CPU 4.2~4.5코어 / 11. SQL 실행 시간 합은 초당 1.4~1.6초 — 커넥션 20개 중 평균 1.5개 몫만 "SQL 을 실제로 돌리는" 데 쓰였다
- **그럼 커넥션은 무엇을 하며 잡혀 있나**: 한 건 발송에 트랜잭션 약 2.5개, 문장 약 5개(알림 조회 2번, 토큰 조회, 여정 조회, SENT 기록 + claim 1/2)가 오간다. 한계점 처리량(약 1,300건/초)에서 커넥션 20개 ÷ 1,300건 ≈ **건당 15ms 를 커넥션을 쥐고 있고, 그중 SQL 실행은 약 1.4ms** 다. 나머지는 JDBC 왕복(도커 네트워크)과 트랜잭션 안의 앱 처리다
- **claim 이 점점 느려짐**: claim(`FOR UPDATE SKIP LOCKED`) 평균이 400건/초 0.21ms → 800건/초 0.30ms → 1,200건/초 0.88ms(r3). 잠긴 행을 건너뛰는 일이 늘어서로 보인다(확인 안 함). 아직 몫은 DB 시간의 약 30%로 주범은 아니지만, 풀을 늘리면 다음 후보다
- **스레드·JVM 은 아님**: 스레드 175개 고정, JVM CPU 1코어 미만, GC 단계당 0.5~0.9초

## 따라 나오는 것

- worker 한 대·풀 20 의 발송 용량 ≈ 초당 1,000~1,300건(노트북 기준). 목표 부하(DAU 1만, 피크 동시 여정 약 2,000)의 긴급 알림 속도와 비교하면 수십 배 여유다 — 발송은 지금 병목이 아니다
- 처리량을 더 원하면 손잡이 순서: ① 풀 크기(A' 풀 40 칸으로 직접 확인) ② 건당 왕복 수 줄이기(알림·여정·토큰 조회를 한 번에, claim 과 같이) ③ worker 증설(#458 — leader-lease 먼저)
- 이 실험에서 발송은 DB 를 혼자 썼다. 운영에서는 평가기가 같은 풀·같은 DB 를 쓰므로 실제 한계는 더 낮다 → 다음 칸 "발송 + 평가기 같이"

## 한계와 주의

- 회차 사이 편차: 한계점이 r1 은 1,600, r2·r3 는 1,200. 1,200건/초 단계가 "간신히 버팀"과 "무너짐"의 경계다. 같은 노트북에서 다른 프로그램 부하가 영향을 줬을 수 있다
- 앞선 A-r1(23:20 이전, 계단 800까지)의 800건/초 lag p95 는 2.05초, PG CPU 3.54코어로 이번(0.26~0.40초, 2.0~2.95코어)보다 나빴다. 원인은 확인하지 않았다(그 회차는 사용자 요청으로 중단된 사슬의 일부)
- 가짜 발송처 접수 TSV 는 껐다(켜면 하네스 자체가 병목). 중복 판정은 `duplicate.id` 지표만 쓴다
- 절대 숫자는 노트북 값이다. 운영 VPS 사양으로 옮기지 말 것 — 옮길 것은 "풀이 먼저 찬다"는 순서와 "건당 커넥션 15ms 중 SQL 1.4ms" 라는 비율이다
